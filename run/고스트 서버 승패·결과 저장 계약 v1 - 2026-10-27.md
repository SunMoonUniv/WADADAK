# 고스트 서버 승패·결과 저장 계약 v1 · 2026-10-27

## 범위

시작 승인에서 고정한 본인 상대와 종료 후 업로드된 원본 입력으로 서버가 승리·패배·무승부·무효를 확정하고 저장한다. 기존 코스 판정기를 재사용하며 앱의 완주 안내·평균 페이스·세션 전체 시간을 판정 근거로 바꾸지 않는다. 공개 상대·대결 결과 화면·상세 재생 조회는 후속이다.

현재 `feature/F09-ghost-recovery`의 기기 복구 변경에 이어 구현한다. 앞서 생성한 시작 승인 PR은 수정하지 않는다. 이 문서의 로컬 구현은 담당자 공동 리뷰·CI·운영 반영을 뜻하지 않는다.

## 처리와 판정 순서

1. 기존 세션 준비/원본 업로드/status 경로를 사용한다. 세션 ID·startedAt·입력 순번·최종 순번은 바꾸지 않는다.
2. 모든 입력이 도착한 PROCESSING 세션만 기존 `RunService.process`에서 처리한다. 누락·잘못된 스트림은 승패를 추정하지 않는다.
3. 기존 `CourseRunService`/`CourseJudge`가 시작 때 저장한 코스 경로로 완주 여부·코스 총 소요시간을 판정한다.
4. `ghost_starts`의 고정 상대 ID·정수 초·원본 완주 ms를 읽는다. 상대 원본·현재 코스·재생 상세·다른 모듈을 재조회하지 않는다.
5. 아래 규칙으로 판정하고 결과 요약을 저장한다. 양수 거리 기록은 기존 개인 기록/목록 요약의 `ghost`에도 같은 값을 넣는다. 기존 기록 등록 이벤트와 DONE 처리까지 같은 트랜잭션이다.

| 서버 판정 | 결과와 사유 |
| --- | --- |
| 완주 확인 | 러너의 서버 확정 코스 총 소요시간이 상대 정수 초보다 짧으면 WIN, 길면 LOSE, 같으면 DRAW. `COMPLETED_TIME_COMPARISON` |
| 미완주·자발적 마감, 고스트 도착 전 | INVALID / `VOLUNTARY_BEFORE_GHOST_FINISH` |
| 미완주·자발적 마감, 고스트 도착 시각 이상 | LOSE / `VOLUNTARY_AFTER_GHOST_FINISH` |
| 미완주·복구 불가 중단 | 도착 전·동시·후 모두 INVALID / `INVOLUNTARY_INCOMPLETE` |
| 앱 ROUTE_END 안내가 있으나 서버 미완주 | INVALID / `FINISH_NOT_CONFIRMED`. 앱 안내만으로 승리나 자발적 패배를 만들지 않는다 |

- **완주 우선:** 종료 사유가 INTERRUPTED·PERMISSION_REVOKED·ACCOUNT_CHANGED여도 구간 종료 이전 자료에서 서버가 완주를 확인했다면 정상 시간 비교다.
- **첫 구간 경계:** 첫 SEGMENT_END, 없으면 END로 대결 마감 시점·사유를 정한다. SEGMENT_END/COURSE_ONLY 또는 END/USER만 자발적 마감으로 본다. 알 수 없는 구간 종료 사유는 자발적 종료로 추정하지 않는다.
- 코스만 종료한 뒤 세션이 오래 이어지거나 비자발적으로 끝나도 먼저 닫힌 대결의 사유·시점을 바꾸지 않는다. 구간 종료 이후 GPS는 기존 코스 판정기에서 제외한다.
- 수동 정지·정상 복구 공백을 포함한 총 소요시간을 사용한다. 정상 60초 복구 자체는 종료가 아니므로 이후 실제 완주·구간 종료 입력으로 판정한다.
- 완주 비교에는 기존 서버 `courseElapsedSeconds`와 시작 때 고정한 `source_elapsed_seconds`를 그대로 사용한다. 기존 CourseJudge의 `floor(ms/1000)` 잠정 구현과 D-13 검토 상태를 유지하며 별도 반올림 규칙을 만들지 않는다. 같은 정수 초의 초 미만 차이로 무승부를 나누지 않는다.
- 미완주 시 고스트 도착 여부는 첫 마감 입력의 `elapsedMs >= source_duration_ms`다. 같은 초여도 실제 원본 도착 ms보다 이르면 선도착으로 보지 않는다. 측정 시각/업로드 시각/서버 시각으로 대체하지 않는다.
- 기존 고스트 원본 적합성 30초/5% 규칙은 진행 중 대결을 자동 종료하거나 무효화하는 기준이 아니다.

## 저장 모델과 재시도

`V20261027_2000__run_ghost_results.sql`이 run 스키마에 `ghost_results`를 추가한다.

| 컬럼 | 용도 |
| --- | --- |
| session_id UUID PK/FK | ghost_starts에 ON DELETE CASCADE. 대결당 요약 하나 |
| finalized_at TIMESTAMPTZ | 서버가 최종 판정을 저장한 시각. 최초 등록과 같은 마이크로초 정밀도 |
| result_json TEXT | 아래 GhostOutcome의 불변 요약. 상대 GPS·재생 배열·프로필 없음 |
| created_at / updated_at | 공통 감사 컬럼 |

보존은 기존 정책 9.1의 ‘세션 종료 및 종료 후 결과 비교까지’를 따른다. 별도의 기간 만료·자동 삭제 기준을 추가하지 않는다. 본인 기록 삭제/탈퇴 때 요약·상세를 기존 삭제 경로로 정리한다. 상대 원본 삭제는 승인과 대결 결과에 전파되지 않는다.

기존 회원→세션 잠금으로 처리/삭제/탈퇴를 직렬화한다. 같은 업로드·중복 처리·동시 처리에서 결과 행과 등록 이벤트를 중복 생성하지 않고 최종 판정 시각을 갱신하지 않는다. 요약 저장 뒤 개인 기록 저장이 실패하면 전체 트랜잭션이 되돌아가고 PROCESSING 상태에서 재시도한다. 기존 입력·원본 결과를 고스트 조회 때문에 재계산/덮어쓰기하지 않는다.

양수 거리의 `records.result_json` 및 `summary_json`에 선택 `ghost`를 추가한다. 자유/일반 코스·과거 기록은 null이며 기존 생성자/JSON 역호환을 유지한다. 목록은 계속 summary_json만 읽고 상대 재생이나 GPS를 읽지 않는다. 과거 stats 보완 조회에서도 저장된 ghost를 유지한다. 다른 모듈 이벤트와 랭킹/코스 통계의 자격·필드는 바꾸지 않는다.

2026-10-27 main `99af5e4` 기반 재구성: main의 GPS 코스 등록 가능성 판단 `gpsGap`과 고스트 결과 `ghost`를 상세·목록 JSON에 함께 유지한다. `withGpsGap`/`saveGpsGap` 후처리와 과거 stats 보완 조회가 다른 필드를 지우지 않도록 병합했다. 기존 main 생성자와 과거 JSON 호환을 유지한다. GPS 코스 등록의 공백 판단과 고스트 원본의 30초/5% 적합성은 서로 다른 기준이며 이번 병합으로 합치지 않는다. 자유 기록 고스트는 정책·개발 계획만 확정된 상태로, 이번 재구성에서 새로 구현하지 않았다.

## 조회 계약

- `GET /api/v1/runs/sessions/{id}/ghost/result`: JWT 본인 전용 `ApiResult<GhostOutcome>`. 승인 전·최종 판정 전·다른 계정·삭제/탈퇴는 기존 RUN-002/404. 처리 상태는 기존 `/sessions/{id}/status`로 구분한다.
- 기존 `GET /api/v1/runs/records/{id}`의 `ghost`, `GET /api/v1/runs/records`의 각 목록 `ghost`도 같은 저장 요약을 반환한다. 상세 재생 자료는 포함하지 않는다.
- GhostOutcome 필드: `version="GHOST_RESULT_V1"`, `sessionId`, `sourceRecordId`, `outcome`, `reason`, `completed`, `courseElapsedSeconds`, `sourceElapsedSeconds`, `courseEndElapsedMs`, `sourceDurationMs`, `courseEndReason`, `finalizedAt`.
- `courseElapsedSeconds`는 기존 코스 판정 값이다. 완주면 실제 완주까지, 미완주면 구간 종료까지다. `courseEndElapsedMs`/`courseEndReason`은 첫 구간 종료 입력의 원본 경과 ms/사유로, 완주 시간 자체와 구분한다.

### 0거리와 전송 실패

유효한 0거리 고스트 업로드도 최종 대결 요약은 보존한다. 기존 개인 기록 정책은 그대로라 ZERO_DISTANCE/FAILED이고 일반 records나 등록 이벤트는 만들지 않는다. 이 경우에도 위 전용 API로 저장된 결과를 조회할 수 있다. 원본 입력 검증 실패는 결과를 만들지 않는다.

앞선 앱은 0거리 중단을 기기에 보존하지만 업로드 대상에 넣지 않는다. 따라서 **기기에만 있는 0거리 중단을 서버가 이미 판정한 것으로 표시할 수 없다.** 앱 업로드·결과 화면 연결 시 이 경계를 별도로 처리해야 한다. 서버가 미업로드/방치 세션에 시간만으로 승패를 생성하는 기능은 넣지 않는다.
