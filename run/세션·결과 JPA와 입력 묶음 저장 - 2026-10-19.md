# 러닝 세션·결과 JPA와 원본 입력 JDBC 묶음 저장

개발 정책 v3의 JPA 엔티티·BaseEntity 규칙과 달리기 개발 아키텍처 4장의 저장 역할 분담에 맞춰 러닝 영속 계층을 정리했다.

## 변경

- `RunSession`·`RunRecord`는 `BaseEntity<UUID>`를 상속하고 `run` 스키마를 명시한다. 세션 생성·상태 변경·결과 저장·조회·삭제·미발행 결과 처리를 Spring Data JPA 저장소로 옮겼다.
- 삭제 ID 예약과 탈퇴 회원 복사본도 같은 방식의 JPA 엔티티로 관리한다. 삭제·탈퇴 중복 처리와 늦게 도착한 업로드 차단을 유지한다.
- GPS·기압·케이던스·시작/종료 입력은 순번을 공유하므로 모두 `RunInputRepository`에서 원본 스트림으로 저장한다. 요청에 포함된 순번을 한 번에 조회하고, 기존 값과 요청 내부 중복을 비교한 뒤 새 행만 `JdbcTemplate.batchUpdate`로 최대 500개씩 묶어서 삽입한다. 원본 JSON 형식은 유지한다.
- 업무 서비스의 직접 SQL을 제거했다. `RunLocks`의 JDBC는 행이 아직 없는 ID도 보호하는 PostgreSQL 트랜잭션 잠금에만 사용한다. JPA 저장소의 일부 네이티브 쿼리는 처리 행 잠금과 기존 복합 커서·요약 전용 조회를 보존한다.
- `JpaTransactionManager`가 JPA와 JDBC에 같은 DataSource·트랜잭션 연결을 제공한다. 입력 삽입 전 부모 세션을 flush하고, 삭제 시 결과 → 원본 입력 → 세션 순서를 지켜 FK를 보존한다.
- 이벤트 발행·발행 완료 표시·결과 확정은 같은 트랜잭션에 남는다. 기존 등록 시각, 통계 보완 조회, 목록의 `summary_json` 전용 조회를 유지한다.

## DB와 API

기존 테이블·컬럼·외부 API·JSON 계약을 그대로 사용한다. 마이그레이션이나 기존 업무 데이터 변경은 없다. 회원 잠금 → 세션 ID 잠금 순서와 처리 행의 `FOR UPDATE SKIP LOCKED`를 유지한다.

## 검증

별도 Testcontainers PostGIS DB에서 기존 업로드·동시 처리·삭제·탈퇴·이벤트·기압/고도 호환 검증과 함께 다음 회귀 검증을 추가했다.

- 같은 요청 안의 동일 순번 재전송은 한 행만 저장하고, 값이 다른 중복은 요청 전체를 거부한다.
- 세션 생성 → 원본 묶음 저장 → 결과 생성의 JPA/JDBC 변경이 한 트랜잭션에서 함께 커밋되고 함께 롤백된다.
- 최초 세션 생성 요청이 동시에 들어와도 한 행만 생성되고, 다른 시작 시각의 재요청은 기존 값을 바꾸지 않는다.
