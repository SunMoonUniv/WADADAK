# 고스트 시작 승인 계약 v1 · 2026-10-26

2026-10-29 보완: 내 코스 원본의 메타 버전 호환과 확정 거절 뒤 재선택은 [보완 계약](<내 고스트 버전 호환·시작 거절 복구 보완 - 2026-10-29.md>)을 따른다. 현재 준비 코스의 버전·경로 검증은 유지하고, 같은 코스 ID·순서 있는 경로·거리의 과거 원본만 현재 버전에 맞춘 파생 재생으로 승인한다. 원본 결과·원본 버전은 보존한다.

상태: 구현·로컬 검증 대상. run REST 계약·RUN-004·run 마이그레이션은 공동 리뷰 대상이며 승인·머지·운영 적용 완료를 뜻하지 않는다.

## 범위

기존 내 고스트 선택/재생 준비 뒤 **본인 완주 1건을 상대에 고정하고 실제 코스 시작을 한 번 승인**한다. 세션 ID는 기존 코스 시도/향후 업로드와 같으며 별도 측정 세션을 만들지 않는다. 공개 상대·새 후보 정책·앱 시작 연결·60초 재개·승패 판정은 후속이다.

기존 `CourseApi.getRouteForRun` 조회 계약을 사용하며 타 모듈 DTO/스텁/이벤트는 새로 만들지 않는다. run 내부 저장은 run 스키마에만 접근한다. CourseRunStartedEvent/CourseActiveRunnersChangedEvent의 기존 양식·집계 경로를 재사용한다. 내부 API와 구현 변경은 이 계약/소스/테스트로 분리 검토할 수 있다.

## 호출 순서

1. 기존 `PUT /api/v1/runs/sessions/{id}/course`로 코스 준비. 응답의 courseId/version/route를 보존한다.
2. 기존 후보/재생 API로 내 완주를 선택한다. 메모리의 선택 준비 완료는 시작 승인이 아니다.
3. 같은 `id`와 `startedAt`을 고정하고 아래 POST를 보낸다. 성공하면 응답의 대결 코스와 고정 재생 자료를 사용한다. **별도 course/start 호출은 필요 없다.**
4. 응답이 유실되면 같은 ID로 GET 또는 모든 필드가 동일한 POST를 보낸다. 새로운 세션 ID/다른 startedAt으로 우회 시작하지 않는다.
5. 이후 기존 코스 구간 종료/종료 업로드를 같은 ID·startedAt으로 진행한다. 이번 승인은 최종 승패가 아니다.

앱의 내구성 저장/동일 단조 시계·실제 START 입력과의 연결은 다음 단계다. 이번 서버 구현을 기존 앱 start에 바로 붙인 것으로 표시하지 않는다.

## 요청

`POST /api/v1/runs/sessions/{id}/ghost/start` · JWT 인증 필수 · `ApiResult<GhostStartApproval>`

```json
{
  "courseId": "019e0000-0000-7000-8000-000000000001",
  "courseVersion": 3,
  "sourceRecordId": "019e0000-0000-7000-8000-000000000002",
  "startedAt": "2026-10-26T11:00:00.123456Z",
  "playbackVersion": "GHOST_PLAYBACK_V1"
}
```

courseVersion은 준비 응답의 비음수 버전이다. startedAt은 기존 코스/업로드 시작 시각과 같고 PostgreSQL에 손실 없이 저장 가능한 마이크로초 정밀도까지 받는다. 현재 시각보다 5분 넘는 미래는 기존 규칙대로 거부한다. 선택 화면 시각·GPS 표본 시각을 startedAt의 대체 값으로 쓰지 않는다.

## 승인 응답

- `version=GHOST_START_V1`, `sessionId`(대결 ID), `sourceRecordId`(상대 원본 ID).
- `startedAt`: 고정된 측정 시작 시각. `approvedAt`: 최초 서버 승인 시각. `courseValidatedAt`: 외부 코스 조회 응답을 받은 시각. 재시도에서 갱신하지 않는다.
- `course`: 기존 CourseSnapshot, sessionId는 **현재 대결**이다. 기존 준비 스냅샷을 유지한다.
- `playback`: GHOST_PLAYBACK_V1 재생 자료 전체. 이 안의 course.sessionId는 **상대 원본 기록**이다. durationMs·정수 초 비교 시간·정지/공백/위치·버전을 서버 저장 자료에서 다시 만들고 검증한다.

승인 영수증이며 현재 RUNNING/FINISHED 상태·서버 완주·승패를 뜻하지 않는다. 실제 임시 DB에서 생성한 전체 예시는 테스트 실행 후 `BackEnd/build/ghost-start-check/approved-own-ghost.json`에 남긴다. 개인정보 없는 합성 완주 자료다.

## 시작 승인 조건과 쓰기 경계

1. 요청자 본인의 준비된 코스 시도가 있어야 한다. 삭제 ID·탈퇴 회원·다른 계정·준비 없는 ID는 RUN-002.
2. 이미 일반 코스로 시작했거나 종료 업로드 세션이 생긴 시도는 고스트로 소급 전환하지 않는다. 상대 ID=현재 대결 ID도 불가.
3. `CourseApi.getRouteForRun`을 **쓰기 트랜잭션·run 잠금 밖에서** 호출한다. 코스가 현재 활성이고 준비 시점의 코스 ID/버전/거리/좌표 순서와 같아야 한다. 준비 후 변경됐다면 새 준비가 필요하다.
4. 쓰기 트랜잭션에서 회원→대결 ID 잠금을 다시 얻고 삭제/탈퇴/기존 승인/시작 상태를 재확인한다. 상대 소유권을 먼저 확인한 뒤 상대 ID 잠금을 얻어 서로 다른 계정의 ID 교차 요청으로 잠금 교착을 만들지 않는다.
5. 상대는 요청자의 서버 확정 완주이며 현재 선택 가능한 실제 원본/스냅샷을 갖고, 기존 30초·5% 재생 적합성을 통과해야 한다. 코스 ID/거리/좌표 순서는 대결 준비 자료와 정확히 같아야 한다. 원본 버전은 원래 값으로 재현·보존하며 현재 이하 버전일 때 이번 대결의 재생 기준 버전만 현재 준비 자료와 맞춘다(2026-10-29 보완). 상대를 자동 교체하지 않는다.
6. 승인 요약·상세 재생 자료·기존 코스 startedAt·도전/현재 러너 수 이벤트를 **같은 트랜잭션**에 저장한다. 도중 실패는 모두 롤백한다. 타 모듈 DB를 읽거나 새 도전/새 세션을 추가하지 않는다.

코스 조회와 run 쓰기를 분리하므로 코스 삭제/비공개와 승인 커밋을 가로지르는 분산 잠금은 없다. **성공한 시작 직전 CourseApi 조회를 코스 사용 가능성 확인 경계**로 삼고 `courseValidatedAt`을 남긴다. 그 조회 이후의 코스 변경은 이미 받은 시작 자료를 소급 폐기하지 않는다. 상대 원본 삭제와 승인은 같은 run 회원 잠금으로 직렬화되어, 삭제가 먼저면 거부하고 승인 커밋이 먼저면 고정 자료를 유지한다. 조회 경계를 넘는 완전 원자적 코스 삭제 차단이 필요하면 course 소유 계약을 별도 협의해야 하며 이번 구현의 보장으로 표시하지 않는다.

## 재시도·응답 유실

- 같은 세션과 courseId/courseVersion/sourceRecordId/startedAt/playbackVersion이 모두 같으면 최초 승인과 상세를 그대로 반환한다. 기존 코스/원본 상대를 재조회하지 않으며 도전 수·러너 수를 다시 올리지 않는다.
- 요청 필드 하나라도 다르면 RUN-003. 서버 원본이 사라졌다는 이유로 다른 기록으로 교체하지 않는다.
- 첫 조회 뒤 동시에 다른 동일 요청이 승인됐으면 최종 쓰기 잠금 안에서 그 승인을 반환한다. 외부 코스 조회가 실패한 동안 동일 승인이 커밋됐어도 저장 승인을 먼저 재확인한다.
- `GET /api/v1/runs/sessions/{id}/ghost/start`는 같은 JWT 소유자의 저장 승인/상세를 반환한다. 업로드용 run.sessions 행 생성 전에도 쓸 수 있다. 원본 삭제·코스 비활성 후에도 조회 가능하다.
- 승인 전 GET의 RUN-002는 아직 승인 자료가 없다는 뜻이다. **다른 시작 요청이 진행 중일 가능성까지 부정하지 않는다.** 같은 POST로 재시도한다. 취소가 필요하면 기존 본인 기록 삭제가 같은 ID를 예약하여 늦은 승인/업로드를 막는다.
- 본인 대결 삭제/회원 탈퇴 후 GET·POST는 RUN-002이며 저장된 승인/상세를 복원하지 않는다. 승인 후 구간 종료/업로드가 돼도 GET은 시작 사실을 재확인할 뿐 현재 주행 중이라고 표시하지 않는다.

## 저장·삭제·후속 범위

run.ghost_starts는 기존 course_attempts에, 상세 run.ghost_start_playbacks는 승인에 같은 스키마 FK/ON DELETE CASCADE를 둔다. 상대 source_record_id에는 FK를 두지 않는다. 상세는 코스 누적 위치/시간 파생 자료이며 상대 GPS 스트림·프로필을 복사하지 않는다. 본인 대결 삭제/회원 탈퇴는 기존 시도 삭제로 두 테이블을 정리한다. 업로드 전에는 sessions가 없으므로 삭제 시 course_attempts 소유자도 검사한다.

요약에 원본 ms·정수 초·정책/계산/재생 버전을 남긴다. 타인 탈퇴 익명화·공개 후보는 후속 구현이다. 고스트 자료는 기존 정책 9.1에 따라 세션 종료 및 종료 후 결과 비교를 위해 보존하며 별도 기간 만료를 추가하지 않는다. 기존 코스의 미업로드 시도 집계/만료 동작을 새로 정의하지 않는다.

공유 리뷰: RunContracts, RunErrorCode, RunService의 업로드 전 삭제 소유권 보강, CourseRunService의 소유권 조회 메서드, 새 run 마이그레이션. 기존 코스 시작/업로드/판정·F5/F6 측정 규칙·이벤트 필드는 유지한다. 공통 core/앱/다른 모듈 코드를 수정하지 않는다.
