# 1주차 — 기반과 계약

[전체 안내](README.md) · 다음: [2주차](02주차-자유-러닝-연결.md)

**목표:** Android·iOS에서 위치와 정지 입력을 기기에 저장하고 재실행해 확인한다. 앱·서버의 동일한 데이터 규격과 최소 저장 API를 준비한다.

## 1. 시작 조건 확인

A/B 배정과 run 모듈 관리자를 정한다. 작업용 프론트·백엔드 저장소를 준비하고 팀 규칙의 feature 브랜치에서 시작한다.

| A가 확인 | B가 확인 | 함께 확인 |
| --- | --- | --- |
| Flutter 버전·Android SDK·실기기, Mac/Xcode·iOS 서명·실기기 | Java 21·Gradle Wrapper, PostgreSQL/PostGIS·로컬 프로필 | 공통 코드 담당·정책 미합의 목록·계약 리뷰 시점 |
| 디자인 시스템·지도 키·위치/센서·SQLite 후보 | JPA·Security·Modulith·Flyway 실제 설정 | 앱 core·인증·CourseApi·RankingApi 제공일 |

환경이 없으면 담당과 확보일을 기록한다. 특히 iOS는 Windows에서 에뮬레이터 테스트로 대신 완료 처리하지 않는다.

## 2. 1일차 — 개발 뼈대 확인

1. A는 작업용 프론트 루트에서 flutter doctor -v와 flutter --version으로 도구 상태를 기록한다. 앱이 없다면 공통 담당과 경로·플랫폼을 확인하고 flutter create app으로 생성한다. 기존 앱이 있으면 새로 생성하지 않는다.
2. app/pubspec.yaml에 로컬 디자인 시스템 경로 ../packages/wadadak_design_system을 연결하고 WdTheme.light()·최소 러닝 진입 화면을 실행한다. 상태 관리·라우팅은 팀 선택을 사용한다.
3. B는 기존 의존성을 유지한 채 서버 기동과 로컬 DB 연결을 먼저 확인한다. PostGIS 확장·Flyway 설정·모듈별 마이그레이션 위치를 공통 담당과 연결한다.
4. **패키지부터 정렬한다.** 실제 Application은 com.wadadak.wadadakbackend, 설계는 com.wadadak이다. 공통 담당과 설계 기준 루트로 정렬하고 component/entity/repository 탐색·Modulith 모듈 발견을 테스트한다. 설계 경로에 run만 추가하고 탐색 여부를 생략하지 않는다.
5. run 공개 DTO·RunApi·RunErrorCode와 내부 스텁을 정의한다. app.stub.run, StubImplementation, prod의 StubGuard 규칙을 적용한다. API는 /api/v1/runs, 응답은 ApiResult를 사용한다.

산출물: 재현 가능한 환경 설정 안내, 최소 앱/서버 기동 결과, 패키지·공통 기반 작업 목록.

## 3. 2일차 — 데이터 계약과 저장 실험

1. 함께 세션 UUID·JWT 소유권·streamSeq 시작값·END/마지막 순번·UTC/ms/m·NULL 센서를 확정한다. 정수 초 변환과 registeredAt 정의는 랭킹 담당과 합의 상태를 적는다.
2. 생명주기 PREPARED/RUNNING/PAUSED/ENDED, 로컬 모드 FREE/COURSE/GHOST, 업로드 상태, 서버 판정 상태를 분리한다. 이번 주는 FREE만 연결한다.
3. A는 LocationService → RunRecorder → RunLocalStore를 연결한다. GPS와 START/PAUSE/RESUME/GAP/END는 같은 큐에서 순번을 받아 트랜잭션으로 저장한다. 화면 타이머만으로 원본을 관리하지 않는다.
4. 세션 상태·원본·마지막 저장 순번을 로컬에 남긴다. 프로세스 재실행 시 새 ID가 아니라 기존 세션을 읽어낸다. 이번 주 복구 검증은 “저장된 자료 재조회”까지이며 자동 재개 정책은 3주차에 확정한다.
5. B는 sessions·stream_records·gps_points·session_events·processing_checkpoints의 최소 스키마와 유니크 제약을 만든다. 다른 모듈 ID는 값으로 저장한다.
6. PUT /sessions/{clientSessionId}, POST /sessions/{id}/record, GET status의 성공·누락·충돌·소유권 오류 명세와 샘플을 작성한다. 계약 PR부터 리뷰한다.

산출물: 앱·서버가 읽는 동일한 free_pause 샘플, 로컬/서버 마이그레이션, 명세·스텁. [전체 안내의 샘플 규칙](README.md)을 따른다.

## 4. 3일차 — 짧은 실제 입력을 저장·조회

1. A는 실제 기기로 짧게 이동하고 수동 정지·재개한다. 위치 정확도·시각·순번·정지 이벤트가 저장됐는지 확인한다.
2. 앱을 종료·재실행해 마지막 저장 순번까지 원본이 남아 있는지 확인한다. 실제 저장 후 종료와 저장 직전 종료를 구분해 테스트한다.
3. B는 해당 비식별 검증 자료를 개발 DB에 저장·조회하고 같은 자료 재전송 시 레코드 수가 늘지 않는지 확인한다.
4. 두 사람이 시각·순번·표본 수를 비교하고 불일치가 있으면 변환·저장 경계부터 수정한다. 완성된 결과 화면은 2주차 범위다.

## 5. 4~5일차 — 양 플랫폼과 계약을 닫기

1. Android는 사용자가 보이는 화면에서 location foreground service를 시작하고 필요한 위치·서비스 권한·알림을 구성한다. 화면 잠금·다른 앱 사용 중 저장을 확인한다. 백그라운드에서 새 서비스 시작은 별도 조건으로 검증한다. [Android 공식 문서](https://developer.android.com/develop/background-work/services/fgs/service-types#location)
2. iOS는 Core Location 백그라운드 업데이트와 프로젝트 설정을 구성하고 같은 시나리오를 실기기로 검증한다. [Apple 공식 문서](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background)
3. 위치·SQLite 후보를 저장·백그라운드·라이선스·지원 환경으로 비교하고 팀 선택을 기록한다. 특정 패키지나 GPS 1초 주기를 확정 정책으로 간주하지 않는다.
4. 거리 오차·저장 지연·배터리를 동일 조건으로 측정할 방법과 개발 목표를 정한다.
5. 정책 제4부 4.2의 합의 결과 또는 미합의 담당/시한을 기록한다. 기존 정책 유지라면 이후 전송 설계 일정 변경을 기록한다.
6. 단독 run 기동·모듈 경계·DTO 직렬화·단일 순번 검증 후 다른 한 명이 시연 자료를 확인한다.

## 6. 검증 순서와 완료 기준

검증: 상태 입력 → SQLite 저장 → 재실행 읽기 → 서버 동일 샘플 저장/조회 → 양 플랫폼 화면 잠금 순서다. [검증 기록 템플릿](검증-기록-템플릿.md)에 증거를 남긴다.

- [ ] Android·iOS에서 짧은 측정 중 화면 잠금 후에도 입력이 저장된다.
- [ ] 재실행 후 동일 세션과 마지막 저장 순번·정지 이벤트를 읽는다.
- [ ] 앱·서버의 순번·시간·좌표·정지·NULL 계약과 샘플이 일치한다.
- [ ] 최소 서버 저장/조회·동일 자료 재전송 검증이 통과한다.
- [ ] 공통 기반·패키지 탐색·run 단독 기동·명세 리뷰 결과가 있다.
- [ ] 기술 선택·정책 합의 상태·타 파트 제공일이 기록돼 있다.

실패하면 환경 부족, 플랫폼 수집 중단, DB 내구성, 계약 불일치로 분류한다. 수집 중단을 해결하기 전 고스트 UI에 시간을 쓰지 않는다. 독립적인 명세/스텁 작업은 계속할 수 있다.

**주간 완료 증거:** 양 플랫폼 기기 정보·저장 전후 순번, 샘플/명세 버전, 기동/테스트 결과, 정책 결정 기록. 모두 통과한 뒤 2주차의 실제 연결을 진행한다.
