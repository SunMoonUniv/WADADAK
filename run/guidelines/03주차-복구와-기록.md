# 3주차 — 복구와 기록

[전체 안내](README.md) · 이전: [2주차](02주차-자유-러닝-연결.md) · 다음: [4주차](04주차-코스-대응과-이탈.md)

**목표:** 자유 러닝 기록이 화면 잠금·통신 단절·앱 종료·계정 전환에도 보존되고, 재전송·분석·삭제가 일관되게 동작한다.

## 1. 진입 조건과 준비 자료

2주차의 실제 한 건 저장·조회가 통과해야 한다. 마지막 저장 순번·등록 시각·서버 결과를 비교할 수 있어야 한다.

free_pause, missing_and_conflict, gap_and_recovery 샘플과 계정 A/B를 준비한다. 실패 실험은 테스트 기기·개발용 DB에서 한다. 앱 강제 종료와 일반 백그라운드 전환을 따로 기록한다.

## 2. 1일차 — 내구성 복구

1. A는 세션 원본과 상태 변경을 트랜잭션으로 저장하고, 저장 실패를 성공 측정으로 표시하지 않게 한다. 디스크 부족·DB 오류에서도 이미 저장된 자료를 보존한다.
2. 실행 시 사용자별 진행·종료·미전송 세션을 조회한다. 합의한 복구 안내·재개/종료 정책을 적용한다.
3. 실행 시계가 바뀐 구간은 clockSegmentId·복구/GAP 이벤트로 분리한다. 강제 종료 중 이동·센서 값을 만들지 않는다. 복구 시간 귀속은 앱 공통과 확정해 테스트한다.
4. SQLite 스키마 업그레이드 후 기존 진행·미전송 세션이 읽히는지 확인한다.
5. B는 저장된 판정 작업을 서버 재시작 후 다시 찾고 동일 세션 처리권·체크포인트로 재개한다. 메모리 큐만 믿고 작업을 잃지 않는다.

실험: 측정 중 화면 이탈 → 정상 종료·재실행 → 프로세스 강제 종료·재실행 → 재부팅·재실행. 마지막 저장까지 복구된 범위와 수집 공백을 각각 기록한다.

## 3. 2일차 — 재전송과 계정 분리

1. 종료 자료·전송 대기 상태를 기기 DB에서 읽는 SyncWorker를 만든다. 앱 재실행·연결 회복·수동 재시도에서도 같은 기록 ID를 사용한다.
2. 응답을 받지 못했으면 기존 ID의 status 또는 같은 멱등 요청으로 확인한다. 새 ID로 기록을 복제하지 않는다.
3. 전송 작업자는 세션별 중복 실행을 막는다. 일시적 통신/서버 오류는 합의한 backoff로 재시도하고 인증 오류는 갱신/재로그인, 충돌은 명시적 오류로 구분한다.
4. 서버 저장 확인 전 원본을 지우지 않는다. 보관 정리는 확정한 기기/서버 보관 정책에 따라 진행한다.
5. 계정 전환 시 이전 작업자를 중단하고 전송 직전에 현재 계정·기록 소유자를 다시 확인한다. 이전 세션 자료는 해당 계정 영역에 남긴다.
6. GPS 공백(GAP)과 전송 누락(빠진 순번)을 구분한다. 누락 보완 완료 전에는 최종 판정을 확정하지 않는다.

실험: 종료 직전 통신 차단 → 요청 중 차단 → 서버 저장 후 응답만 유실 → 앱 종료 → 재실행 → 계정 전환 → 원래 계정 재로그인. 서버에 1건만 남고 registeredAt이 바뀌지 않아야 한다.

## 4. 3일차 — 랩·센서·결과 분석

1. A는 총 정상 주행 거리 1km마다 자동 랩을 만들고 마지막 부분 랩을 실제 거리와 함께 저장한다. 정지/GAP를 가로질러 가짜 이동을 만들지 않는다.
2. 랩의 시간·거리·페이스 계산 및 경계 표본 분배 규칙을 B와 합의한다. 마지막 짧은 랩을 1km로 나누어 계산하지 않는다.
3. 케이던스·고도·수집 가능한 지표에 지원/품질 정보를 남긴다. NULL을 0으로 넣어 평균을 낮추지 않는다. 최소 자료가 없으면 —를 표시한다.
4. B는 저장 원본으로 랩·요약을 재계산하고 D3 구간 분석·D5 케이던스·D6 고도 화면과 연결한다.
5. 앱과 서버 계산 결과 차이는 원본·정지 경계·정밀도 수준에서 비교한다. 같은 반올림값이라는 이유로 시간 단위 오류를 통과시키지 않는다.

## 5. 4일차 — 음성과 기록 삭제

1. A는 MY의 기기 설정을 읽는다. 음성 기본 ON·거리 기준·1km, 거리/시간 중 하나만 선택한다.
2. 거리 음성은 세션 총 주행 거리, 시간 음성은 정지 제외 세션 달린시간을 사용한다. PAUSED에서는 재생을 중단하고 음성 OFF에서도 측정은 계속한다.
3. 같은 임계값 중복 재생·재개/복구 후 지난 안내 일괄 재생 억제는 제안 사항으로 MY와 합의 후 적용한다. 음악·이어폰·화면 꺼짐 출력 조건을 기록한다.
4. B는 소유권 검사 → 삭제 식별자/버전 보존 → 기록 삭제 → 삭제 이벤트 기록을 안전한 트랜잭션으로 연결한다.
5. 삭제 이후 늦은 업로드·판정 작업·등록 이벤트가 원본을 다시 살리지 않게 한다. 멱등 삭제의 응답 형식과 식별자 보관 기간을 계약에 남긴다.
6. 앱은 삭제 중 해당 세션의 업로드 작업을 정리하고 목록·상세 상태를 갱신한다. 서버 실패인데 성공 삭제로 끝내지 않는다.
7. 리뷰·랭킹 소비자가 아직 없다면 삭제 이벤트 발행과 계약 검증을 완료하고 실제 소비 확인은 7주차 항목으로 남긴다.

## 6. 5일차 — 실패 행렬 실행

| 조작 | 기대 결과 |
| --- | --- |
| 측정 중 네트워크 차단 | 측정·로컬 저장 계속, FREE 유지 |
| 화면 잠금·다른 앱 | 양 플랫폼 지원 조건에서 입력 지속 |
| END 직후 앱 종료 | 종료 상태·전송 대상 복구 |
| 같은 묶음 두 작업자 전송 | 한 기록, 같은 등록 시각 |
| 순번 하나 누락/다른 내용 | 누락 보완 대기/충돌 거부 |
| 계정 전환/토큰 만료 | 다른 계정 전송 없음, 저장 유지 |
| 판정 중 서버 재시작 | 동일 원본 처리 재개 |
| 삭제 후 재업로드 | 기록 재생성 없음 |
| 센서 없음·0거리 | — 표시, 가짜 평균 없음 |

[검증 기록](검증-기록-템플릿.md)에 기기/서버의 순번·레코드 수·작업 상태·등록 시각을 남긴다.

## 7. 완료 기준과 다음 단계

- [ ] 양 플랫폼의 화면 잠금·앱 종료·재실행 복구를 검증했다.
- [ ] 네트워크/응답 유실 후 같은 기록이 한 번만 등록된다.
- [ ] 계정 전환·인증 만료에도 원본이 유지되고 사용자 영역이 섞이지 않는다.
- [ ] 판정 재시작·누락/충돌·삭제 후 늦은 업로드가 검증된다.
- [ ] 자동 랩·부분 랩·센서 없음 상태·분석 화면이 연결된다.
- [ ] 거리/시간 음성과 MY 설정·정지 연동이 동작한다.
- [ ] 합의한 배터리·거리 오차 측정 결과와 남은 기기 문제가 기록돼 있다.

이 주는 자유 러닝 내구성 통과 지점이다. 저장 유실·중복·사용자 혼합이 남아 있으면 코스/고스트 연결보다 먼저 고친다. 4주차 합성 경로 자료·순수 판정 개발은 독립적으로 준비할 수 있다.
