# 2주차 — 자유 러닝 연결

[전체 안내](README.md) · 이전: [1주차](01주차-기반과-계약.md) · 다음: [3주차](03주차-복구와-기록.md)

**목표:** 실제 자유 러닝 1건을 시작 → 측정 → 정지/재개 → 종료 → 서버 등록 → 결과 재조회까지 연결한다.

## 1. 진입 조건과 이번 주 산출물

1주차의 로컬 저장·순번/시간 계약·최소 API가 통과해야 한다. 미완료 플랫폼은 별도로 남기고 양 플랫폼 완료로 세지 않는다.

산출물은 RunRecorder/MetricCalculator, 자유 준비·측정·정지·결과 화면, 멱등 업로드·판정·기록 조회 API, 실제 한 세션의 기기/서버 비교 기록이다.

## 2. 1일차 — 상태 전이부터 고정

1. A는 C5 자유 준비, H4 카운트다운, C4 측정, 일시정지, D1-2 결과의 최소 흐름을 디자인 시스템으로 조립한다. 지도는 실제 위치와 경로만 우선 표시한다.
2. 카운트다운 완료 때 START를 한 번 저장한다. 이전 카운트다운 취소는 실제 러닝으로 세지 않는다.
3. 정지→재개→정지→종료 흐름을 구현하고 같은 조작이 반복돼도 PAUSE/END가 중복되지 않게 한다. 종료 확인 취소 시 기존 상태를 유지한다.
4. B는 준비 세션과 실제 측정 세션을 구분한다. FREE는 오프라인 로컬 시작과 종료 후 같은 clientSessionId로 서버 생성·업로드가 가능해야 한다.
5. ENDED는 더 이상 표본을 추가하지 않는 불변 입력 경계다. 수집 콜백과 END를 같은 순서 처리기로 직렬화한다. 늦은 콜백의 제외·경계 규칙을 테스트한다.

## 3. 2일차 — 시간·거리와 원본 저장

1. 경과 총 소요시간은 정지를 포함하고 달린시간은 정지를 제외한다. 단조 증가 시계와 UTC 시각을 구분한다.
2. 정상 인접 GPS만 거리 계산에 사용한다. PAUSE·GAP 경계 전후를 직선으로 연결하지 않는다. 위치 튐은 품질 상태로 처리하고 원본과 정제 결과를 구분한다.
3. 정지 중 이동 표본을 보존할지와 플래그 형식을 계약에 기록하되 거리에는 넣지 않는다. 재개 첫 표본은 이전 정지 위치와 연결하지 않는다.
4. 평균 페이스는 정책의 세션 총 소요시간 기준으로 계산한다. 거리 0·센서 미지원은 계산 불가로 표시하고 0 또는 무한대 페이스로 보여주지 않는다.
5. B는 같은 원본에서 시간·거리 요약을 재계산한다. 표시용 단순 경로를 판정 원본으로 사용하지 않는다.

통제 샘플 free_pause의 총 120초·정지 20초·달린시간 100초를 확인한다. 실제 GPS 거리 정확도 목표는 1주차에 정한 기준을 사용한다.

## 4. 3일차 — 종료 저장과 업로드 연결

1. A는 END·마지막 예상 순번·세션 종료 상태·전송 대기 표시를 기기 트랜잭션으로 저장한다. 네트워크 요청보다 먼저 내구성 저장을 끝낸다.
2. Repository/SyncWorker가 같은 ID로 세션 생성·종료 업로드를 수행한다. 실행 중 측정 원본의 주기 업로드는 넣지 않는다.
3. B는 인증·소유권·필드/시간 유효성·END·순번 완결성을 검사한다. 입력 저장 완료와 최종 등록 완료 응답을 분리한다.
4. 같은 순번·같은 내용은 기존 저장을 반환한다. 같은 순번·다른 내용, 다른 소유자의 세션은 거부한다.
5. 누락 입력은 NEEDS_DATA 등 합의 상태로 돌려주고 누락 범위를 알려준다. 전체 입력이 갖춰지기 전 완주·랭킹·최종 판정 이벤트를 발행하지 않는다.
6. 판정이 오래 걸리면 내구성 작업 상태를 저장하고 status 조회로 이어간다. registeredAt은 최초 완결·검증 결과 등록 때 설정하고 재시도에 바꾸지 않는다.

## 5. 4일차 — 결과 화면과 재조회 연결

1. 업로드 실패·판정 중 상태는 기기 거리·시간·페이스와 “동기화 대기/판정 대기”를 보여준다. 자유 러닝에 코스 완주·대결 결과를 꾸며 넣지 않는다.
2. 서버 등록이 끝나면 원격 요약으로 갱신하고 기기값/서버값의 출처를 구분한다.
3. GET records를 커서로 조회하고 GET records/{id}로 같은 결과를 연다. 빈 목록·로딩·오류는 별도 표시한다.
4. 앱 재실행 후 결과와 목록을 다시 조회한다. 목록 응답에 전체 GPS를 싣지 않고 상세 경로와 요약을 구분한다.
5. JWT의 sub를 소유권 기준으로 사용한다. request memberId만 바꿔 다른 사용자의 기록을 읽거나 쓰는 요청은 거부한다.

## 6. 5일차 — 실제 한 건으로 연결 검증

두 사람이 실제 주행 → 정지 중 이동 → 재개 → 종료 → 업로드 → 결과 → 앱 재실행·기록 재조회 순서로 시연한다.

| 검사 | 확인할 증거 |
| --- | --- |
| 시간/정지 | START·PAUSE·RESUME·END, 총/달린시간 |
| 거리 | 정지 이동이 제외된 정상 구간과 품질 상태 |
| 저장 | 기기/서버 세션 ID·순번·표본 수·마지막 순번 |
| 멱등 | 동일 종료 자료 재전송 전후 레코드 수·registeredAt |
| 누락 | 표본 하나 제거하면 최종 등록 보류, 보완 후 정상 등록 |
| 권한 | 다른 사용자 조회·업로드 거부 |
| 화면 | 기기 대기 → 서버 결과 → 재조회 상태 |

DB 제약·멱등·완결성은 실제 개발용 테스트 DB로 검증한다. [검증 기록](검증-기록-템플릿.md)에 값과 테스트 결과를 남긴다.

## 7. 완료 기준과 실패 대응

- [ ] 실제 주행 1건의 전체 흐름이 연결된다.
- [ ] 수동 정지 포함 총 시간·정지 제외 시간·거리 귀속이 앱/서버에서 일치한다.
- [ ] END 이후 입력 변경이 차단되고 종료 자료가 기기에 먼저 남는다.
- [ ] 동일 자료 재업로드로 서버 기록·등록 시각이 바뀌지 않는다.
- [ ] 누락·충돌·소유권 오류를 성공으로 취급하지 않는다.
- [ ] 결과·기록 목록을 재실행 후 다시 조회할 수 있다.
- [ ] 자동 검증·실기기 시연을 다른 한 명이 확인했다.

값이 어긋나면 화면 반올림보다 원본 순번·시간 단위·정지 경계를 먼저 비교한다. 업로드가 실패하면 기록을 삭제하지 말고 대기 상태를 유지한다. 단계가 통과하면 3주차의 반복 실패·복구 검증으로 넘어간다.
