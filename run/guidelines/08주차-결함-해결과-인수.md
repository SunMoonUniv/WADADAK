# 8주차 — 결함 해결과 인수

[전체 안내](README.md) · 이전: [7주차](07주차-통합과-실기기-검증.md)

**목표:** 여유 기간을 남은 결함·실제 연동 지연 대응에 사용하고, 시작부터 결과 재조회까지 검증된 범위를 근거로 개발 완료를 판단한다.

## 1. 진입 조건과 첫날 작업

7주차 검증 기록·미통과/미실행 항목·기기별 문제·모듈 제공 지연을 모은다. 모두 통과했다면 이 주를 새 기능 추가에 쓰지 않고 최종 인수 자료를 정리한다.

1. 각 문제에 재현 빌드·시나리오·예상/실제 값·영향·담당·수정/재검증 시점을 적는다.
2. 다음 우선순위는 이번 개발의 작업 순서 제안으로 사용한다.
3. 해결에 필요한 입력 자료와 실패 지점부터 확보한다. 재현되지 않는 오류는 근거 없이 완료 처리하지 않는다.

| 우선 | 문제 | 처리 |
| --- | --- | --- |
| 1 | 기록 유실·다른 계정 자료 접근/전송·잘못된 최종 완주 | 후속 완료 선언 전에 수정·재검증 |
| 2 | 중복/역전 집계·고스트 시간/승패 오류·활성 수 누적 | 실제 DB·관련 모듈 재현 후 수정 |
| 3 | 지원 플랫폼 백그라운드·복구·권한·오디오·배터리 기준 실패 | 해당 기기 조건에서 수정·재검증 |
| 4 | 표시·정렬·레이아웃·문구 | 핵심 기능 영향에 맞춰 수정 |

미확정 정책/모듈 제공 지연은 버그와 구분한다. 결정을 대신 만들어 제품 동작을 확정하지 말고 담당·결정 시점·영향을 기록한다.

## 2. 2~3일차 — 작은 수정과 회귀 검증

1. A/B는 각자 맡은 실패를 입력·기기 저장·전송·판정·이벤트·표시 단계로 나눈다.
2. 실패 입력을 재현 테스트로 고정하고 최소 수정한다. 정책 변경·추가 기능을 섞지 않는다.
3. 알고리즘·스키마·이벤트 변경은 버전을 반영하고 담당 관리자 리뷰를 받는다. 이미 머지한 Flyway 파일을 수정하지 않는다.
4. 기존 결과 정정·재판정·집계 정리가 필요한 수정이면 영향 기록을 만들고 타 모듈 담당과 합의한 처리만 진행한다.
5. 원래 실패 사례와 직접 관련된 회귀 시나리오를 실행한다. 새 실패나 범위 변화가 없다면 무관한 테스트를 반복 확장하지 않는다.
6. 기기 오류는 같은 모델/OS/권한, 이벤트 오류는 같은 순서/중복, 판정 오류는 같은 원본·버전으로 수정 전후를 비교한다.

## 3. 4일차 — 완료 후보 빌드의 최종 시연

수정이 반영된 앱·서버 빌드를 고정하고 다음을 실제 인증·실제 제공 모듈로 시연한다.

| 흐름 | 시연 절차 | 마지막 확인 |
| --- | --- | --- |
| 자유 | 오프라인 시작 → 정지/재개 → 종료 → 재실행/재전송 | 기록 1건·같은 등록 시각·결과 재조회 |
| 코스 | 준비 → 실제 시작 → 정상 진행/이탈 → 구간 종료 → 자유 추가 → 세션 종료 | 서버 완주/미완주·리뷰 자격·코스값 고정 |
| 고스트 | 내/공개 후보 → 다운로드 → 정지 포함 재생 → 도전 마감 → 세션 종료 | 승패/동점/무효·스냅샷 보존 |
| 연동 | 등록/삭제·중복/지연 이벤트 처리 | 랭킹/통계/리뷰 자격·작성 리뷰 보존 |
| 복구·관측 | 화면 잠금·권한/연결 변화·서버 재시작 | 저장 범위·GAP·대기 상태·작업 재개 |

최종 시연은 7주차 전체 인수 행렬을 대체하지 않는다. 수정 때문에 무효가 된 기존 증거는 갱신하고, 유효한 통과 기록은 그대로 연결한다.

## 4. 5일차 — 인수 자료 만들기

[검증 기록 템플릿](검증-기록-템플릿.md)으로 다음을 정리한다.

- 코드 저장소의 PR·머지 커밋, 앱/서버/정책/알고리즘/명세 버전.
- 실제 연동 모듈·스텁 상태, 지원 기기/OS·권한·복구 범위.
- 인수 시나리오별 최종 상태·자동 검증 결과·실기기 증거.
- 측정된 거리 오차·배터리·저장/업로드/판정 지연과 합의 기준.
- 로컬/서버 재시작·업로드 재시도·판정 대기·이벤트 소비 실패 확인 방법.
- 마이그레이션 적용 순서·환경 설정 이름·문서 위치. 실제 토큰/비밀번호는 넣지 않는다.
- 정책 결정 기록, 고스트/원본/삭제 식별자 보관 범위, 남은 제한·후속 작업.
- 한 사람이 나머지 개발자의 자료를 받아 같은 시나리오를 재현한 결과.

배포·스토어 제출은 별도 팀 일정으로 정한다. 이 가이드의 완료 기준은 개발·검증·인수 자료의 준비다.

## 5. 전체 완료 판정

- [ ] 1~7주차 필수 항목에 검증 증거가 있고 최종 빌드에도 유효하다.
- [ ] 양 플랫폼의 실제 자유·코스·고스트 시작부터 종료·복구·재조회가 통과했다.
- [ ] 원본 유실·중복 등록·소유권 오류·잘못된 완주/승패·집계 역전이 남지 않았다.
- [ ] 실제 인증·CourseApi·RankingApi·review·MY 연동을 스텁과 구분해 확인했다.
- [ ] 정책 변경 합의 및 구현 계약이 반영됐고 모순되는 동작이 없다.
- [ ] 개발 계획의 인수 행렬에 실패·미실행인 필수 항목이 없다.
- [ ] 데이터·이벤트 복구 절차와 지원/미지원 조건을 다른 개발자가 재현할 수 있다.
- [ ] 팀 리뷰·CI·모듈 경계·DB/판정 자동 검증 결과가 있다.

필수 항목이 남으면 “부분 완료”로 기록하고 담당·다음 행동·재검증일을 정한다. 8주가 지났다는 이유로 완료로 바꾸지 않는다. 모든 기준을 통과했을 때 최종 완료 기록을 남긴다.
