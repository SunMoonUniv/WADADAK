작성일: 2026-10-08 · 대상: 달리기 풀스택 개발자 2명 · 일정: 7주 개발 + 1주 여유

**각 주는 “진입 조건 확인 → 계약·데이터 준비 → 작은 구현 → 연결 → 검증 → 완료 증거 기록” 순서로 진행한다.** 다음 문서는 일정표를 실제 작업 절차로 풀어 쓴 가이드다. 체크 항목은 아직 수행하지 않았으며, 완료 증거가 있을 때만 체크한다.

## 2. 시작 전에 확인할 규칙

### 저장소와 역할

- 문서는 이 저장소의 run 폴더에서 관리한다. 상위 README의 읽기 전용 규칙에 따라 이 체크아웃의 FrontEnd·BackEnd에는 구현을 쓰지 않는다.
- 코드는 별도 작업용 WADADAK-FrontEnd·WADADAK-BackEnd 저장소에서 기능 브랜치로 개발한다. 아래 경로는 그 작업용 저장소 기준이다.
- A는 측정·기기 저장·백그라운드·러닝 UI, B는 서버 저장·판정·결과 UI의 주 책임자다. 둘 다 맡은 작업을 API부터 화면까지 연결하며 다른 한 명이 리뷰한다.
- 공통 코드·공개 인터페이스·이벤트·마이그레이션은 개발 정책 v3에 정해진 관리자 리뷰를 받는다.
- 클래스명·추가 상태명·요청 필드명은 구현 제안이다. 계약에서 확정한 이름을 앱·서버·테스트에 동일하게 사용한다.

### 정책 상태

이 가이드는 최신 아키텍처의 **측정 중 기기 저장, 종료 후 원본 업로드**를 작업 가정으로 사용한다. 코스 시작·구간 종료 신호는 예외다. 정책 문서 제4부 4.2의 앱 도착 안내·자유 전환·완주 음성·통신 90초 규칙 변경은 아직 미합의로 남아 있다.

1주차에 합의 상태를 기록하고, 5주차의 관련 동작을 연결하기 전에 확인한다. 합의 전에는 해당 변경을 확정 기능으로 체크하지 않는다. 자유 러닝·입력 저장·순수 경로 판정은 진행한다. 기존 확정 정책을 유지하면 러닝 중 전송·서버 판정 조회·통신 타이머를 설계하고 4주차 이후 일정을 다시 산정한다.

## 3. 매일 작업하는 방법

1. 오늘 구현할 동작 하나와 통과시킬 시나리오를 정한다. 예: “END를 기기에 저장한 뒤 네트워크가 끊겨도 재전송 대상이 남는다.”
2. 입력·출력·상태 전이와 실패 응답을 먼저 확인한다. 모호한 계약을 화면 코드에서 임의로 정하지 않는다.
3. 화면과 무관한 로직을 먼저 구현하고 자동 검증한다. 이어 최소 화면/API에 연결한다.
4. 실제 변경에 필요한 테스트와 주간 연결 시나리오를 수행한다.
5. 두 사람이 같은 세션 ID·순번·시간을 기준으로 기기 DB, 서버 응답, 결과 화면을 비교한다.
6. 검증 기록·PR에 실제 결과를 붙인다. 실패가 있으면 다음 날 첫 작업으로 재현 원인부터 해결한다.

월요일은 진입 조건·계약·샘플, 화~목요일은 작은 구현과 연결, 금요일은 주간 시연·교차 리뷰·완료 판정으로 배분한다. 날짜보다 의존 순서와 검증 결과를 우선한다.

## 4. 공통 검증 명령

아래 명령은 개발자가 작업용 저장소에서 실행한다. 이 문서를 만들면서 실행한 결과는 아니다. SDK·키·DB·프로필 설정을 갖춘 후 사용한다.

Flutter 앱의 app 디렉터리:

```powershell
flutter pub get
flutter analyze
flutter test
flutter devices
```

실기기 실행은 flutter devices에서 확인한 ID로 한다. 에뮬레이터 검증과 실기기 주행 검증을 구분한다. [Flutter CLI 공식 문서](https://docs.flutter.dev/reference/flutter-cli)

백엔드 저장소 루트의 Windows PowerShell:

```powershell
.\gradlew.bat test
.\gradlew.bat bootRun
```

bootRun은 로컬 프로필·DB 설정을 확인한 후 실행하며 서버가 계속 떠 있는 별도 터미널을 사용한다. Mac/Linux는 같은 프로젝트의 ./gradlew를 사용한다. 테스트 결과는 앱 test 결과와 서버 build/reports/tests/test를 검증 기록에 연결한다.

테스트 DB는 개발·운영 자료와 분리한다. 코스 공간 판정·멱등 저장은 실제 PostgreSQL/PostGIS 또는 해당 Testcontainers 환경으로 검증한다. DB를 흉내 낸 mock 테스트만으로 저장·공간 판정 완료를 선언하지 않는다.

## 5. 공유 검증 데이터 관리

양 코드 저장소에 같은 버전의 비식별 합성 샘플을 둔다. 서버 테스트 리소스와 앱 test/fixtures에서 읽을 수 있게 하고, 파일 이름·버전·예상 결과를 기록한다. 원본 좌표를 일반 로그나 공개 PR에 첨부하지 않는다.

| 샘플 | 준비 주차 | 반드시 표현할 것 |
| --- | --- | --- |
| free_pause | 1~2 | 총 120초, 정지 [40초, 60초), 달린시간 100초. 정지 중 이동 미포함 |
| missing_and_conflict | 2~3 | 순번 하나 누락, 같은 순번 재전송, 다른 내용 충돌, 동일 END 재전송 |
| gap_and_recovery | 3 | GPS 공백·프로세스 종료·시계 구간 변경. 미수집 이동 추정 안 함 |
| straight/out_back/loop/cross/shortcut/parallel | 4 | 기준 경로 구간 ID·실제 입력·예상 인정 범위. 모호한 경우 판단 보류 |
| completion_boundary | 5 | 정책 단위 입력 4750m/4749m, 출발·도착 증거 유무. 별도 GPS 통합 자료 |
| ghost_pause_and_finish | 6 | 상대 정지 구간, 러너 정지, 상대 도착 전후 마감, 같은 정수 초 |
| delete_and_delayed_event | 7 | 삭제→등록 역전, 중복 이벤트, 늦은 공개 변경, 등록 기간 경계 |

정책 단위 테스트에 직접 넣은 “인정 거리”와 GPS부터 계산하는 통합 테스트를 구분한다. 같은 계산 코드를 기대값 계산에도 사용하지 않고, 검토된 구간 범위·시간·정책 예시로 기대 결과를 정한다.

## 6. 매주 남길 증거와 통과 규칙

[검증 기록 템플릿](검증-기록-템플릿.md)을 주차별로 복사해 사용한다. 최소한 앱·서버 커밋, 기기/OS, 스텁 여부, 샘플 버전, 재현 순서, 예상/실제 값, 테스트 결과와 남은 오류를 기록한다.

- **완료:** 그 주의 필수 체크 항목과 자동/실기기 검증이 모두 통과하고 다른 한 명이 증거를 확인했다.
- **부분 완료:** 한 플랫폼·스텁·합성 데이터만 통과했다. 실제로 통과한 범위를 적고 주차 전체 완료로 세지 않는다.
- **미완료:** 필수 기능이나 검증이 실패하거나 미실행이다. 원인·다음 행동·담당·재검증 시점을 정한다.

1주차 기반, 3주차 자유 러닝 내구성, 5주차 코스 판정, 7주차 실제 통합이 주요 통과 지점이다. 통과하지 못하면 후속 의존 기능의 연결을 늦춘다. 독립적인 테스트 자료·명세·UI 작업은 이어갈 수 있다.

모든 구현 PR은 모듈 경계·스텁 보호·이벤트 멱등·마이그레이션 규칙을 지키고 CI와 팀 리뷰를 통과한다. ApplicationModules.verify()와 run 단독 기동 검증을 포함한다. [Spring Modulith 검증 문서](https://docs.spring.io/spring-modulith/reference/verification.html)

전체 완료는 주차별 체크 수의 합계가 아니라 **실제 기기 → 기기 저장 → 서버 판정 → 실제 관련 모듈 → 결과 재조회** 흐름과 실패·복구 시나리오의 통과로 판정한다.
