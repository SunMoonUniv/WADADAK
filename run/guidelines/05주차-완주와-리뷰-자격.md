# 5주차 — 완주와 리뷰 자격

[전체 안내](README.md) · 이전: [4주차](04주차-코스-대응과-이탈.md) · 다음: [6주차](06주차-고스트-대결.md)

**목표:** 서버가 종료 원본으로 완주·미완주·리뷰 자격을 판정하고, 앱의 코스 구간 종료/자유 전환과 개인 기록을 연결한다.

## 1. 진입 조건과 정책 확인

4주차 구간 대응·인정 범위 검증이 통과해야 한다. [전체 안내](README.md)의 정책 제4부 4.2 합의 상태를 먼저 확인한다.

앱 도착 안내·구간 종료·완주 음성·통신 90초 규칙이 미합의라면 해당 변경 동작은 연결 완료로 체크하지 않는다. 서버의 순수 완주/리뷰 판정과 결과 API는 계속 개발한다. 아래 앱 흐름은 종료 후 업로드 방식이 합의된 경우의 절차다.

complete/incomplete·courseClosureSeq·코스 시간·리뷰 자격·reason의 응답과 RunSessionEndedEvent 계약을 course/ranking/review 담당에게 확인한다.

## 2. 1일차 — 서버의 순수 정책 구현

1. B는 출발 GPS 확인, 도착 GPS·기준 경로 끝 도달 확인, 인정 거리 ≥ 코스 거리 × 0.95를 모두 검사한다.
2. 완주 거리에는 총 주행 거리·반복 주행·자유 전환 후 거리를 넣지 않는다. 95% 완주라도 실제 진행도를 100%로 바꾸지 않는다.
3. 출발/끝 반경·경로 대응 오차·품질은 버전 설정을 사용한다. 테스트 수치와 확정 95% 조건을 구분한다.
4. 리뷰 자격은 종료·저장·검증 후 한 세션의 인정 거리 ≥ 1000m AND 진행도 ≥ 20%로 판정한다. 미완주와 리뷰 불가는 같은 상태가 아니다.
5. 정책 단위 테스트는 정확히 4750m/4749m 등 통제 입력으로 작성하고, GPS→판정 통합 테스트를 별도로 둔다. 표시 반올림으로 경계 결과를 바꾸지 않는다.

## 3. 2일차 — 최초 완료 시점과 마감 경계

1. 서버는 courseClosureSeq 이전의 순서 있는 입력에서 최초 완주 조건 충족 시점을 찾는다. 조건이 마감 전 충족됐다면 그 시점으로 코스 값을 고정한다.
2. 앱이 늦게 구간을 종료해도 최초 완료 이후 원본은 세션 기록에만 포함한다. 마감 전에 조건을 충족하지 못했다면 이후 자유 러닝으로 완주를 보완하지 않는다.
3. 코스 총 소요시간/달린시간, 세션 총 소요시간/달린시간을 분리한다. 정지는 총 소요시간에 포함한다.
4. 표본 누락이면 판정을 보류한다. 품질 모호함은 계약된 품질 사유로 남기고 자료가 없는데 미완주/승패를 확정 발행하지 않는다.
5. 같은 완결 원본을 다시 처리해도 완료 시각·registeredAt·결과 버전이 임의로 바뀌지 않는지 확인한다.

## 4. 3일차 — 앱의 구간 종료와 결과

1. A는 앱 도착 감지 시 원본에 구간 종료 경계·사유를 저장하고 같은 세션의 FREE로 전환한다. 앱은 랭킹에 쓸 완주 여부를 확정하지 않는다.
2. 확정 이탈 상태 30초 지속·사용자 종료의 경계를 저장한다. 정지 시 타이머 중단, GPS 불량 시 보류/누적 초기화, 복귀 시 지속 상태 해제를 검증한다.
3. 안내 반복/확인 버튼과 자동 전환 타이머를 분리한다. “다시 표시하지 않음”으로 자동 전환·기록 판정을 끄지 않는다.
4. 합의된 완주 음성 시점에 기기 계산 시간·페이스를 안내한다. OFF/정지 상태·대기 안내 취소·중복 처리 규칙을 적용한다. 승패 음성은 추가하지 않는다.
5. 세션은 계속 수집하다 사용자가 종료하면 한 번 업로드한다. 판정 전에는 대기, 판정 후에는 D1/D1-1과 리뷰 가능 여부를 서버값으로 갱신한다.
6. 앱 도착 안내와 서버 미완주가 다르면 서버 결과를 따른다. 원본·알고리즘 버전을 남겨 허용 오차/경계를 점검한다.

## 5. 4일차 — 활성 수와 결과 이벤트

1. course-end 신호는 멱등으로 활성에서 제외한다. 정지 중에도 활성에는 포함하되 구간 종료·포기·세션 종료·업로드로 끝난 도전은 제외한다.
2. 종료 신호가 없으면 기록 업로드 시 제외하고, 둘 다 없는 방치 세션은 합의한 시간과 DB 기반 스케줄로 제외한다. 예시 3시간을 확정값으로 사용하지 않는다.
3. B는 판정 결과 등록과 RunSessionEndedEvent 저장을 같은 트랜잭션으로 묶는다. 이벤트는 수신자가 원본을 다시 조회하지 않아도 되는 결과·식별자·버전을 포함한다.
4. course가 완주 수·평균·연장, ranking이 코스/누적 거리, review가 자격을 소비하는 계약을 확인한다. run이 다른 모듈 테이블을 직접 고치지 않는다.
5. 코스 비공개/삭제 상태는 신규 집계 소비 시 확인하고 개인 기록은 보존한다. 유지 기간 연장은 등록 시각·수신 시 코스 상태 조건을 따른다.
6. 실제 소비 모듈이 준비됐다면 연결한다. 아직 스텁이면 발행·멱등 계약 결과와 미연동 항목을 분리해 7주차에 남긴다.

## 6. 5일차 — 경계 사례를 시연

| 입력 | 기대 결과 |
| --- | --- |
| 5km, 출발/도착·끝 확인, 인정 4750m | 완주 가능, 진행도 95% |
| 동일 조건 4749m | 거리 미충족 |
| 인정 4800m, 출발/도착 증거 없음 | 거리만으로 완주 안 됨 |
| 1km 코스 인정 950m | 완주 가능, 리뷰 불가 |
| 5km 코스 인정 1000m, 미완주 | 진행도 20%, 리뷰 가능 |
| 코스 밖/반복 포함 총 6km, 인정 3km | 미완주 |
| 최초 완료 후 자유 러닝 10분 | 코스값 고정, 개인 세션 하나 |
| 이탈 30초 전후·정지·GPS 불량 | 정확한 경계와 타이머 처리 |
| 늦은 종료 신호·업로드·배치 경합 | 활성 수 음수/중복 감소 없음 |
| 시작 후 코스 비공개/삭제 | 개인 결과 보존, 신규 코스 집계 제한 |

서버 판정 단위·실제 DB 통합·앱 실기기 흐름 각각의 증거를 [검증 기록](검증-기록-템플릿.md)에 남긴다.

## 7. 완료 기준과 다음 단계

- [ ] 서버 완주 3조건·리뷰 2조건 및 경계 테스트가 통과했다.
- [ ] 최초 완료 시점·구간 마감·코스/세션 값 고정이 검증됐다.
- [ ] 합의된 앱 전환·타이머·음성·대기/서버 결과 화면이 연결된다.
- [ ] 시작/종료/업로드/방치 제외 경합에도 활성 수가 일관된다.
- [ ] 결과/이벤트 저장·재처리·집계 제한 계약과 연동 상태를 확인했다.
- [ ] 판정 버전·경계 자료·실기기 결과를 다른 한 명이 검토했다.

코스 인정 오류가 있으면 4주차 자료로 되돌려 수정한다. 95%를 완화하거나 GPS 자료를 임의 보완해 통과시키지 않는다. 코스 판정이 안정된 뒤 고스트 승패를 연결한다.
