# 7주차 — 통합과 실기기 검증

[전체 안내](README.md) · 이전: [6주차](06주차-고스트-대결.md) · 다음: [8주차](08주차-결함-해결과-인수.md)

**목표:** 실제 관련 모듈과 연결된 달리기 흐름을 Android·iOS에서 검증하고, 이벤트 재처리·삭제·지연 등록·배터리 문제를 해결한다.

## 1. 진입 조건과 검증 환경

1~6주차의 저장·판정·고스트 통과 기록을 확인한다. 미완료 조건을 그대로 다음 주에 통과로 옮기지 않는다.

| 준비 | 확인할 내용 |
| --- | --- |
| 앱/서버 빌드 | 커밋·빌드 번호·정책/알고리즘·계약 버전 |
| 실제 연동 | 소셜 로그인/JWT·CourseApi·RankingApi·review 소비자·MY 설정 |
| 검증 DB | PostgreSQL/PostGIS·마이그레이션·이벤트 저장소·테스트 데이터 |
| 기기 | Android/iOS 모델·OS·권한·배터리·위치/센서 지원 |
| 계측 | 기기 저장 지연·표본/GAP·업로드 크기/시간·판정 대기·이벤트 실패·활성 수 |

이번 주는 개발 검증용 환경에서 수행한다. 검증 기록에는 스텁/실제 구성을 표시하고 위치·토큰을 일반 로그에 남기지 않는다.

## 2. 1일차 — 스텁을 실제 구현으로 교체

1. B는 common/member/course/ranking/review 담당과 제공 버전·명세를 맞춘다. 준비된 모듈만 app.stub.*를 실제 구현으로 전환한다.
2. 실제 JWT의 사용자와 소유권·갱신·로그아웃·탈퇴 상태를 확인한다. 개발용 인증 우회를 실제 통합 완료로 세지 않는다.
3. A는 실제 CourseApi·공개 고스트·MY 설정·리뷰 진입과 결과/기록 목록을 연결한다. 일부 API 오류는 해당 영역의 상태로 표시한다.
4. B는 ApplicationModules.verify(), run 단독 기동, 공개 DTO 직렬화와 prod 스텁 보호를 확인한다.
5. 최소 자유 1건·코스 1건·고스트 1건을 실제 제공 모듈로 저장하고 결과를 다시 조회한다. 다른 모듈이 느리거나 실패해도 원본 기록 저장이 롤백되지 않아야 한다.

## 3. 2일차 — 이벤트·삭제·공개 상태 경합

1. 결과/이벤트 기록은 같은 트랜잭션으로 커밋되는지 확인한다. 소비 실패 후 서버를 재시작하고 같은 이벤트를 다시 처리한다.
2. processed_event 등록과 집계 변경의 트랜잭션을 각 소비자 담당과 확인한다. 같은 이벤트 2회 수신 시 집계가 한 번만 바뀌어야 한다.
3. 삭제 이벤트가 등록 이벤트보다 먼저 도착하게 재생한다. 지연 등록으로 기록·랭킹·리뷰 자격이 재생성되지 않아야 한다.
4. 오래된 회원 공개/코스 상태 버전이 늦게 도착해도 최신 상태를 덮어쓰지 않는지 확인한다.
5. 시작 후 코스 비공개/삭제는 개인 기록을 보존하고 신규 코스 랭킹·리뷰·통계·연장 반영을 제한한다. 상대 기록 삭제와 진행 고스트 스냅샷은 구분한다.
6. 개인 기록 삭제 후 작성 리뷰·저장된 최고 진행도는 보존한다. 해당 기록의 신규 리뷰 작성 자격과 개인 통계/랭킹은 정책에 맞게 정리한다.
7. 시작/종료 신호·업로드·방치 배치를 겹쳐 활성 수가 음수 또는 이중 감소하지 않는지 확인한다.

[Spring Modulith 이벤트 문서](https://docs.spring.io/spring-modulith/reference/events.html)의 저장소·재처리 기능을 팀 구성에 맞춰 사용한다. 외부 호출 성공 여부를 메모리 플래그로만 추적하지 않는다.

## 4. 3일차 — 시간·집계 기간 경계

1. Clock을 주입한 테스트에서 일요일 측정 완료·월요일 최초 등록·동일 자료 재전송을 재현한다.
2. 코스 및 누적 거리 랭킹은 최초 registeredAt의 기간에 들어가고 재전송으로 기간이 이동하지 않아야 한다.
3. 코스 시간이 같은 정수 초이면 공동순위이며 완료 시각으로 순위를 나누지 않는지 ranking 담당과 확인한다.
4. 만료 전 완주·만료 후 이벤트 수신을 재현한다. 숨김/삭제 코스를 복구하거나 유지 기간을 소급 연장하지 않아야 한다.
5. 실제 측정 완료 시각과 서버 응답 시각을 다르게 만들어 코스 시간에 응답 지연이 포함되지 않는지 확인한다.
6. GPS 등록용 원본 경로와 course 생성 검증을 연결한다. 미전송/미판정 자료를 신뢰된 생성 근거로 쓰지 않는다.

## 5. 4일차 — 장시간 양 플랫폼 주행

1. 1주차와 같은 조건·합의한 기준으로 비교한다. 예를 들어 60~90분 측정은 검증용 제안이며 제품의 최소/최대 러닝 시간 정책이 아니다.
2. 자유·코스·고스트 각각에서 화면 잠금·다른 앱·정지/재개·이어폰·음악·음성 OFF·네트워크 차단을 확인한다.
3. 위치 권한 철회·GPS 약화·프로세스 종료는 별도 실험으로 수행한다. 마지막 저장 범위·미수집 공백·사용자 안내를 기록한다.
4. 배터리 사용량·기기 발열·표본 간격/GAP·거리 오차·저장 지연·업로드 시간·판정 시간을 기록한다.
5. 맵을 숨기거나 결과 화면으로 이동한 뒤 수집/종료 상태가 의도대로 유지되는지 확인한다.
6. 기기별 실패는 모델/OS·권한·설정과 함께 재현하고 지원 범위/수정 여부를 명시한다. 강제 종료 중 계속 수집된다고 표시하지 않는다.

## 6. 5일차 — 인수 시나리오 전체 점검

[완료 기준 추적표](완료-기준-추적표.md)의 T01~T22에 상태·증거를 붙이고, 상세 과정은 검증 기록에 남긴다. 아래 묶음으로 빠짐없이 확인한다.

| 묶음 | 반드시 포함할 검사 |
| --- | --- |
| 저장·복구 | 화면 잠금, 정지 이동, GPS 공백/튐, 오프라인 종료, 강제 종료/재부팅 |
| 입력·권한 | 동일/누락/충돌 입력, 응답 유실, 서버 재시작, 계정 전환/인증 만료 |
| 코스 | 4750/4749m, 출발/도착 누락, 리뷰 950m/1000m, 반복/왕복/지름길/순환 |
| 전환·시간 | 최초 완료 후 자유 러닝, 이탈 30초와 정지/GPS 불량, 응답 지연 |
| 고스트 | 양쪽 정지, 선도착, 도착 전후 미완주 마감, 동초 무승부, 격차 모호함 |

| 관측·운영 | 배터리/거리 기준, 판정 대기, 소비 실패 재처리, 활성 수 정리 |

## 7. 완료 기준과 실패 대응

- [ ] 실제 인증·코스·랭킹·리뷰·MY 연동 상태와 버전을 기록했다.
- [ ] 자유·코스·고스트의 실제 기기→DB→판정→소비 모듈→재조회 흐름이 통과했다.
- [ ] 이벤트 중복/역전·삭제·지연 등록·활성 수 경합이 통과했다.
- [ ] 양 플랫폼의 장시간 측정·오디오·권한·복구 검증 증거가 있다.
- [ ] 개발 계획의 모든 인수 시나리오에 통과/실패/미실행 상태와 증거가 있다.
- [ ] 합의한 성능·배터리·거리 기준과 남은 결함/책임자를 확인했다.

실제 제공 모듈이 없으면 해당 연동은 미실행이다. 합성 데이터 통과를 실기기 통과로 대체하지 않는다. 저장 유실·잘못된 완주·중복 집계·소유권 문제는 먼저 해결하고 8주차에 수정 범위별 재검증을 수행한다.
