# 회원 탈퇴 로컬 러닝 기록 정리 연결 · 2026-11-03

`RunLocalStore.deleteOwner(String owner)`를 추가했다. F4 담당자는 서버 탈퇴 성공 뒤 아래 순서로 연결하면 된다. 이 변경에는 `AuthController.withdraw()` 연결을 포함하지 않는다.

## 삭제 범위와 동작

- `sessions`: 업로드 전·업로드 완료·중단·진행 중 기록, 서버 결과 사본의 GPS 경로, 요약, 고스트 정보와 복구 기준점.
- `inputs`: 해당 회원의 세션에 연결된 GPS 등 원본 입력. `owner` 열이 없어 `sessions`를 조회해 먼저 삭제한다.
- `ghost_start_intents`, `course_start_intents`: 아직 세션을 만들지 않은 시작 요청과 승인 사본.
- `ghost_closures`: 고스트 구간 종료 전송 대기.
- `run_deletions`: 전송 전·완료된 개별 기록 삭제 대기열.
- `run_settings`: 회원별 러닝 설정.

7개 테이블의 삭제는 한 트랜잭션이다. 오류는 호출자에게 전달되고, 앞서 지운 행도 모두 복구된다. 같은 회원을 여러 번 지우거나 없는 회원을 지워도 성공한다. 다른 회원의 행은 바꾸지 않는다. 서버 요청이나 새 삭제 대기열을 만들지 않으며 DB 버전 변경도 필요 없다.

## 탈퇴 쪽 호출 순서

1. 토큰을 지우기 전에 `memberId`와 현재 `RunController`를 확보한다. 탈퇴 처리 중에는 중복 탈퇴, 러닝 시작·설정 변경을 막는다.
2. `run.preparing`이면 시작 요청·카운트다운이 끝난 뒤 탈퇴하도록 한다. 진행 중인 시작 처리와 삭제를 동시에 실행하지 않는다.
3. 서버 탈퇴 API가 성공해야 토큰을 지우고 로컬 정리를 시작한다. 서버 실패 시 로컬 기록은 보존한다.
4. 토큰 삭제를 완료한 뒤 **`await run.accountChanged()`** 한다. 이 메서드는 로그인 회원이 `null`이 된 것을 읽고, 진행 중 또는 일시정지한 기록을 `ACCOUNT_CHANGED` 사유로 마감하고 GPS·센서·음성을 정리하며 메모리의 기록 목록도 비운다.
5. 전환이 끝난 것을 확인한 뒤 **`await run.store.deleteOwner(memberId)`** 한다. 마지막에 로그인 화면으로 전환한다.

`SignedOut` 상태를 듣는 기존 리스너는 `accountChanged()`를 기다리지 않는다. 리스너 실행에만 맡기고 바로 삭제하면 종료 입력 저장과 삭제가 겹칠 수 있으므로 위의 명시적인 `await`가 필요하다.

`run.end()`는 일반 사용자 종료라 일시정지 전에는 종료되지 않고 동기화도 시작한다. 탈퇴 정리에는 위 계정 전환 경로를 사용한다. `shutdown()`은 저장소까지 닫으므로 여기서 사용하지 않는다.

아래는 `AuthController.withdraw()`에 연결할 때의 핵심 예시다. 실제 실패 안내·재시도 UI는 F4에서 처리한다.

```dart
final storage = ref.read(tokenStorageProvider);
final memberId = (await storage.read())?.memberId;
if (memberId == null) throw StateError('로그인 정보를 확인해 주세요.');
final run = ref.read(runControllerProvider);
if (run.preparing) throw StateError('러닝 시작 처리가 끝난 뒤 탈퇴해 주세요.');

await ref.read(memberApiClientProvider).withdraw();
await storage.clear();
try {
  await run.accountChanged();
  // accountChanged()는 오류를 화면 상태로 변환하므로 전환 완료를 확인한다.
  if (run.currentOwner != null || run.recorder.current != null) {
    throw StateError('러닝 중지를 완료하지 못했어요. 기기 정리를 다시 시도해 주세요.');
  }
  await run.store.deleteOwner(memberId);
} finally {
  state = const AsyncData(SignedOut());
}
```

서버 탈퇴 성공 뒤 로컬 정리가 실패해도 로그인 상태로 되돌리거나 탈퇴 API를 다시 호출하지 않는다. `memberId`를 정리 재시도에 사용할 수 있도록 유지하고, 기기 정리가 끝나지 않았다는 안내와 재시도 경로를 제공한다. `deleteOwner()` 오류를 삼키고 정리 성공으로 처리하지 않는다. 앱 종료를 넘어 재시도하려면 회원 ID만 담은 별도의 정리 대기 표시가 필요하며, 이는 F4 연결 범위에서 결정한다.

## 검증 범위

- 실제 SQLite 파일에서 7개 테이블의 회원별 삭제, 다른 회원의 모든 행 보존, 재개방 뒤 삭제 유지, 중복 호출, 특수문자가 든 회원 ID의 정확한 일치.
- 삭제 중 강제 오류를 발생시켜 전체 트랜잭션 복구 확인.
- 늦은 동기화 결과·상태 갱신이 삭제한 세션과 GPS를 되살리지 않음.
- 러닝 실행 중·일시정지 중에 토큰 삭제를 흉내 낸 뒤 `accountChanged()` → `deleteOwner()` 순서 검증. GPS 구독 중지와 메모리 목록 정리, 뒤늦은 GPS 입력 후에도 7개 테이블이 비어 있음을 확인.
- F4 실제 탈퇴 연결과 실기기 탈퇴는 이 변경에 포함되지 않는다.


## 후속 실제 연결 완료 — 2026-11-03

이번 러닝 정책 보완에서 auth의 정리 계약과 앱 조립 지점을 연결했다. 서버 탈퇴가 성공한 뒤 `RunController.purgeWithdrawnOwner`가 해당 계정의 비동기 시작·생산자·동기화를 정리하고 로컬 삭제를 수행한다. 기존 `deleteOwner` API와 위 검증은 보존하며 같은 행 삭제 구현을 재사용한다. 일반 로그아웃은 삭제하지 않는다.

SQLite v6의 `withdrawn_run_owners`는 늦은 쓰기 차단과 정리 재시도 표시를 겸한다. 삭제 트랜잭션 전에 식별자를 저장하고, 삭제 중 오류가 나면 기록 행 삭제는 전부 롤백하되 이 표시를 보존한다. 다음 저장소 열기 때 해당 계정만 다시 정리한다. 서버 탈퇴 성공 후 로컬 오류 때문에 서버 탈퇴 API를 다시 호출하거나 로그인 상태로 되돌리지 않는다. 체중 캐시도 계정별로 삭제한다. 상세는 [러닝 정책 보완·칼로리 구현](<러닝 정책 보완·칼로리 구현 - 2026-11-03.md>)을 따른다.
