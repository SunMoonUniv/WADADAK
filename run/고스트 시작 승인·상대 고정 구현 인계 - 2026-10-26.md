# 고스트 시작 승인·상대 고정 구현 인계 · 2026-10-26

브랜치: `feature/F09-ghost-start` · 기반 HEAD: `6c14fb8`(코스러닝 C6·C11·C12 포함).
아래는 로컬 구현/검증 완료 시점의 기록이다. 이후 커밋·push·PR 상태는 Git과 해당 PR에서 확인한다. 기존 미추적 문서 11개를 보존했다.

PR 준비 시 최신 main `6c79b19`(PR #123, F7 GPS 공백 검사)까지 포함됨을 확인했다. main의 정책문서를 유지하고 run 담당 표에 내 고스트 시작 항목 한 줄을 추가했다.

## 구현 결과

내 고스트 후보·선택 준비 다음 단계로, 준비된 코스 세션과 본인 확정 완주 1건을 실제 시작에 연결하는 서버 기반을 추가했다.

- POST `/api/v1/runs/sessions/{id}/ghost/start`: 현재 코스와 내 원본 재생 적합성을 재검증하고 승인·상대·최소 비교 시간/버전·상세 파생 재생 자료를 저장한다.
- GET 같은 경로: 원본/현재 코스를 다시 읽지 않고 저장된 시작 승인과 재생 자료를 재확인한다. 새 repository로 읽어도 동일하며 메모리 캐시에 기대지 않는다.
- 동일 요청/동시 요청은 최초 승인 하나를 반환한다. 상대/시각/코스/버전을 바꾸면 충돌이다. 별도 course/start 없이 기존 CourseRunService.start와 이벤트를 같은 트랜잭션에서 실행한다.
- 소유권·삭제·탈퇴를 기존 회원→세션 잠금으로 직렬화한다. 승인 후 원본 삭제/코스 비활성은 고정 자료를 지우지 않는다. 대결 본인 삭제/탈퇴는 승인·상세를 함께 지우고 재시작을 막는다.
- 외부 CourseApi는 쓰기 트랜잭션 밖에서 호출한다. 경로·거리·비음수 버전을 비교한다. 코스 조회와 run 커밋 사이의 삭제 경계는 계약에 명시했다.
- 상대 GPS 원본 전체·회원 프로필은 복사하지 않는다. 요약과 파생 상세를 별도 테이블에 저장하고 최종 승패 후 30일 정리는 후속으로 연결한다.

요청/응답·에러·정밀도·동시성의 정확한 의미는 [시작 승인 계약](<고스트 시작 승인 계약 v1 - 2026-10-26.md>)에 있다. 준비된 선택 자료와 실제 시작 승인을 구분한다.

## 변경 파일과 공동 리뷰

신규 서버: `GhostStartController`, `GhostStartService`(외부 조회 오케스트레이션), `GhostStartStore`(트랜잭션), `GhostStartRepository`(run JDBC 저장), `GhostStartTest`.

공유 파일:

- `RunContracts`: GhostStart/GhostStartApproval DTO. courseVersion은 0을 허용하되 필수 값 누락은 거부한다. startedAt은 마이크로초까지 보존하며 재시도에서 바꾸지 않는다.
- `RunErrorCode`: RUN-004(본인 상대 재생 부적합). 공개 에러 영역이므로 run 담당 공동 리뷰 대상이다.
- `RunService`/`CourseRunService`: 업로드 전에는 sessions 행이 없어도 기존 course_attempts 소유자를 확인한 뒤 삭제하도록 보강했다. 타인 대결을 ID만으로 삭제할 수 없게 하며 기존 업로드/판정 규칙은 바꾸지 않는다.
- `V20261026_2000__run_ghost_starts.sql`: run 스키마 전용, 기존 행 변경 없음. 승인→코스 시도/상세→승인 FK는 run 내부 CASCADE만 사용한다. 마이그레이션 담당 리뷰 대상이다.
- `DB 구조.md`, `개발 정책 v3.md`, `FrontEnd/README.md`: 테이블/연동/후속 범위 반영.

타 모듈 공개 인터페이스·이벤트 양식·스텁·app.stub 플래그·공통 core·앱 제품 코드를 변경하지 않았다. 실제 코스 시작 신호/집계는 기존 이벤트를 재사용한다. 담당자 메시지 발송이나 리뷰 승인 완료로 표시하지 않는다.

## 다음 연결

1. 앱에 세션/선택/시작 요청과 승인 자료를 내구성 있게 저장한다. 동일 ID/startedAt을 보존하고 응답 유실/계정 전환/로컬 START 저장 실패를 다룬다. GET 404만으로 진행 중인 POST까지 취소됐다고 해석하지 않는다.
2. 동일 단조 시계 근거·60초 재개를 붙인다. 복구가 새 코스 시작/도전 수를 만들지 않게 한다.
3. 서버 승패·최종 확정 시각·상세 30일 만료를 구현한다. 현재 승인 응답을 승패나 실시간 주행 상태로 사용하지 않는다.
4. 코스러닝 화면에 선택→출발→고스트 시작 승인→지도 재생/격차를 연결한다. 기존 측정기/지도/시계를 복제하지 않는다.

기존 코스의 미업로드 시도 도전 수 삭제/만료 동작과 새로운 완전 원자적 cross-module 코스 삭제 차단은 이번 단계에서 새로 정의하지 않았다. 공개 상대·최종 승패·기기 복구와 함께 담당 경계를 지켜 후속 리뷰한다.
