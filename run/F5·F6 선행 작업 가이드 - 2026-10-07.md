# F5·F6 선행 작업 가이드

작성일: 2026-10-07 · 대상: run 담당 김효성·문석용 · 상태: 작업 제안

## 1. 목적과 문서 기준

F0·F1 전체 구현이 끝나기 전에 run 담당이 시작할 수 있는 작업, 다른 담당에게 먼저 필요한 계약, F5·F6의 완료 기준을 정리한다.

이 문서는 작업 순서 제안이며 기존 기능 정책을 변경하지 않는다. 개발정책 v3은 구현 방법의 기준이고, 기능 동작은 정책 문서의 확정 정책을 따른다. 정책 문서 제4부 4.2의 변경 제안은 합의 전까지 확정 동작으로 취급하지 않는다.

## 2. 결론: F5부터 착수하고 F6는 계약·스텁으로 준비한다

개발정책의 핵심 흐름은 F0 → F1 → F5 → F6 → F8이다. 같은 문서 3.2는 실제 구현 전 공개 인터페이스와 스텁을 제공해 다른 모듈 개발이 막히지 않게 하고, 10.3은 계약 PR → 구현 PR 순서를 정한다.

이를 근거로 이 가이드는 핵심 흐름의 통합 순서를 유지하면서 독립 작업은 먼저 착수하도록 제안한다. 문서가 기능별 착수 조건을 모두 정의한 것은 아니므로 최소 골격·계약의 제공 시점은 담당끼리 맞춘다.

| 대상 | 필요한 선행 요소 | 전체 완료를 기다리지 않고 할 일 |
| --- | --- | --- |
| F5 자유 러닝 | 앱 최소 실행 골격·팀 라이브러리 선택, 서버 공통 기반 | 측정·기기 저장·복구, 업로드 계약, run 저장·조회 |
| F6 코스 러닝 | F5 측정 기반, CourseApi 계약·코스 스냅샷 | 고정 코스와 GPS 데이터로 판정 엔진·화면 상태 준비 |
| 실제 코스 연동 | course의 실제 구현 | 스텁으로 검증한 흐름을 실제 CourseApi에 연결 |
| F6 완주 안내·전환·통신 처리 | 정책 문서 제4부 4.2 협의 | 공통 측정·거리 판정은 진행하고 해당 동작의 최종 구현은 합의 후 결정 |

F5는 코스 없이 시작하므로 CourseApi를 호출할 필요가 없다. 서버의 사용자 ID는 JWT의 sub에서 받으며, 사용자 식별만을 위해 MemberApi를 호출하지 않는다.

## 4. 지금 진행할 작업 순서

### 4.1 기록 데이터·상태·시간 계약부터 맞춘다

앱과 서버가 같은 샘플 기록을 사용하도록 run 담당 두 명이 저장·업로드 형식을 먼저 합의한다.

| 항목 | 준비할 내용 |
| --- | --- |
| GPS 표본 | 순번, 측정 시각, 좌표, 정확도, 수집 가능한 센서 값 |
| 조작 이벤트 | 시작·일시정지·재개·종료·GPS 공백. F6 코스 구간 경계는 정책 합의에 맞춰 추가 |
| 시간 | 일시정지 포함 총 소요시간, 제외한 달린시간. 코스 시간과 세션 시간 구분 |
| 거리 | 총 주행 거리, 코스 인정 거리, 코스상 위치를 별도 값으로 관리 |
| 기록·동기화 | 클라이언트 기록 ID, 업로드 대기 상태, 재시도·중복·충돌 처리 |
| 상태 | 측정 생명주기, 러닝 모드, 저장·동기화 상태, 서버 검증 상태를 구분 |

순번·필드명·단위 등 구체 형식은 계약에서 확정한다. API 좌표는 공통 GeoPoint의 lat·lng 객체 규칙을 따른다. 서버 날짜는 Instant·TIMESTAMPTZ, 거리 기본 단위는 m로 맞춘다.

반드시 반영할 기능 규칙:

- 시작 버튼을 1초간 누르면 3초 카운트다운을 진행하고, 카운트다운 종료부터 측정한다. 취소는 기록·도전 횟수에 포함하지 않는다.
- MVP는 수동 일시정지다. 정지 중 이동을 거리로 추가하거나 재개 시 정지 전후 위치를 주행으로 연결하지 않는다.
- 총 소요시간은 종료 확인까지 계속 흐르고, 달린시간은 일시정지 중 멈춘다.
- 개인 평균 페이스는 세션 총 소요시간 ÷ 총 주행 거리다.
- 자동 랩은 총 주행 거리 1km마다 생성하고 마지막 1km 미만 구간도 실제 거리로 보존한다.
- 센서 미지원·측정 불가 값은 —로 표시한다. 누락값을 0으로 평균에 넣지 않는다.

완료 기준: 시작·정지·재개·종료가 포함된 샘플 기록 1건과 그 기록의 기대 거리·시간·랩 결과를 앱·서버 담당이 함께 확인한다.

### 4.2 F5 화면을 하나의 흐름으로 연결한다

첫 화면 범위:

**C5 자유 러닝 준비 → H4 카운트다운 → C4 자유 러닝 → 일시정지·종료 확인 → D1-2 자유 러닝 결과**

1. 가짜 GPS 입력으로 조작·상태·화면 이동을 연결한다.
2. 기기 저장을 붙인다.
3. 실제 GPS와 백그라운드 측정을 붙인다.
4. 서버 업로드·결과 조회를 연결한다.

색·간격·글꼴은 기존 디자인 시스템 토큰과 위젯을 사용한다. 화면 이동·지도 숨김과 측정 엔진의 수명을 분리한다.

결과 화면은 기기 계산값과 서버 확정값을 구분한다. 업로드 실패 시 거리·시간·페이스는 표시하고, 서버 판정 항목은 판정 대기, 기록은 기기에 저장됨·동기화 대기로 표시한다.

고스트 준비·선택·대결 결과 화면은 F9 작업으로 구분한다. D4의 코스 등록은 F7 담당과 연결할 후속 작업이다.

### 4.3 실제 기기의 측정·저장·복구를 일찍 검증한다

| 시나리오 | 기대 결과 |
| --- | --- |
| iOS·삼성 Android에서 화면 끄고 30분 측정 | GPS 수집과 기기 저장 유지 |
| 다른 앱 사용·러닝 화면 이동 | 측정·저장 계속 |
| 일시정지 중 이동 후 재개 | 정지 중 이동 거리 제외, 총 소요시간 포함 |
| 인터넷 없이 자유 러닝 시작·종료 | 측정·기기 저장 가능, 업로드 대기 기록 보존 |
| 앱 종료 후 재실행 | 마지막 저장 데이터와 업로드 대기 기록 복구 |
| GPS 끊김 후 복구 | 확인되지 않은 공백을 임의로 주행 거리로 채우지 않음 |

강제 종료·재부팅 후 자동 재개 범위와 공백의 시간 귀속은 후속 협의 사항이다. 우선 내구성 있는 저장·보존·복구를 검증한다. GPS 수집 주기와 허용 정확도는 실험값을 측정해 결정하고 정책 확정값처럼 고정하지 않는다.

완료 기준: 실기기 검증 기록에 기기·OS·측정 시간·표본 수·저장 결과·복구 결과·발견한 문제를 남긴다.

### 4.4 F5 서버 저장·조회와 재업로드 처리를 구현한다

기존 백엔드 골격에 run 모듈을 추가한다. 공개 인터페이스·DTO·에러 코드는 모듈 루트, 구현은 internal, DB는 run 스키마에 둔다.

- 세션 종료 후 전체 기록 업로드·저장·결과 조회 계약을 작성한다.
- 같은 클라이언트 기록 ID·같은 내용 재업로드는 기존 결과를 반환한다.
- 같은 ID에 다른 내용·다른 소유자가 오면 충돌로 거부한다.
- 누락 입력이 있는 기록은 필요한 데이터 확보 전 최종 결과를 확정하지 않는다.
- registeredAt은 최초 등록 시 설정하고 재업로드로 바꾸지 않는다.
- 기록 저장과 RunSessionEndedEvent 기록은 같은 트랜잭션으로 처리한다.
- 다른 모듈 Entity·Repository·테이블에 직접 접근하지 않는다.
- 서버 소유권 검사는 JWT 사용자 기준으로 한다.

개발정책 v3·아키텍처가 제시한 종료 후 전체 업로드를 기준으로 F5를 준비한다. 이 구조와 F6의 러닝 중 서버 판정·전환 요구 사이의 조정은 7장의 협의 항목으로 남긴다.

완료 기준: 자유 러닝 1건을 저장·조회하고 같은 기록 재업로드 후 기록 수·이벤트·등록 시각이 중복 변경되지 않는지 검증한다.

### 4.5 F6는 고정 코스 데이터로 판정 엔진부터 준비한다

course 실제 구현 전에는 합의한 CourseApi와 CourseApiStub으로 고정 경로를 받아 개발한다. 엔진의 입력을 코스 스냅샷·측정 기록으로 두고 외부 조회와 판정 계산을 분리한다.

| 테스트 | 기대 결과 |
| --- | --- |
| 기준 경로 정상 주행 | 실제 확인된 코스 구간 인정 |
| 지름길 후 후반 구간 복귀 | 건너뛴 구간 미인정 |
| 같은 코스 구간 반복 | 코스 인정 거리는 같은 구간 한 번만 합산 |
| 왕복·순환·교차 경로 | 좌표와 주행 이력으로 대응 구간 구분, 모호하면 보류 |
| 일시정지 중 이동·GPS 공백 | 확인되지 않은 구간을 자동 연결하지 않음 |
| 5km 코스 인정 거리 4.75km / 4.749km | 출발·도착·경로 끝 조건도 충족하면 전자는 거리 기준 충족, 후자는 미충족 |
| 1km 코스 인정 거리 950m | 다른 조건 충족 시 완주 가능, 리뷰 자격 없음 |
| 5km 코스 인정 거리 1km·진행도 20% | 종료·저장·검증 후 리뷰 거리·진행도 조건 충족 |

완주는 출발 GPS·도착 GPS·기준 경로 끝 도달·코스 인정 거리 95% 이상을 함께 확인한다. 표시용 반올림 값, 총 주행 거리, 지도 km 표지로 대체하지 않는다.

리뷰 자격은 종료·저장·검증 후 한 세션의 코스 인정 거리 1km 이상이면서 진행도 20% 이상일 때 판정한다. 완주 여부와 독립이다.

C6·H1·코스 러닝 C4·이탈 안내·D1/D1-1 화면은 고정 데이터로 상태를 준비한다. 이탈 관련 30m·20m·10초 등의 값은 기존 테스트 수치다. 확정 이탈 30초 자동 전환과 안내 반복 30초는 별개 규칙으로 관리한다.

| F0 | 기존 서버 실행·로컬 인증 방식, 공통 응답·에러·좌표 타입 | run API·계약 PR |
| F0 | Flyway·Modulith·아웃박스·단독 기동 테스트 사용 방식 | run 저장·이벤트·검증 |
| F1 | CourseApi.getRouteForRun(), CourseRouteSnapshot, CourseApiStub | F6 고정 코스 개발 |
| MY | AudioGuide가 읽을 음성 설정 형식·변경 적용 시점 | 거리·시간 안내, 이탈 음성 |

이미 있는 공통 코드는 재사용하고 누락 타입·설정은 담당과 맞춘다. F1의 화면·코스 등록 전체 완료보다 경로 조회 계약과 스텁 제공을 먼저 요청한다.

run은 RunApi·ReviewEligibility·RunErrorCode·RunApiStub과 발행 이벤트 계약을 준비한다. 공개 영역과 이벤트는 모듈 관리자와 합의하고 개발정책 10.3의 계약 PR 절차를 따른다.

## 7. F6 최종 동작 전에 협의할 항목

정책 문서 제4부 4.2는 합의 전까지 본문 확정 정책이 바뀌지 않는다고 명시한다. 아래 개발정책의 방향을 이미 승인된 기능 동작으로 구현하지 않는다.

| 항목 | 본문 확정 정책 | 개발 변경 제안 |
| --- | --- | --- |
| 완주 안내·자유 전환 | 서버 완주 확정 후 같은 세션 자유 러닝 전환·고스트 마감 | 앱 경로 끝 감지 후 안내·전환, 세션 종료 업로드 후 서버 최종 판정 |
| 완주 음성 | 서버 완주 확정 결과 수신 후 재생 | 앱 경로 끝 감지 시 기기 계산값으로 재생 |
| 통신 단절 | 90초 초과 시 코스·고스트 마감 후 자유 전환 | 러닝 중 통신하지 않으므로 규칙 삭제 |
| 현재 러너 수 | 일시정지 포함, 완주·종료·전환 후 제외 | 시작·구간 종료 신호·업로드·시간 경과로 제외 |

종료 후 업로드만으로는 본문의 러닝 중 서버 완주 확정·전환 요구를 그대로 충족할 수 없다. F6 통신·완주 응답 흐름은 변경 제안의 합의 여부를 확인한 뒤 확정한다. 임의로 새 통신 방식이나 타임아웃 값을 확정하지 않는다.

함께 정할 구현 항목:

- 시작·끝 허용 반경, 경로 대응 오차, GPS 품질 기준.
- 강제 종료 복구·재개 범위와 방치 세션 제외 시간.
- 코스 총 소요시간의 정수 초 변환 규칙.
- 음성 안내 간격·우선순위·설정 변경 적용 시점.

측정·기기 저장·F5 업로드·거리 판정 테스트는 위 협의와 병행할 수 있다.
