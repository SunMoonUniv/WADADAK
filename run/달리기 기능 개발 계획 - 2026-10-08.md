# 달리기 기능 개발 계획 — 재작성

작성일: 2026-10-08 · 상태: 개발 계획 제안 · 담당: 풀스택 개발자 2명

**첫 완료 목표는 실제 기기의 자유 러닝 한 건을 측정하고, 앱 종료·통신 실패에도 보존하며, 서버에 중복 없이 등록한 뒤 다시 조회하는 것이다.** 이 흐름을 먼저 완성하고 코스 판정과 고스트 대결을 추가한다. 일정은 **7주 개발 + 1주 여유**를 기준으로 제안하며, 단계 완료 기준을 통과해야 다음 기능을 연결한다.

주차별 실제 작업 순서와 검증 절차는 [달리기 개발 실행 가이드](guidelines/README.md)를 따른다.

## 1. 기준 문서와 현재 상태

기능 규칙은 [정책 문서](../정책%20문서.md), 기술·협업 규칙은 [개발 정책 v3](../개발%20정책%20v3.md), 달리기 상세 구조는 [달리기 개발 아키텍처](달리기%20개발%20아키텍처%20-%202026-10-06.md)를 따른다. 이 문서는 [2026-10-06 계획](달리기%20기능%20개발%20계획%20-%202026-10-06.md)을 대체하는 실행 계획이다.

2026-10-08 로컬 체크아웃에서 확인한 상태:

| 영역 | 확인 내용 | 일정에 반영할 작업 |
| --- | --- | --- |
| 백엔드 | Spring Boot 4.1.1, Java 21, Spring Modulith 2.1.1, JPA·Security·PostgreSQL 의존성. 소스는 애플리케이션과 기본 테스트 뼈대 | 공통 기반·run 모듈·마이그레이션·API·인증 연결부터 필요 |
| 프론트 | Flutter 디자인 시스템 패키지와 카탈로그. 실제 앱 디렉터리는 없음 | 앱 생성·라우팅·상태 관리·위치·SQLite·HTTP 연결 필요 |

| 지도·인증 | 개발 정책에 네이버 지도, 카카오·Apple·Google 소셜 로그인 및 자체 JWT가 정해져 있음 | SDK 선택을 다시 논의하는 대신 키·권한·개발 환경·공통 담당 연결 확인 |
| 저장·판정 | 아키텍처 문서는 있으나 run 구현 소스·DB 마이그레이션은 확인되지 않음 | 처음부터 구현하고 검증해야 함 |

위 버전은 저장소 설정값이며, 서버 기동·모바일 빌드·DB 연결이 통과했다는 뜻은 아니다. 상위 저장소 README에 따라 이번 작업에서는 **계획 문서만 작성**한다. 실제 프론트·백엔드 구현은 각 서브모듈의 담당 저장소에서 진행한다.

### 기존 계획에서 바꾼 점

- 실제 존재하는 정책 문서를 기준으로 사용한다. 이전 계획의 존재하지 않는 정책 경로·ERD 경로에 의존하지 않는다.
- Spring Boot·PostGIS·네이버 지도·JWT를 미정으로 취급하지 않는다.
- 앱 뼈대와 서버 공통 기반이 아직 준비되지 않은 상황을 1주차에 반영한다.
- 러닝 중 측정 원본 업로드를 종료 후 업로드 구조로 정렬한다.
- GPS 표본과 조작 이벤트는 같은 세션 순번을 사용한다.
- 자유 러닝의 복구·재전송을 끝낸 후 코스·고스트를 개발한다.
- Android·iOS 검증은 첫 주부터 시작하고, 코스 판정에는 두 주를 확보한다.

## 2. 정책 합의가 필요한 경계

**작업 가정:** 최신 개발 정책 v3와 아키텍처의 “측정 중 기기 저장, 세션 종료 후 업로드” 방식을 기준으로 일정을 산정한다.

다만 정책 문서 제4부 4.2는 아래 내용을 아직 **정책 변경 제안**으로 표시하고, 합의 전에는 기존 확정 정책이 유지된다고 명시한다. 이 계획을 작성하는 행위로 정책이 확정되지는 않는다.

| 항목 | 계획 기준인 개발 제안 | 구현 전 합의할 내용 |
| --- | --- | --- |
| 완주 안내·자유 전환 | 앱의 코스 끝 도착 감지로 구간 종료·안내, 서버는 세션 종료 후 완주 판정 | RUN-08의 서버 확정 후 전환과 다른 부분 |
| 완주 음성 | 도착 감지 때 기기 계산 시간·페이스 안내 | AUD-06의 재생 주체·시점 |
| 통신 단절 | 측정 원본의 주기 전송·생존 신호 없음. 시작·구간 종료 신호만 사용 | ERR-04의 통신 단절 90초 자동 전환 삭제 여부 |
| 현재 러너 수 | 시작·구간 종료·기록 업로드·방치 제외 작업으로 관리 | 기존 통신 타임아웃 방식과의 변경 및 방치 기준 |

**결정 시한은 1주차 말, 앱의 코스 구간 종료·음성·통신 동작 연결 전이다.** 합의 결과는 정책 문서와 아키텍처 양쪽에 기록한다. 합의 전에도 자유 러닝, 원본 저장, 재전송, 서버의 순수 경로 판정 개발은 진행할 수 있다.

기존 확정 정책을 유지하기로 하면 코스·고스트의 러닝 중 업로드·서버 판정 조회·통신 타이머가 추가된다. 전송 주기·배터리·오프라인 동작을 다시 검증하고 4주차 이후 일정을 재산정한다. 두 전송 방식을 동시에 구현하는 비용은 이 일정에 포함하지 않는다.

## 3. 담당 범위와 분담

달리기 담당은 개발 정책 v3의 김효성·문석용 2명이다. 아래 A/B의 개인별 배정은 팀에서 정한다.

| 역할 | 주 책임 | 함께 검토할 작업 |
| --- | --- | --- |
| A — 기기 측정 중심 | 위치·센서, 상태·시간·거리, 백그라운드, SQLite, 복구, 러닝 화면·지도·음성 | 입력 규격, 재전송, 코스 안내와 서버 결과 차이 |
| B — 저장·판정 중심 | run DB·API, 멱등 저장, 판정 작업 복구, 코스·리뷰·고스트 판정, 기록·결과 화면 | 실제 기기 업로드, 고스트 재생 계약, 이벤트·삭제 경합 |

둘 다 풀스택으로 작업하되 측정 엔진과 서버 판정 엔진의 주 책임자는 유지한다. PR은 다른 한 명이 리뷰하고, 공유 데이터 규격을 먼저 정한 뒤 같은 샘플로 앱·서버를 구현한다.

### 포함 범위

- 자유·코스·고스트 준비, 3초 카운트다운, 측정·정지·재개·종료.
- 위치·거리·총 소요시간·달린시간·페이스·자동 랩, 케이던스·고도 자료의 수집 가능 범위와 분석 표시.
- 지도, GPS 품질 상태, 경로 이탈 안내, 거리·시간 음성.
- 기기 기록·종료 후 업로드·재전송·앱 종료 후 복구.
- 서버 코스 인정 거리·완주·리뷰 자격·고스트 승패/무효 판정.
- 결과·상세 분석·내 기록 조회/삭제, 코스 등록용 전체 실제 주행 경로 제공.
- 내 최고·최근·과거 완주 고스트와 공개 랭킹 고스트 선택.
- 시작·구간 종료 신호, 현재 러너 수, 타 모듈에 필요한 이벤트.

코스 생성·검색·등록 검증은 course, 랭킹 집계·화면은 ranking, 리뷰 CRUD는 review, 로그인·토큰 발급은 member, 앱 공통 기반은 공통 담당이 맡는다. AI 추천 고스트·자동 일시정지 등 미확정 설정은 기본 일정에 새로 넣지 않는다.

## 4. 다른 파트와 먼저 맞출 계약

| 상대 | 제공받는 계약 | 달리기가 제공하는 계약 | 필요한 시점 |
| --- | --- | --- | --- |
| 앱 공통·member | 앱 뼈대·라우팅, JWT 사용자·갱신, 설정, 계정 전환 | 기록·복구 진입점, 동기화 상태 | 1주차 |
| common | ApiResult·에러·커서·Clock, 지역·좌표 타입, Flyway, 이벤트 저장소, 모듈 검증 | run 모듈 설정·요구사항 | 1주차 |
| course | CourseApi: 공개 상태·순서 있는 기준 경로·거리·스냅샷 버전 | 시작·등록 결과·활성 수 이벤트, 실제 주행 경로 전달 계약 | 계약 1주차, 실제 연결 4주차 |
| ranking | RankingApi: 공개 후보·실제 순위·공개 허용 | 완주 결과·코스 정수 초 시간·registeredAt·전체 정상 주행 거리 | 계약 1주차, 실제 연결 6주차 |
| review | 리뷰 진입·삭제 자격 처리 | 종료·검증된 리뷰 자격·인정 거리·진행도 | 계약 1주차, 실제 연결 5주차 |
| MY | 음성 설정·기록 목록·계정 전환 흐름 | 기록 요약·상세·삭제·동기화 대기 | 2~3주차 |

공개 인터페이스는 조회 전용 DTO와 스텁을 먼저 제공한다. 모듈 루트 공개 타입만 참조하고 다른 모듈 내부 구현·스키마 JOIN·FK는 사용하지 않는다. 변경 전달은 event 모듈의 이벤트를 사용한다.

공통 기반이 늦으면 개발용 스텁·샘플로 단독 개발을 이어간다. **스텁 동작은 실제 연동 완료로 세지 않으며**, 실제 인증·코스·랭킹·리뷰 연동은 마지막 완료 기준에 포함한다.

## 5. 구현할 기본 흐름과 데이터

### 5.1 기기와 서버의 역할

자유 러닝은 오프라인 시작을 허용한다. 코스·고스트는 온라인에서 시작 스냅샷과 시작 신호를 확보해야 시작한다.

```text
준비·권한·스냅샷
→ 카운트다운·시작
→ GPS/조작 이벤트를 기기에 저장
→ 정지·재개, 지표·지도·고스트·이탈 안내
→ 코스 구간 종료 후 필요하면 같은 세션 자유 러닝
→ 세션 종료를 기기에 저장
→ 전체 기록 업로드
→ 서버의 입력 완결성·코스·리뷰·고스트 판정
→ 결과 등록 + 이벤트 저장
→ 결과 화면·MY·다른 모듈 반영
```

측정 원본은 세션 종료 후 전송한다. 코스 시작·구간 종료 신호는 활성 수 관리용 예외이며 완주 증거가 아니다. 데이터가 크면 종료 후 조각 업로드를 하되 전체 순번이 도착하기 전에는 판정·집계를 확정하지 않는다.

결과가 아직 없으면 기기 거리·시간·페이스와 “판정 대기”를 표시한다. 등록·판정 완료 후 서버 결과로 갱신한다. 측정 종료, 전송 완료, 서버 판정 완료, 다른 모듈 반영 완료를 구분한다.

### 5.2 먼저 합의할 데이터 규격

| 항목 | 계약 |
| --- | --- |
| 식별자·소유권 | 클라이언트 세션 UUID, JWT의 memberId. 다른 사용자의 요청으로 덮어쓰지 않음 |
| 입력 순서 | 세션 단일 streamSeq에 GPS와 START/PAUSE/RESUME/MODE_SWITCH/GAP/END를 함께 기록 |
| 멱등성 | 같은 세션·순번·내용은 재사용. 내용·소유권 충돌은 명시적 오류 |
| 완결성 | 마지막 예상 순번·END·업로드 완료 선언을 함께 검증. GPS 공백과 전송 누락을 구분 |
| 시간 | 원본 ms·UTC Instant, 기간 Asia/Seoul. 총 소요시간과 달린시간·코스와 세션을 분리 |
| 거리 | m 단위. 총 실제 주행 거리·코스 인정 거리·코스상 위치를 분리 |
| 좌표·센서 | 공개 API는 lat/lng 객체. 미지원·미수집 센서는 NULL이며 0으로 만들지 않음 |
| 버전·경계 | 정책/알고리즘/스냅샷 버전, courseClosureSeq·사유, 결과 버전 |
| 등록 시각 | 서버의 최초 완결·검증 결과 등록 시각을 registeredAt으로 정하는 제안. 재시도로 변경하지 않음 |
| 정수 초 | 원본 ms 보존. 랭킹·고스트 동일 변환 규칙을 1주차에 확정 |
| 시계·복구 | 실행 중 단조 증가 시계, 날짜 시각 병행. 재부팅·복구 구간은 별도 경계로 저장 |

앱의 “구간 종료”와 서버의 “완주 확정”은 별도 상태다. 종료·동기화·판정 상태를 한 enum에 합치지 않는다. 정지 중 이동, GPS 공백, 복구 공백을 직선 주행으로 연결하지 않는다.

### 5.3 DB와 API의 구현 순서

DB는 PostgreSQL + PostGIS의 run 스키마를 사용하고 모듈별 Flyway 마이그레이션을 만든다.

1. 자유 러닝: sessions, stream_records, gps_points, session_events, processing_checkpoints.
2. 지표·기록: laps, 개인 기록 조회 인덱스, 삭제 후 늦은 업로드로 기록이 재생성되지 않는 삭제 식별자 보존 계약.
3. 코스: course_attempts, recognized_intervals, 시작 스냅샷·활성 수 관리.
4. 고스트·연동: ghost_matches, 회원 공개 복사본, processed_event.

API는 아키텍처의 경로를 기준으로 명세를 먼저 작성한다. 아래는 계약 초안이며 접두사는 모두 /api/v1/runs다.

| 순서 | 경로 | 목적 |
| --- | --- | --- |
| 1 | PUT /sessions/{clientSessionId} | 멱등 세션 준비·생성 |
| 1 | POST /sessions/{id}/record | 종료 원본·이벤트 업로드, 필요 시 종료 후 조각 전송 |
| 1 | GET /sessions/{id}/status | 저장·누락·판정 상태 및 결과 |
| 1 | GET /records, GET /records/{id} | 내 기록 커서 조회·상세 결과 |
| 2 | DELETE /records/{id} | 기록 삭제·삭제 이벤트 |
| 3 | POST /sessions/{id}/course-start, /course-end | 코스 시작·구간 종료 신호 |
| 3 | GET /courses/{courseId}/active-count | 현재 코스 러너 수 |
| 4 | GET /ghosts, GET /ghosts/{recordId}/playback | 고스트 후보·재생 자료 |
| 4 | GET /records/{id}/course-source | 코스 등록에 전달할 전체 실제 주행 경로 |

시작·종료 신호도 재시도에 안전해야 한다. 시작 요청의 응답이 사라졌을 때 같은 요청으로 확인하고, 시작 횟수·활성 수를 다시 증가시키지 않는다. 시작 실패·불확실 상태를 새 세션 생성으로 우회하지 않는다.

서버는 입력 저장과 판정을 분리하고 작업 상태를 DB에 남긴다. 같은 세션의 판정은 직렬화하며 서버 재시작 후 이어 처리한다. 결과 등록·이벤트 저장은 한 트랜잭션으로 처리하고 소비 실패는 재처리한다.

| 계정 전환·인증 만료 | 다른 계정 토큰으로 이전 계정 자료를 보내지 않음. 인증 실패에도 측정·저장 지속 |

자동 검증은 상태·시간·정지 경계, 좌표 시계열 판정, 실제 DB의 멱등·완결성·삭제, 이벤트 재처리를 대상으로 한다. 개발 정책 v3의 ApplicationModules.verify(), run 단독 @ApplicationModuleTest, 이벤트 발행/중복 수신·오래된 버전 검증을 포함한다. 권한·백그라운드·배터리·음성은 실제 기기로 확인한다.

운영 확인 항목은 기기 저장 지연·누락, 업로드 크기·재시도, 판정 대기/처리 시간, 미처리 이벤트·활성 세션, 배터리 소모·거리 오차다. 숫자 목표는 1주차 실험 후 합의하고 7주차 같은 조건으로 비교한다.

| 케이던스·고도 수집·음성 출력 | 1주차 기기 지원, 3~6주차 표시/동작 | 미지원 센서 상태와 음악/이어폰/화면 꺼짐을 검증 |
| 실제 공통·코스·랭킹·리뷰 제공 지연 | 매주 담당 간 확인 | 스텁 개발은 지속, 실제 인수 일정은 제공일 기준 재산정 |

3주차까지 자유 러닝 내구성 기준이 통과하지 못하면 코스·고스트 연결을 뒤로 옮긴다. 5주차까지 왕복·교차·지름길 판정이 안정되지 않으면 고스트 공개 후보·경쟁 결과 연결을 늦춘다. 8주차까지 실제 연동이 준비되지 않으면 스텁 상태를 명시하고 완료로 선언하지 않는다.

## 11. 기술 검증 참고

- Android는 사용자가 화면에서 시작하는 location foreground service, 위치·서비스 권한과 알림을 검증한다. 백그라운드에서 새 서비스를 시작하는 조건은 별도로 확인한다. [Android 공식 서비스 유형 문서](https://developer.android.com/develop/background-work/services/fgs/service-types#location)
- iOS는 Core Location의 백그라운드 업데이트를 구성하고 실기기로 확인한다. [Apple 공식 위치 문서](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background)
- 기기·원격 데이터 접근은 Repository로 묶고 측정 저장과 동기화 상태를 구분한다. [Flutter 오프라인 우선 설계](https://docs.flutter.dev/app-architecture/design-patterns/offline-first)
- 이벤트 저장소·재처리 정책은 팀의 Spring Modulith 구성에 맞춰 확인한다. [Spring Modulith 이벤트 문서](https://docs.spring.io/spring-modulith/reference/events.html)
