# 달리기 기능 개발 계획

작성일: 2026-10-06 · 담당: 풀스택 개발자 2명 · 앱: Flutter · DB: PostgreSQL

## 1. 목표와 전제

첫 목표는 실제 기기에서 시작 → 측정 → 일시정지 → 재개 → 종료 → 기기 저장 → 서버 저장 → 결과 조회가 연결되는 자유 러닝이다. 이후 코스 판정과 고스트 대결을 추가한다.

이 계획의 정책 기준은 `policy-decisions-2026-10-06/홈·코스·달리기 통합 설계서 - 일관성 정리본.md`다. 기존 `outputs/running-app-erd`는 참고 초안이며 최신 정책과 맞춘 뒤 사용한다. 이 문서는 개발 제안으로, 기존 확정 정책을 변경하지 않는다.

백엔드 프레임워크, 지도 SDK, 인증 방식은 아직 확인되지 않았다. 팀의 기존 선택을 사용하며, 이 세 가지의 선택과 개발 환경 확인을 첫날에 끝낸다. 일정은 인증·코스 조회·기본 지도 연동을 다른 파트가 제공하고 두 명이 전담한다는 가정의 작업량 추정이다. 첫 주 기술 검증 후 다시 산정한다.

## 2. 구조와 책임

Flutter 앱 → 인증된 백엔드 API → PostgreSQL 구조를 사용한다. 앱은 PostgreSQL에 직접 연결하지 않는다.

- Flutter: 위치 권한, 위치 수집, 러닝 조작, 실시간 거리·시간 표시, 지도, 음성, 기기 저장, 재전송, 결과 화면.
- 달리기 서버: 세션·표본·정지 구간 저장, 코스 인정 거리, 완주 판정, 리뷰 자격, 고스트 결과, 관련 영역에 전달할 판정 결과.
- 기기 DB: 진행 중 기록과 미전송 데이터를 내구성 있게 저장. 메모리나 설정 저장소만으로 위치 기록을 보관하지 않는다.
- PostgreSQL: 원본 측정과 서버 판정 결과 보존. 공간 연산이 필요하면 PostGIS 도입을 검증한다. 확장만으로 교차·왕복 구간 판정이 해결되지는 않는다.

Flutter는 화면, 러닝 상태 관리, 저장·동기화 담당 Repository, 위치·API·기기 DB 접근 서비스를 분리한다. 러닝 측정을 화면의 생명주기에 종속시키지 않는다. 상태 관리 라이브러리는 팀의 기존 방식을 따른다.

## 3. 2명 역할 분담

| 담당 | 주 책임 | 함께 연결할 작업 |
|---|---|---|
| A | Flutter 측정 엔진, 권한·백그라운드, 시간·거리, 기기 저장·복구, 러닝 화면 | 세션·표본 업로드와 서버 응답 반영 |
| B | 달리기 DB·API, 멱등 저장, 서버 코스 판정, 고스트 판정·재생 데이터, 결과 화면 | 코스·고스트 흐름과 판정 결과 표시 |

두 사람 모두 풀스택으로 작업하되 핵심 측정 로직과 서버 판정 로직에는 각각 한 명의 주 책임자를 둔다. 데이터 규격, 상태 전이, 경계 사례는 함께 검토한다. API 초안을 먼저 합의하고 같은 샘플 데이터로 앱·서버를 구현한다.

## 4. 다른 파트와 첫 주에 합의할 계약

| 상대 파트 | 달리기가 받는 것 | 달리기가 제공하는 것 |
|---|---|---|
| 앱 공통·인증·MY | 로그인 사용자, 인증 방식, 설정, 권한·복구 연결 방식 | 개인 기록 ID, 요약·상세 조회, 동기화 상태 |
| 홈·코스 | 코스 ID, 공개·만료 상태, 이름·기준 경로·거리·방향, 시작 시 스냅샷 | 서버 확정 완주 이벤트, 활성 도전 정보, 코스 등록용 전체 실제 주행 경로 |
| 랭킹 | 공개 고스트 후보와 해당 기록 ID, 기간·순위 정보 | 종료·등록·검증된 코스 결과, 정수 초 코스 총 소요시간, 기록 등록 시각 |
| 리뷰 | 리뷰 작성 흐름의 진입 계약 | 종료·저장 후 검증한 리뷰 자격, 실제 인정 거리·진행도 |

코스 생성·검색·등록, 랭킹 화면·집계, 리뷰 CRUD는 각 담당이 구현한다. 달리기는 판정 근거와 결과를 제공한다. 코스 유지 기간 연장은 코스 담당과 이벤트 소비·중복 방지 책임을 합의한다. 내 최고·최근·과거 완주 기록 선택도 MVP에 포함한다.

## 5. 먼저 정할 상태·데이터 규격

다음은 구현 제안이며 첫 주에 확정한다.

- 세션 생명주기: 준비 / 측정 중 / 일시정지 / 종료.
- 현재 모드: 자유 / 코스 / 고스트. 코스 도전 마감 후 같은 세션에서 자유 모드로 전환할 수 있다.
- 동기화 상태: 기기 저장 / 전송 대기 / 전송 중 / 서버 등록. 판정 처리 상태는 별도로 둔다.
- 세션 종료와 코스 완주는 별개다. 서버가 실제 측정 시각을 기준으로 완주 시점을 정하며 응답 지연을 코스 시간에 더하지 않는다.
- 표본: 세션 ID, 순번, 측정 시각, 경과 시간, 위도·경도, 위치 정확도, 수집 가능한 속도·센서 값. 누락 센서는 NULL.
- 시간: 코스/세션 각각 총 소요시간과 달린시간을 구분한다. 시간 단위와 정수 초 변환은 하나의 규칙으로 맞춘다.
- 거리: 총 주행 거리 / 코스 인정 거리 / 코스상 위치를 구분한다. 기본 단위는 m, 시각은 timestamptz, 화면의 기간 경계는 Asia/Seoul을 사용한다.
- 시작·정지·재개·모드 전환·종료 이벤트와 GPS 공백의 경계를 저장한다. 정지 중 이동이나 확인되지 않은 공백을 직선 주행으로 연결하지 않는다.
- 같은 세션 ID·표본 순번·이벤트 ID의 재전송은 중복 저장·집계를 만들지 않는다. 소유자나 내용이 충돌하면 덮어쓰지 않는다.
- 종료 업로드는 예상 마지막 순번 등 완결성 정보를 포함하도록 검토한다. 필요한 표본이 누락됐는데 최종 결과를 확정하지 않는다.

DB의 첫 범위는 `running_sessions`, `running_points`, `running_pauses`, `course_runs`, `ghost_matches`와 필요한 이벤트·전송 관리 데이터다. 자동 랩은 측정 엔진 안정화 후 추가한다. 전체 앱 ERD를 한 번에 구현하지 않는다.

API는 세션 생성·재전송, 표본 묶음 업로드, 이벤트 업로드, 종료 요청, 판정 상태·결과 조회, 내 기록 조회·삭제, 고스트 재생 데이터 조회를 우선 정의한다. 코스 러닝 중에도 측정 데이터를 전송하고 서버 확정 결과를 받을 경로가 필요하다. 전송 주기·묶음 크기·폴링 또는 실시간 통신 방식은 첫 주 실험 후 결정한다.

5주 개발 + 1주 여유는 확정 납기나 작업 보장이 아니다. 위치 추적 경험, iOS 빌드·실기기 환경, 다른 파트 준비 상태에 따라 조정한다. 1주차에 핵심 추적이 동작하지 않으면 뒤 일정의 UI 작업보다 원인을 먼저 해결한다.

## 7. 정책을 구현할 때 지킬 기준

- 완주는 서버만 판정한다. 앱은 오프라인에서도 자체·잠정 완주를 확정하지 않는다.
- 코스 완주에는 출발·도착 GPS 확인과 경로 끝 도달 확인이 필요하다. 코스 인정 거리 ≥ 코스 전체 거리 × 0.95가 거리 조건이다. 방향·신뢰도·연속성을 검증한다.
- 리뷰 자격은 한 세션의 코스 인정 거리 ≥ 1km이면서 진행도 ≥ 20%일 때 종료·저장 후 판정한다. 완주 여부와 독립이다.
- 코스 총 소요시간에는 수동 일시정지가 포함된다. 랭킹·고스트 비교는 이 시간을 사용한다. 개인 평균 페이스도 세션 총 소요시간을 사용한다.
- 코스 완주 후 코스 값은 고정하고 같은 세션의 자유 러닝 측정은 이어간다.
- 확정 이탈이 30초 지속되면 자유 러닝으로 전환한다. 일시정지·GPS 불량 시 이탈 타이머 처리는 최신 정책을 따른다.
- 통신 단절 90초 초과 시 코스·고스트를 마감하고 자유 러닝으로 전환한다. 타이머 시작·복구·정지 중 처리와 오프라인 시작은 구현 결정 항목으로 합의한다.
- 서버가 전환 전 데이터에서 확인한 완주를 우선하는 원칙을 따른다. 전송 지연과 전환 이벤트 순서의 경합은 앱·서버가 함께 설계·검증한다.
- 고스트는 총 소요시간 축으로 재생하며 러너의 정지 중에도 진행한다. 고스트 선도착만으로 러너의 도전을 마감하지 않는다.
- 코스 랭킹 기간은 기록 등록 시각 기준이다. 같은 정수 초의 코스 시간은 공동순위이며 완주 시각으로 나누지 않는다.
- 시작 후 코스·고스트 원본이 삭제돼도 스냅샷으로 진행·결과를 보존한다. 개인 기록 삭제 시 작성 리뷰와 저장된 최고 진행도는 유지한다.

GPS 수집 주기·허용 정확도·튀는 위치 필터·시작/끝 반경·선투영 오차 등은 실기기 검증값이다. 기존 이탈 안내 테스트 수치를 완주 허용 오차로 재사용하지 않는다.

## 8. 기존 ERD 수정 항목

| 기존 초안 | 최신 정책에 맞출 내용 |
|---|---|
| course_waypoints / waypoint_passes와 순차 통과 완주 | 판정용 웨이포인트 제거. 경로 투영·실제 구간 인정·출발/도착 확인으로 설계 |
| completion_time_s가 정지 제외 시간 | 정지 포함 코스 총 소요시간과 코스 달린시간 분리 |
| active_ms가 고스트 재생 기준 | 총 소요시간 축과 정지 이력을 사용 |
| completed_at을 공동순위 기준에 포함 | 순위는 정수 초 코스 총 소요시간만 사용. 안정 표시 정렬은 별도 |
| 완주 시각 기준 랭킹 기간 | 기록 등록 시각을 명시하고 재전송에도 유지 |
| 리뷰 근거 기록 삭제 시 CASCADE | 리뷰·저장된 최고 진행도를 보존하는 관계와 삭제 처리로 변경 |

이번 계획 작성에서 기존 SQL이나 설계서를 변경하거나 실제 DB에 적용하지 않았다. 변경된 스키마를 별도 검토 후 마이그레이션한다.

## 9. 반드시 확인할 시나리오

1. 실제 주행 중 화면 잠금·다른 앱 사용 → 측정 유지. Android와 iOS 실기기로 각각 검증한다.
2. 정지 중 이동 후 재개 → 이동 거리를 합산하지 않고 총 소요시간은 유지한다.
3. 인터넷 단절 → 기기 저장 지속, 복구 후 동일 기록 1건만 등록한다.
4. 앱 강제 종료 후 재실행 → 마지막 저장 데이터 복구. 강제 종료·재부팅 중 계속 측정된다고 보장하지 않는다.
5. 위치 튐·GPS 공백 → 비정상 거리와 지름길 인정 방지. 대응 구간 불확실 시 판정 보류.
6. 5km 코스에서 출발/도착 확인·인정 4.75km → 서버 완주. 4.749km → 거리 조건 미충족.
7. 1km 코스 인정 0.95km → 다른 조건 충족 시 완주 가능하지만 리뷰 불가.
8. 완주 후 자유 러닝 → 개인 기록은 하나, 코스 시간·거리는 고정.
9. 고스트 정지 구간·러너 정지·고스트 선도착 → 재생과 최종 승패가 정책과 일치.
10. 완주 응답 지연·이탈/통신 전환·재전송 순서 변경 → 서버 판정 우선과 거리 귀속 유지.
11. 코스·상대 기록 삭제 → 시작 스냅샷 유지, 신규 집계 제한 및 결과 안내 적용.
12. 일요일 완주·월요일 등록 → 새 주 귀속. 재시도로 등록 시각과 순위가 중복 변경되지 않는다.

좌표 시계열을 같은 판정 엔진에 반복 재생해 정상·이탈·왕복·교차·공백 결과를 검증한다. 시간·거리·중복 저장·판정 경계에는 자동화 테스트를 두고, 권한·백그라운드·배터리는 실제 기기로 확인한다. 배터리·거리 오차 허용 기준은 첫 주 기준 측정 후 합의한다.

## 10. 바로 시작할 첫 3일

- 1일차: 정책 기준·역할·다른 파트 계약 확인, 기존 ERD 수정 목록, 세션·시간·표본 규격 작성. 백엔드·지도·기기 DB와 Android/iOS 검증 환경 확인.
- 2일차: A는 위치 수집·화면 잠금·기기 저장 실험, B는 세션·표본 저장·조회 API와 개발 DB 준비. 공통 샘플 요청·응답 작성.
- 3일차: 실제로 짧게 달린 기록을 끝까지 저장·조회하고 정지·재전송 사례 확인. 실험 결과로 기술 선택과 주차별 일정 보정.

첫 완료 목표: 실제 기기로 달리기 → 정지/재개 → 종료 → 기기 및 서버 저장 → 결과 조회.
