# run 패키지 정리 (1번 인계)

작성: 2026-10-16 · 2번 문석용 → 1번 김효성 · 브랜치 `feature/F06-course-judging`

자유 러닝(1번)과 코스 판정(2번)이 같은 run 모듈에서 같은 규칙을 따로 갖고 있어서 한 번에 정리했다. **계산·API·JSON·DB는 바뀌지 않는다.** 1번 테스트(`FreeRunCalculatorTest`·`RunFeaturesTest`·`RunResultStatsTest`)와 공통 fixture가 그대로 통과한다.

## 1. 한눈에

| 무엇 | 전 | 후 |
| --- | --- | --- |
| 업로드 DTO `RunContracts` | `run/` (모듈 루트) | `run/internal/` |
| 세션·업로드·처리·삭제 | `run/internal/` | `run/internal/recording/` |
| 자유 러닝 계산 | `run/internal/` | `run/internal/metrics/` |
| GPS 품질 기준 | `FreeRunCalculator.good()` + 숫자 `30`·`12`·`10000` | `run/internal/GpsQuality` |
| 입력 종류 | `START GPS PAUSE RESUME GAP END CADENCE` | `SEGMENT_END` 추가 |
| 판정 입력 | 2번 전용 `judging/RunInput` | 삭제, `RunContracts.Input` 사용 |

```
run/
├── RunErrorCode.java
└── internal/
    ├── RunContracts.java          ← 루트에서 이동 (앱용 REST DTO)
    ├── GpsQuality.java            ← 새로 (public)
    ├── RunWebConfig.java
    ├── recording/                 1번
    │     RunController · RunService · RunProcessingWorker · RunEventHandler
```

테스트도 같은 패키지로 옮겼다: `test/.../run/internal/recording/RunIngestionTest`, `test/.../run/internal/metrics/{FreeRunCalculatorTest, RunFeaturesTest, RunResultStatsTest}`.

## 2. 커밋별 변경과 이유

리뷰는 커밋 순서대로 보면 된다. 1번 커밋은 이동만이라 넘겨도 된다.

### ① `refactor(run): run/internal을 recording·metrics로 나누고 RunContracts를 internal로 (이동만)`
- **이유**
  - `RunContracts`를 다른 모듈이 하나도 쓰지 않는다. 모듈 루트는 다른 모듈용 공개 계약 자리다(개발 정책 3.1). course도 요청 DTO를 `internal`에 둔다.
  - `internal`에 1번 파일은 평평하게, 2번 파일은 `judging/`에 있어 섞여 있었다. course·ranking·member처럼 기능별 하위 패키지로 나눠 담당이 폴더로 보이게 했다.
- **바뀐 것:** `package`·`import` 줄, 그리고 패키지가 갈라져 `recording`이 부르는 것만 `public`
  - `FreeRunCalculator` 클래스, `calculate()`, `Calculation`
  - `RunResultStatsCalculator` 클래스, `VERSION`
- `MotionPace`는 `metrics` 안에서만 쓰여 그대로 package-private이다.

### ② `refactor(run): GPS 품질 기준을 GpsQuality로 모음`
- **이유:** 같은 기준이 네 곳(자유 러닝 3곳 + 코스 판정)에 숫자로 흩어져 있었다. 코스 판정이 자유 러닝 계산기(`FreeRunCalculator.good()`)에 기대는 것도 이름이 맞지 않아, `metrics` 밖 `run/internal`에 따로 뒀다.
- **`GpsQuality`:** `MAX_ACCURACY_M = 30`, `MAX_SPEED_MPS = 12`, `MAX_INTERVAL_MS = 10_000`, `good(Input)`(기존 `FreeRunCalculator.good()` 그대로)
- **바꾼 줄 (식 모양은 그대로, 숫자만 상수로)**

| 파일 | 줄 |
| --- | --- |
| `FreeRunCalculator` | `good(p)` 호출, `dt > 10000 \|\| d/(dt/1000.0) > 12`. `good()` 메서드는 삭제 |
| `MotionPace` | `FreeRunCalculator.good(p)`, `dt > 10000 \|\| distance(...) / (dt / 1000.0) > 12` |
| `RunResultStatsCalculator` | `FreeRunCalculator.good(p)`, 최고 페이스 연결의 `dt > 10000 \|\| ... > 12` |

- **일부러 그대로 둔 10초·12** (용도가 다르다고 봤다. 같은 기준이면 `GpsQuality`로 바꿔도 된다)
  - `MotionPace`: 정지 창 `span > 10000`, 정지 끝 `previous.elapsedMs() + 10000`, 속도 센서 신뢰 `speedMps() <= 12`
  - `RunResultStatsCalculator`: 고도 단절 `dt > 10000`
  - `FreeRunCalculator`: 케이던스 묶음 `durationMs() > 10000`, 시각 신선도 `age <= 10000`

### ③ `feat(run): 입력 종류에 코스 구간 종료 SEGMENT_END 추가`
- **이유:** 정책 공통 7·D-20, 입력 계약 #49. 서버는 이 입력 이전 데이터로만 코스를 판정한다. 없으면 `END`가 경계.
- **`RunContracts.Kind`:** `START, GPS, PAUSE, RESUME, GAP, SEGMENT_END, END, CADENCE`. JSON은 이름으로 저장돼 기존 payload에 영향이 없다.
- **`MotionPace`:** `SEGMENT_END`를 `START`·`CADENCE`처럼 무시한다. 다른 이벤트처럼 정지 창을 닫으면 자유 러닝 거리·이동시간이 바뀐다.
- `FreeRunCalculator`(switch에 case 없음)·`RunResultStatsCalculator`(GPS 아닌 입력 건너뜀)는 손대지 않아도 지나간다.
- **새 테스트** `FreeRunCalculatorTest.segmentEndDoesNotChangeFreeRunResult`: fixture 중간에 넣어도 거리·시간·랩·통계가 같다. `MotionPace` 무시를 빼면 실패하는 것도 확인했다.
- 사유는 기존 `reason` 필드에 담는다. 테스트에서는 `COURSE_ONLY`를 썼다(아래 4번에서 이름 합의).

### ④ `refactor(run): 코스 판정이 업로드 입력 RunContracts.Input과 GpsQuality를 쓴다`
- 2번 코드만 바뀐다. `judging/RunInput` 삭제, 판정이 `RunContracts.Input`을 그대로 받는다. GPS 품질은 `GpsQuality.good()`.

## 3. 앞으로 run에 파일을 둘 때

| 둘 것 | 위치 |
| --- | --- |
| 다른 모듈이 부르는 공개 계약 (계획: `RunApi`·`ReviewEligibility`, review용) | `run/` 루트 |
| 앱 REST DTO | `run/internal/RunContracts` |
| 자유 러닝·코스 판정이 같이 쓰는 기준 | `run/internal/` (`GpsQuality` 옆) |
| 세션·업로드·처리 | `run/internal/recording/` |
| 자유 러닝 지표 | `run/internal/metrics/` |
| 코스 판정 | `run/internal/judging/` (2번) |

- 하위 패키지끼리 부를 때는 Java상 `public`이 필요하다. Modulith는 run 하나로 보므로 다른 모듈 경계는 그대로다(`ModularityTests` 통과).
- run 밖에서 run 패키지를 import하는 곳은 없다(main·test 전체 확인). review·ranking은 `event.run.*` 이벤트만 받는다.

## 4. 1번이 정해 줄 것

### 정리됨 (2026-10-19)

자유 러닝과 코스 판정이 정책 문서 자유 러닝 측정의 "10초 초과 공백·12m/s 초과 위치 튐은 연결하지 않는다" 하나로 맞춰졌다.

| 항목 | 결과 |
| --- | --- |
| 표본 간격 상한 | 1번이 판정에도 10초 상한 추가(`c9e3c71`). 10초 넘게 GPS가 없으면 GAP처럼 기준·보류 가설을 버린다 |
| 속도 검사 GPS 오차 여유 | 2번이 판정에서 제거(`021fa43`). 정책에 없던 여유라 자유 러닝과 같은 12m/s 기준으로. 오차로 걸리면 그 한 구간만 빠지고 다음 표본부터 다시 이어진다 |
| 입력 계약 문서의 간격 15초 | 10초로 수정(`a53e08c`) |
| `SEGMENT_END` 사유 코드 | `ROUTE_END`(경로 끝 도착) / `COURSE_ONLY`(코스만 종료). 정책에 이름이 없어 제안대로 정함, 계약 문서 반영. 1번 fixture `free_barometer_v3`도 `COURSE_ONLY`. 서버는 사유 값을 검사하지 않고 보존만 한다(판정은 사유와 상관없이 구간 경계로만 씀). 틀린 사유 하나로 기록 전체가 실패하지 않게 |
| 앱 `RunKind` | 1번이 `segmentEnd` 추가(`7d3c32b`). Dart 이름은 `segmentEnd`, JSON은 `SEGMENT_END`로 바꿔 서버와 같다 |
| FREE 세션의 `SEGMENT_END` | 거부하지 않고 무시한다. 기록 안의 입력은 판정이 코스 세션에서만 돌아 영향이 없고, 구간 종료 **신호** API(B단계)는 세션 상태를 보고 FREE면 무시한다 |
| `SEGMENT_END` 세션당 최대 1회 | 거부하지 않고 무시한다. 기록은 판정이 첫 `SEGMENT_END`에서 멈추고 경계도 첫 번째로 잡는다. 신호 API(B단계)는 이미 구간 종료된 세션이면 무시한다(재시도도 같은 결과) |
| 위 "그대로 둔 10초·12" | 1번이 값·동작은 그대로 두고 용도별 상수로 정리(정지 창·정지 시간 인정 범위·센서 속도 신뢰 상한·고도 단절·케이던스 묶음·시각 신선도). GPS 표본 연결 간격·속도는 `GpsQuality` 공유 |

남은 항목 없음. B단계 신호 API에서 FREE·중복 무시를 구현할 때 이 표를 따른다.

## 8. 1번 후속 반영 · 2026-10-19 기압 센서 상승 고도

- 이 정리의 recording·metrics·internal/RunContracts 및 GpsQuality 경계를 유지해 구현했다.
- RunContracts.Kind에 BAROMETER, Input에 pressureHpa·pressureAccuracy를 선택 필드로 추가했다. 실제 센서 시각은 기존 sampleEndMs를 사용한다. GPS altitudeM은 보존한다.
- 앱/서버 MotionPace는 BAROMETER를 이동·정지와 무관한 입력으로 무시한다. 앱의 SEGMENT_END 이름 읽기/쓰기 및 무시도 맞췄다. 코스 판정·GPS 품질 수치는 변경하지 않았다.
- RunResultStatsCalculator와 앱 RunResultStats는 RESULT_V3로 기압 우선/구간별 GPS 대체 계산을 한다. 세션·업로드 검증은 recording/RunService에 있다. 테이블·이벤트·공개 모듈 계약은 바꾸지 않는다.
- 센서 없는 기기의 고도 DB 보정과 이 문서 4장의 다른 판정 결정은 이번 범위에서 진행하지 않는다.
- 상세: [기압 센서 상승 고도](기압%20센서%20상승%20고도%20-%202026-10-19.md).
- 2026-10-19 후속 검증: Docker 런타임 소켓 오류를 데이터 초기화 없이 복구했다. 실제 프로젝트의 RunIngestionTest 18개(기압 원본 업로드·재시도·V2 상세 보완·삭제 포함)가 모두 통과했다. 제품 구현 코드는 추가 변경하지 않았다. [복구·DB 검증 기록](<Docker 복구와 DB 통합 검증 - 2026-10-19.md>) 참조.

## 9. 2026-10-20 실시간 고도와 PACE_V3 후속 반영

- 기능 기준은 정책 문서 공통 2, 구현 계약은 개발 정책 v3의 「실시간 누적 고도와 PACE_V3 구현 계약」을 따른다.
- 앱/서버 internal/metrics의 MotionPace는 연속된 원본 GPS의 품질·시간 간격·12m/s 초과 경계를 먼저 적용한다. 보정으로 가운데 점을 제거해도 큰 튐이나 공백 앞뒤를 재연결하지 않는다. 코스 판정 GpsQuality·judging 규칙은 변경하지 않는다.
- 신규 러닝은 PACE_V3, 과거 PACE_V2와 이전 기록은 원래 버전을 유지한다. RESULT_V3 고도는 라이브 잠정 표시로 확장하고 종료 확정 통계·원본과 분리한다. DB·API 필드·이벤트 및 판정 정책 버전 변경은 없다.
- 앱/서버 공통 free_motion_v3.json은 23개 시나리오를 검증한다. 상세: [실시간 고도와 균형형 GPS 보정](<실시간 고도와 균형형 GPS 보정 - 2026-10-20.md>).
