# 운영 PC (감시 · 백업)

상태: 구현 PR · 작성일 2026-11-23 · 기준: main `9b15e8a`(서버 3대)

> **문서 목적**: 네 번째 PC를 서비스가 없는 운영 PC로 쓴다. run PC에 있는 감시(Loki · Prometheus · Grafana)를 옮기고, core DB · run DB를 매일 백업해 보관한다. 저장소에서 바꿀 것, PC에서 할 일, 옮기는 순서를 정한다.
> 서버 배치는 [MSA 분리 준비와 CI·CD](<MSA 분리 준비와 CI·CD - 2026-11-04.md>) 2.3, 감시 설정은 [observability](observability/README.md), 운영 절차는 [README](README.md)를 따른다.

## 1. 결론

- 감시가 서비스와 같은 PC에 있으면 그 PC가 꺼질 때 알림도 멈춘다. 지금은 run PC가 꺼지면 아무도 모른다. 운영 PC로 옮기면 서비스 PC 셋 중 어느 것이 꺼져도 알림이 온다.
- DB 백업이 없다. core DB는 전환 때 뜬 `core-db.tar` 하나뿐이고 run DB는 없다. 매일 두 DB를 `pg_dump`로 떠서 운영 PC에 30일 보관하고, 매주 복원해 본다.
- 그날 백업이 오지 않았거나 복원 검사가 실패하면 운영 PC가 Discord로 알린다. 운영 PC 자체가 꺼지거나 백업 · 복원 검사 · 데이터 대조가 아예 안 돌면 바깥의 healthchecks.io가 알린다(6장).
- 옮기는 동안 서비스는 멈추지 않는다. 알림이 몇 분 비고, 지금까지의 로그 · 지표(7일치, 거의 비어 있다)는 옮기지 않는다(8장).
- 앱 지표(core · run `/actuator/prometheus`)도 운영 PC의 Prometheus가 모은다([observability README](observability/README.md)).

```
인프라 PC Alloy ─┐                                  ┌─ Discord (알림)

core PC  ─ pg_dump 매일 ─ Taildrop ─► 운영 PC 백업 폴더(30일) ─ 안 왔거나 복원 검사 실패 ─► Discord
```

- 운영 PC가 꺼지면 로그 · 알림 · 백업 받기가 멈추고 서비스는 그대로다. 하트비트가 끊겨 healthchecks.io가 알린다(6장 4번). 서비스 PC가 백업을 보내지 못한 날은 운영 PC와 healthchecks.io가 알린다.
- 네 PC는 같은 건물 · 전원 · LAN에 있다. 정전이나 건물 장애에는 소용이 없다. 건물 밖 백업은 7장.

## 3. 그대로 옮기면 깨지는 곳

| # | 깨지는 곳 | 어떻게 깨지나 | 막는 법 |
| --- | --- | --- | --- |
| 1 | 알림이 두 번 간다 | run PC와 운영 PC의 Grafana가 같은 규칙 · 웹훅으로 함께 돈다 | run PC의 Grafana · Prometheus를 내린 뒤 운영 PC Grafana에 알림 설정을 올린다(5.2) |
| 2 | run PC 로그가 끊긴다 | run PC Alloy의 전송 주소가 같은 compose의 `http://loki:3100`으로 박혀 있다(`run/config.alloy`). Loki를 내리면 보낼 곳이 없다 | core와 같이 `LOKI_PUSH_URL` 환경 변수로 받는다(4.2) |
| 3 | Grafana를 운영 PC에서만 본다 | 지금처럼 `127.0.0.1:3000`에 열면 운영 PC 앞에서만 열린다 | 운영 PC Tailscale 주소에 연다. 로그인(admin 비밀번호)은 그대로 필요하다(6장 결정 1) |
| 4 | 백업이 개인정보를 들고 나간다 | 덤프에는 회원 정보가 그대로 있다. 저장소가 공개라 Actions artifact로 올리면 누구나 받는다 | Taildrop으로 운영 PC에만 보낸다. 운영 PC 계정은 팀 관리자만 쓰고 백업 폴더를 공유하지 않는다 |
| 5 | Taildrop 파일이 섞인다 | 받은 파일은 받는 계정의 `Downloads`에 쌓인다. 같은 이름을 다시 보내면 어떻게 되는지는 아직 보지 않았다 | 파일 이름에 PC와 날짜를 넣고, 운영 PC 작업이 매일 백업 폴더로 옮긴다(4.4) |
| 6 | 덤프를 못 읽는다 | 서버(17)보다 낮은 `pg_dump`로 뜨거나, 높은 버전으로 뜬 덤프는 낮은 `pg_restore`가 못 읽는다 | 각 DB 컨테이너 안의 `pg_dump`로 뜨고, 복원도 같은 메이저(17) 이미지로 한다 |
| 7 | 백업이 있는 줄 알았는데 깨져 있다 | 뜨기만 하고 복원해 보지 않으면 모른다 | 매주 운영 PC에서 임시 컨테이너에 복원해 본다(4.4) |
| 8 | SSH 세션에서 `docker`를 못 찾는다 | core PC의 SSH 세션 PATH에 Docker가 없다(2026-11-23) | 스크립트는 `docker.exe` 전체 경로를 쓴다. 작업 스케줄러는 로그인 세션에서 돌린다 |

## 4. 저장소에서 바꿀 것 (구현 PR)

### 4.1 `deploy/observability/ops/` (새 폴더, 운영 PC)

지금 `run/`의 Loki · Grafana · Prometheus 파일을 옮긴다. 내용은 그대로이고 아래만 바꾼다.

- `compose.yaml`: `loki` · `prometheus` · `grafana` 셋. 프로젝트 `wadadak-ops-observability`. 지금 `compose.yaml` · `compose.loki-tailnet.yaml` · `compose.prometheus.yaml`을 하나로 합친다.
  - Loki 3100은 `100.111.111.92:3100`에만 연다(Alloy 셋이 Tailscale로 보낸다).
  - Grafana 3000은 `${GRAFANA_BIND_IP:-100.111.111.92}:3000`.
  - Prometheus는 포트를 열지 않는다(Grafana만 compose 안에서 읽는다). 보관 7일 그대로.
- `.env.example`: `GRAFANA_ADMIN_PASSWORD` · `DISCORD_WEBHOOK_URL`. 비밀 값은 운영 PC `.env`에만 둔다.
- `Verify-DLQ.ps1` · `Verify-Grafana.ps1` · `verify.ps1` · 대시보드 · 알림 규칙 파일은 그대로 옮긴다.

### 4.2 `deploy/observability/run/` (run PC)

- `compose.yaml`: `alloy`(와 `smoke`)만 남긴다. 프로젝트 이름 `wadadak-run-observability`는 그대로 둬 읽기 위치 볼륨을 이어 쓴다.
- `config.alloy`: `loki.write`의 주소를 `sys.env("LOKI_PUSH_URL")`로 바꾼다. compose 기본값 `http://100.111.111.92:3100/loki/api/v1/push`.

### 4.3 `deploy/observability/core/` (core PC · 인프라 PC)

- `compose.yaml`의 `LOKI_PUSH_URL` 기본값을 `http://100.111.111.92:3100/loki/api/v1/push`로 바꾼다.

### 4.4 `deploy/backup/` (새 폴더)

| 파일 | 도는 곳 | 하는 일 |
| --- | --- | --- |
| `Backup-Db.ps1` | core PC 04:00 · run PC 04:05 | 그 PC DB 컨테이너 안에서 `pg_dump -Fc`를 떠서 `C:\wadadak-backup\<core\|run>-<yyyyMMdd>.dump`로 꺼낸다 → `tailscale file cp`로 운영 PC에 보낸다 → 그 PC에는 최근 3개만 남긴다 |
| `Receive-Backup.ps1` | 운영 PC 04:30 | `Downloads`의 `*.dump`를 `D:\wadadak-backup\<core\|run>\`로 옮기고 30일 지난 파일을 지운다. 그날 core · run 덤프 중 하나라도 없으면 Discord로 알린다 |
| `Test-Restore.ps1` | 운영 PC 일요일 05:00 | 가장 최근 core · run 덤프를 임시 컨테이너(`postgis/postgis:17-3.5`)에 `pg_restore`한다 → 오류가 나거나 복원된 테이블 수가 덤프 목록(`pg_restore -l`의 `TABLE DATA`)과 다르면 Discord로 알린다 → 컨테이너를 지운다 |

- Discord 웹훅은 운영 PC `.env`에만 있다. 서비스 PC의 백업 작업은 알림을 보내지 않고, 빠진 날은 운영 PC가 찾는다.
- 매개변수(컨테이너 이름, DB 계정, 파일 이름 앞부분, 운영 PC 이름)만 PC마다 다르다. 작업 스케줄러 등록 명령은 러너와 같은 방식(로그인할 때가 아니라 매일 그 시각, 로그인 세션에서)이다.
- 데이터 크기(8장)로는 하루 약 9MB, 30일 약 0.3GB다.

## 5. PC와 바깥 서비스에서 할 일

### 5.1 준비 (서비스 영향 없음)

1. 운영 PC: Windows 설정은 [README](README.md) 1번과 같다(절전 안 함, 자동 로그인, 업데이트 사용 시간). Docker Desktop을 설치하고 **Start Docker Desktop when you sign in**을 켠다. GitHub 러너와 Git은 필요 없다(감시 · 백업은 Actions로 배포하지 않는다).
2. Tailscale에 서버들과 같은 계정으로 로그인하고 **Disable key expiry**. 주소(`tailscale ip -4`)를 이 문서와 4장 파일의 `100.111.111.92`에 채운다.
3. 운영 PC 앞에서 이미지를 받는다(SSH로 받으면 자격 증명 도우미가 실패한다): `grafana/loki:3.7.2` · `grafana/grafana:13.3.1` · `prom/prometheus:v3.13.5` · `postgis/postgis:17-3.5`.
4. 사전 점검: 세 서비스 PC에서 `tailscale ping 100.111.111.92`가 직접 연결, 운영 PC에서 `Test-NetConnection 100.75.79.15 -Port 15692`가 True. Taildrop 시험으로 작은 파일을 core PC → 운영 PC로 보내 본다.

### 5.2 감시 옮기기 (서비스 영향 없음, 알림이 몇 분 빈다)

1. 운영 PC: `ops/` 폴더를 복사하고 `.env`를 채운 뒤 `docker compose up -d loki prometheus`. 이때 Grafana는 아직 띄우지 않는다(3장 1번).
2. core PC · 인프라 PC: Alloy 폴더의 `compose.yaml`을 4.3의 것으로 바꾸고 `docker compose up -d --force-recreate alloy`.
3. run PC: `run/` 폴더를 4.2의 것으로 바꾸고 `docker compose up -d --remove-orphans`. 같은 프로젝트에서 loki · grafana · prometheus가 빠지며 컨테이너가 지워진다. 볼륨은 남는다(되돌리기용).
4. 운영 PC: `docker compose up -d grafana`. 알림 규칙 · 대시보드 · 하트비트가 파일에서 만들어진다.
5. 확인: 운영 PC Grafana에서 `{host="core-pc"}` · `{host="infra-pc"}` · `{service="run"}`이 새로 들어오는지, `Verify-DLQ.ps1 -SendTest`가 Discord에 닿는지.

### 5.3 백업 켜기

1. core PC · run PC에 `Backup-Db.ps1`을 두고 작업을 등록한 뒤 한 번 손으로 돌린다. 운영 PC `Downloads`에 덤프가 오는지 본다.
2. 운영 PC에 `Receive-Backup.ps1` · `Test-Restore.ps1`을 등록하고 각각 한 번 손으로 돌린다.
3. 다음 날 아침 운영 PC 백업 폴더에 core · run 덤프가 있고 Discord 알림이 없으면 끝. `Receive-Backup.ps1`의 알림은 덤프 하나를 일부러 빼고 돌려 한 번 확인한다. 그 뒤 인프라 PC의 `C:\wadadak-move\core-db.tar`를 지워도 된다(인프라 PC 분리 5.5).

### 5.4 되돌리기

- 감시: run PC `run/` 폴더를 옛 파일로 되돌려 `docker compose up -d`(볼륨이 남아 있다). 세 PC Alloy의 `LOKI_PUSH_URL`을 run PC로 되돌린다. 운영 PC는 `docker compose down`.
- 백업은 감시와 따로라 되돌릴 필요가 없다. 끄려면 작업 스케줄러에서 작업을 끈다.

## 6. 정할 것

1. Grafana를 tailnet에 열지: 제안은 운영 PC Tailscale 주소에 열고 로그인으로 막는다. 팀원 기기를 tailnet에 넣으면 ACL로 `<운영 PC>:3000`만 허용한다.
2. 보관 기간: 로그 · 지표는 지금처럼 7일, 백업 30일로 시작한다. 앱 지표를 붙이면 지표를 30일로 늘린다(디스크 여유를 보고).
3. 역할: `deploy/observability`는 로그 담당자 작업이다. 옮기는 PR을 누가 할지 정한다.
4. 운영 PC 자체 감시: healthchecks.io(팀 관리자 계정, 프로젝트 `WADADAK`)에 체크 다섯을 둔다. 핑이 정해진 시간 안에 오지 않거나 `/fail`이 오면 healthchecks.io가 Discord로 알린다. 핑 주소는 남이 알면 가짜 신호를 보낼 수 있어 비밀 값처럼 다룬다.

| 체크 | 핑을 보내는 곳 | 주기 · 유예 | 핑 주소를 두는 곳 |
| --- | --- | --- | --- |
| 감시 하트비트 | 운영 PC Grafana(`grafana-alerting-heartbeat.yaml`, 5분마다) | 5분 · 10분 | 운영 PC `ops\.env`의 `HEALTHCHECKS_GRAFANA_URL` |
| core DB 백업 | core PC `Backup-Db.ps1`(성공 핑, 실패 `/fail`) | 1일 · 2시간 | core PC `C:\wadadak-backup\healthchecks-url.txt` |
| run DB 백업 | run PC `Backup-Db.ps1` | 1일 · 2시간 | run PC `C:\wadadak-backup\healthchecks-url.txt` |
| 복원 검사 | 운영 PC `Test-Restore.ps1`(매주) | 7일 · 1일 | 운영 PC `ops\.env`의 `HEALTHCHECKS_RESTORE_URL` |
| 데이터 대조 | GitHub Actions `reconcile.yml`의 `ping` 작업 | 1일 · 2시간 | 저장소 Actions Secret `HEALTHCHECKS_RECONCILE_URL` |

## 8. 확인 근거 (2026-11-23, 읽기 전용)

- 운영 PC desktop-65isqe2(`100.111.111.92`): Windows 11 Home, i7-8700, 메모리 15.8GB, C: 여유 418GB, 절전 안 함, `docker-users` 그룹, Docker Desktop 설치(자동 시작 꺼짐). 세 서비스 PC에서 `tailscale ping`이 직접 연결 1~2ms(인프라 PC는 학교 공인 주소 경유, core · run PC는 LAN). 운영 PC에서 인프라 PC 15692에 닿는다.
- `pg_dump -Fc`(컨테이너 안, PostgreSQL 17.5): core DB 57MB → 덤프 7.8MB · 1.2초 · 표 데이터 49개, run DB 18MB → 1.3MB · 0.6초 · 19개. `pg_restore -l`로 목록을 읽을 수 있었다.
- run PC 감시 볼륨: Loki 0.1MB · Prometheus 0.4MB · Grafana 350MB. 로그는 허용 목록 요약 줄만 받고 7일 보관이라 거의 비어 있어 옮기지 않는다.
