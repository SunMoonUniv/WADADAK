# 인프라 PC 분리 (서버 3대)

상태: 구현 PR · 작성일 2026-11-20 · 기준: main `d343b81`

> **문서 목적**: 지금 core PC(desktop-i27ecdj)에는 진입점(cloudflared · gateway) · 브로커 · 사진 저장소만 남겨 인프라 PC로 쓰고, core · graphhopper · core DB를 새 core PC(desktop-elsmcmh)로 옮긴다. 구현 PR이 바꿀 것, PC와 GitHub 화면에서 사람이 할 일, 전환 · 되돌리기 순서를 정한다.
> 서버 배치(3대)는 [MSA 분리 준비와 CI·CD](<MSA 분리 준비와 CI·CD - 2026-11-04.md>) 2.3, 서버 2대 때의 배포는 같은 문서 8장, 운영 절차는 [README](README.md)를 따른다.

## 1. 결론

- 할 수 있다. 새 PC로 옮기는 데이터는 core DB 볼륨(165MB) 하나와 길찾기 파일(utilfile 약 1GB)이다. 사진 · 브로커 볼륨은 지금 PC에 그대로 둔다.
- core의 DB 호출은 같은 PC 안에서 끝난다. PC 사이를 오가는 것은 gateway → core, core → 브로커 · 사진 저장소, run → core 내부 API다.
- 그대로 옮기면 배포가 깨지거나 데이터가 갈라지는 곳이 7곳이다(3장). 로컬 재현 · 서버 확인 · 소스로 확인했다(9장).
- 전환 때 core API가 약 10분 멈춘다. 옛 core를 멈추고 DB 볼륨을 새 PC로 복사해 맞춰 본 뒤 머지하고, 새 core가 healthy가 될 때까지다.
- 옛 DB 볼륨은 지금 PC에 남겨 되돌리기에 쓴다. 전환 뒤 쌓인 데이터까지 살려 되돌리려면 DB를 반대로 한 번 더 복사한다(5.4).
- run은 이미 run PC의 자기 DB를 쓴다(6장). 로그 수집기는 core PC에 새로 띄우고 인프라 PC 것은 라벨만 바꾼다(7장).

core만 옮기는 안(DB는 지금 PC)과 비교:

| | 이 계획 (core · graphhopper · core DB를 새 PC로) | core만 옮기기 |
| --- | --- | --- |
| 옮기는 데이터 | core DB 볼륨(165MB) · utilfile | utilfile |
| core의 DB 호출 | 같은 PC 안 | 요청마다 Tailscale |
| 전환 중단 | 약 10분(DB 복사 · 확인 + 배포) | 약 3분(배포) |
| 되돌리기 | 배포를 되돌린다. 전환 뒤 데이터를 살리려면 DB를 반대로 복사한다 | 배포만 되돌린다 |
| 지금 PC가 tailnet에 여는 포트 | 5672 · 15692 · 9000 | 5432 · 5672 · 15692 · 9000 |

## 2. 배치

| PC | 이름 · Tailscale 주소 | 띄우는 것 | 러너 라벨 | compose (프로젝트) |
| --- | --- | --- | --- | --- |
| 인프라 PC (지금 core PC) | desktop-i27ecdj · `100.75.79.15` | rabbitmq · storage(RustFS) · gateway(Caddy) · cloudflared | `wadadak-infra` | `deploy/compose.yaml` (`wadadak-server` 그대로) |
| core PC (새 PC) | desktop-elsmcmh · `100.64.78.38` | core · graphhopper · postgres(core DB) | `wadadak-core` | `deploy/core/compose.yaml` (`wadadak-core`) |
| run PC | desktop-266eggn · `100.73.249.33` | run · run 전용 postgres | `wadadak-run` | `deploy/run/compose.yaml` (`wadadak-run`) |

```
폰 ─► Cloudflare ─► 인프라 PC: cloudflared ─► gateway(Caddy) ─┬─ /api/v1/runs/* ── Tailscale ──► run PC: run ─ postgres(run)
                                                              └─ 나머지 ────────── Tailscale ──► core PC: core ─ postgres(core) · graphhopper
                    인프라 PC: rabbitmq ◄── Tailscale ── core · run
                    인프라 PC: storage  ◄── Tailscale ── core        (앱은 터널의 files 주소로 직접 올리고 받는다)
                    core PC:   core     ◄── Tailscale ── run         (내부 API)
```

- 그대로인 것: 앱 주소, Cloudflare 터널 설정(cloudflared · gateway · storage가 같은 compose에 남아 Service URL `http://gateway:8080` · `http://storage:9000`이 그대로다), 브로커 주소(run의 `RABBITMQ_HOST`), 사진 · 브로커 데이터, GitHub 환경과 Secrets.
- compose 프로젝트 이름 `wadadak-server`를 바꾸지 않는다. 사진 · 브로커 볼륨 이름(`wadadak-server_photos` · `wadadak-server_broker`)이 프로젝트 이름에 묶여 있어, 바꾸면 빈 저장소 · 빈 브로커로 뜬다.
- core DB는 새 PC의 볼륨 `wadadak-core_db`로 옮긴다. 옛 볼륨 `wadadak-server_db`는 안정될 때까지 지우지 않는다(5.4 · 5.5).
- 세 PC는 같은 LAN에 둔다. PC 사이 호출이 모두 Tailscale을 탄다. 지금은 세 PC가 LAN으로 직접 이어진다(9장).

| 꺼지는 PC | 멈추는 것 |
| --- | --- |
| 인프라 PC | 전체. 진입점 · 브로커 · 사진 저장소가 여기 있다 |
| core PC | core API 전체와 run의 코스 러닝 준비 · 고스트(core 내부 API를 3초 제한으로 부른다). GPS 업로드에는 동기 호출이 없어 동작한다 |
| run PC | 러닝 API만 |

## 3. 그대로 옮기면 깨지는 곳

| # | 깨지는 곳 | 어떻게 깨지나 | 막는 법 |
| --- | --- | --- | --- |
| 1 | 새 PC에서 빈 DB로 뜬다 | 새 PC에 볼륨 `wadadak-core_db`가 없으면 postgres가 빈 DB를 만들고 core의 Flyway가 빈 스키마를 만든다. healthy로 떠서 배포는 통과한다. 그 뒤에 옛 데이터를 넣으려면 그 볼륨을 지우고 다시 해야 한다 | 머지 전에 옛 볼륨을 새 PC 볼륨으로 복사한다(5.3) |
| 2 | core 둘이 함께 뜬다 | DB가 PC마다 따로라 브로커 메시지(`wadadak.core-service`)가 두 core에 나뉘어 서로 다른 DB에 쓰인다. 스케줄 작업 잠금(`common.shedlock`)도 DB마다 있어 같은 작업이 두 번 돈다 | 옛 core를 멈춘 뒤 복사하고 새 core를 띄운다(5.3). 되돌릴 때는 새 core부터 멈춘다(5.4) |
| 3 | cloudflared의 `depends_on: core` | 없는 서비스를 가리켜 compose가 아예 뜨지 않는다 | gateway만 기다린다(4.1) |
| 4 | 사진 저장소 포트 | storage는 포트를 열지 않는다. core가 다른 PC라 닿지 않아 업로드 폼 · 사진 확인 · 삭제가 실패한다. 저장소는 처음 쓸 때 연결해서(`ObjectStorage.ensureBucket`) 배포 healthcheck로는 잡히지 않는다 | storage를 `100.75.79.15:9000`에 연다(4.1) |
| 5 | 러너 라벨 | 지금 PC의 라벨이 `wadadak-core`다. 같은 라벨 러너가 둘이면 어느 PC가 작업을 받을지 정할 수 없다. 다른 PC로 가면 그 PC에 없는 주소에 포트를 열다 실패한다 | 지금 PC는 `wadadak-infra`, 새 PC는 `wadadak-core`. 바꾸는 시점은 5.3 |
| 6 | 새 PC에서 utilfile이 지워진다 | checkout은 git이 없거나, `.git`이 없거나, origin 주소가 `https://github.com/SunMoonUniv/WADADAK`과 글자까지 같지 않으면 `clean: false`여도 작업 폴더 안을 모두 지운다. graph-cache 없이 배포하면 graphhopper가 그래프부터 만들다 300초를 넘겨 배포가 실패한다(README 7번) | 새 PC에 Git을 깔고, 저장소를 미리 clone한 뒤 utilfile을 넣는다(5.1) |
| 7 | 인프라 PC에서 utilfile이 지워진다 | 인프라 작업은 utilfile을 쓰지 않아 checkout을 기본값(`clean: true`)으로 바꾸기 쉽다. 그러면 첫 배포의 `git clean -ffdx`가 utilfile을 지워 옛 구성(core · graphhopper)으로 되돌릴 수 없다 | 인프라 작업도 `clean: false` + `git clean -ffdx -e /utilfile/`을 그대로 둔다(4.5) |

배포가 확인하지 못하는 것이 둘 있다. 브로커 연결(core는 `management.health.rabbit.enabled: false`라 브로커가 끊겨도 healthy다)과 사진 저장소 연결(4번)이다. 전환 뒤 손으로 본다(5.3). DB 연결은 확인된다. DB에 닿지 않으면 core가 Flyway에서 멈춰 healthy가 되지 않는다.

## 4. 구현 PR

### 4.1 `deploy/compose.yaml` (인프라 PC)

- `postgres` · `core` · `graphhopper`를 빼서 4.2로 옮긴다. `volumes:`의 `db`도 뺀다. 배포의 `--remove-orphans`는 빠진 서비스의 컨테이너만 지우고 볼륨은 남겨, 옛 볼륨 `wadadak-server_db`가 되돌리기용으로 남는다(9장).
- `name: wadadak-server`는 그대로다. rabbitmq 포트(5672 · 15692)도 그대로다. core · run과 run PC 모니터링이 쓴다.
- 아래 둘을 바꾼다.

```yaml
  storage:
    # core PC의 core만 Tailscale로 붙는다. 앱은 그대로 터널의 files 주소로 올리고 받는다.
    ports:
      - "100.75.79.15:9000:9000"

  cloudflared:
    depends_on:
      gateway:
        condition: service_healthy
```

### 4.2 `deploy/core/compose.yaml` (core PC, 새 파일)

`deploy/compose.yaml`의 `postgres` · `core` · `graphhopper`를 옮기고 아래만 바꾼다. 나머지 환경 변수 · healthcheck는 그대로다.

| 항목 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| `name` | `wadadak-server` | `wadadak-core` |
| `RABBITMQ_HOST` | `rabbitmq` | `100.75.79.15` |
| `STORAGE_ENDPOINT` | `http://storage:9000` | `http://100.75.79.15:9000` |
| core `ports` | `100.75.79.15:8080:8080` | `100.64.78.38:8080:8080` |
| core `depends_on` | postgres · rabbitmq | postgres |
| utilfile 경로 | `../utilfile/...` | `../../utilfile/...` (compose 파일 위치 기준) |
| graphhopper 설정 | `./graphhopper/config.yml` | `../graphhopper/config.yml` |

- `DB_URL: jdbc:postgresql://postgres:5432/wadadak`은 그대로다(같은 compose). postgres는 포트를 열지 않는다.
- postgres 이미지는 `postgis/postgis:17-3.5` 그대로다. 볼륨을 파일째 옮기므로 PostgreSQL 메이저(17) · PostGIS(3.5)가 옛 PC와 같아야 한다.
- `GRAPHHOPPER_URL: http://graphhopper:8989`는 그대로다(같은 compose).
- `SERVER_FORWARD_HEADERS_STRATEGY: native`는 그대로다. 게이트웨이가 Tailscale 너머에 있는 것은 run과 같다.

	}

### 4.4 `deploy/run/compose.yaml`

`CORE_API_URL`만 `http://100.64.78.38:8080`으로 바꾼다. 브로커 주소(`100.75.79.15`)는 그대로다.

### 4.5 `.github/workflows/backend.yml`

| 작업 | runs-on | environment | concurrency | 하는 일 |
| --- | --- | --- | --- | --- |
| `deploy-core` (새로) | `[self-hosted, wadadak-core]` | `wadadak-server` | `wadadak-core` | checkout(`clean: false`) → utilfile 빼고 정리 → GHCR 로그인 → `docker pull ghcr.io/sunmoonuniv/wadadak-core:main` → `docker compose -f deploy/core/compose.yaml up -d --wait --wait-timeout 300 --remove-orphans` → 이미지 정리 |
| `deploy-infra` (지금 `deploy`) | `[self-hosted, wadadak-infra]` | `wadadak-server` | `wadadak-server` | checkout(`clean: false`) → utilfile 빼고 정리 → `docker compose -f deploy/compose.yaml up -d --wait --wait-timeout 300 --remove-orphans` → `caddy reload` → 이미지 정리. GHCR 이미지를 쓰지 않아 로그인 · pull 단계는 뺀다 |
| `deploy-run` | 그대로 | `wadadak-run` | `wadadak-run` | 그대로. `needs: deploy-infra` |
| `smoke` | `[self-hosted, wadadak-infra]` | 없음 | 없음 | 그대로. gateway가 인프라 PC에 있다 |

- 순서는 `images` → `deploy-core` → `deploy-infra` → `deploy-run` → `smoke`다. 새 core가 healthy가 된 뒤에 gateway가 새 주소를 읽는다(`caddy reload`). 전환 때 `deploy-core`가 실패하면 인프라 PC는 손대지 않은 채라 되돌리기가 짧다(5.4).
- 비밀값을 PC별로 나눠 넘긴다. 작업은 자기가 적은 Secrets만 받는다.
  - `deploy-core`: `DB_PASSWORD` · `JWT_PUBLIC_KEY` · `JWT_PRIVATE_KEY` · `STORAGE_SECRET_KEY` · `BROKER_PASSWORD` · `FCM_CREDENTIALS_LOCATION`(`FCM_SERVICE_ACCOUNT`로 만든다) · `NAVER_SEARCH_CLIENT_ID` · `NAVER_SEARCH_CLIENT_SECRET` · `NAVER_GEOCODE_CLIENT_ID` · `NAVER_GEOCODE_CLIENT_SECRET` · `TYPESAFE_API_KEY` · `ADMIN_USERNAME` · `ADMIN_PASSWORD`
  - `deploy-infra`: `STORAGE_SECRET_KEY` · `BROKER_PASSWORD` · `TUNNEL_TOKEN`, 그리고 `COMPOSE_PROFILES`
- 환경은 새로 만들지 않고 `wadadak-server`를 두 작업이 같이 쓴다. 저장한 Secrets 값은 다시 읽을 수 없어서, 새 환경을 만들려면 원래 값이 있어야 한다. JWT 키를 새로 만들면 모든 기기가 다시 로그인해야 한다.
- 동시 실행 그룹은 PC마다 따로 둔다. 한 그룹을 같이 쓰면 다음 실행의 대기 작업이 앞 실행의 대기 작업을 취소해, 한 PC만 배포된 채 남을 수 있다.
- `deploy-infra`의 checkout을 기본값으로 바꾸지 않는다(3장 7번).

### 4.6 사진 저장소 호출 시간 제한 (`ObjectStorage`)

`ObjectStorage`가 만드는 `MinioClient`에는 시간 제한이 없어 MinIO 기본값 5분을 쓴다. 저장소가 다른 PC로 가면, 응답 없이 끊긴 망에서 사진 요청이 최대 5분 매달린다. `setTimeout`으로 연결 3초 · 쓰기 5초 · 읽기 5초를 건다(소셜 로그인 · FCM 호출과 같은 값).

### 4.8 머지 전에 손으로 검사

deploy 작업은 main에서만 돌아서 PR의 CI는 compose 오류를 잡지 못한다. 구현 PR에서 아래가 오류 없이 끝나야 한다(비밀값 자리는 아무 값).

```bash
STORAGE_SECRET_KEY=x BROKER_PASSWORD=x docker compose -f deploy/compose.yaml config -q
```

```bash
DB_PASSWORD=x JWT_PUBLIC_KEY=x JWT_PRIVATE_KEY=x STORAGE_SECRET_KEY=x BROKER_PASSWORD=x docker compose -f deploy/core/compose.yaml config -q
```

`-q`를 빼고 돌리면 utilfile 경로가 저장소 최상위 `utilfile`로 풀리는지 볼 수 있다.

## 5. PC와 GitHub에서 할 일

### 5.1 새 core PC 준비 (언제 해도 된다, 서비스에 영향 없음)

1. Windows 설정은 [README](README.md) 1번과 같다. 절전 안 함, 재부팅 뒤 자동 로그인, Windows 업데이트 사용 시간, 로그인 계정을 `docker-users` 그룹에 넣는다. JWT 개인키가 `docker inspect`로 보이므로 이 계정은 팀 관리자만 쓴다.
2. Docker Desktop을 설치하고, 한 번 실행해 첫 화면을 마친 뒤 Settings → General → **Start Docker Desktop when you sign in**을 켠다.
   - core JVM · graphhopper(`-Xmx2g`) · postgres가 함께 돈다. Docker(WSL2)는 기본으로 PC 메모리의 절반을 쓴다. desktop-elsmcmh는 16GB라 그대로 둔다. 8GB PC라면 `%UserProfile%\.wslconfig`의 `memory`를 6GB 이상으로 올린다.
3. **Git for Windows를 설치한다(기본 옵션).** 없으면 checkout이 배포마다 작업 폴더를 통째로 지운다(3장 6번).
4. Tailscale에 지금 두 PC와 같은 계정으로 로그인한다. 주소(`tailscale ip -4`)가 `100.64.78.38`이 아니면 4장의 이 주소를 그 주소로 바꾼다.
5. GitHub 러너를 [README](README.md) 2번대로 등록한다(`C:\actions-runner-wadadak`, 작업 스케줄러).
   - **`--labels`는 빼고** 등록한다(라벨 질문은 Enter). 지금 PC가 아직 `wadadak-core`라 같은 라벨을 주면 지금 배포가 새 PC로 갈 수 있다.
   - Git · Docker를 러너보다 먼저 설치한다. 러너를 먼저 띄웠으면 다시 시작한다(`Stop-ScheduledTask` · `Start-ScheduledTask -TaskName 'WADADAK GitHub Runner'`).
   - 포크 PR 승인(README 보안 1번)은 저장소 설정이라 새 러너에도 걸린다.

## 7. 로그 · 알림

수집기(Alloy)는 자기 PC의 Docker만 본다. core PC와 인프라 PC에 같은 설정([`observability/core`](observability/README.md))을 띄우고 `host` 라벨만 다르게 한다. 구현 PR이 바꾸는 것:

- 대시보드 `core-logs.json`: `host="core-pc"` 대신 `host=~"core-pc|infra-pc"`로 두 PC를 함께 본다.
- Tailscale ACL 예시(`run/README-run-pc.md`)에 새 PC를 넣는다. Loki(`100.73.249.33:3100`)는 새 PC에서 닿는다(9장).

- PC가 멈췄을 때 알림: core PC나 core가 멈추면 "큐 소비자 없음"(core 큐 consumer 0이 2분), 인프라 PC가 멈추면 "DLQ 지표 수집 중단"이 Discord로 온다. run PC가 멈추면 알림을 보내는 Grafana도 멈춘다(받아들인 한계).

## 9. 확인 근거

  - run 컨테이너의 `DB_URL`이 `jdbc:postgresql://postgres:5432/wadadak`(run PC DB)이고, core DB에 붙은 계정은 `wadadak`뿐이다(6장)
  - 새 PC(desktop-elsmcmh): RAM 16GB · i7-8700 · 디스크 여유 415GB · Windows 11 Home · Docker Desktop 29.9.3 (5.1)
  - 새 PC의 `tailscale ping`: 인프라 PC `via 192.168.0.145:41641` 2ms, run PC `via 192.168.0.146:41641` 1ms. 인프라 PC의 5672 · 15692 · 8080과 run PC의 Loki 3100에 TCP로 닿는다. 시계는 다른 PC와 1초 안으로 맞았다(2장 · 5.2 · 7장)
  - Actions 기록: 서버 코드가 그대로인 main 실행(`37a9cb5` · `803f56c`)은 머지부터 smoke 끝까지 약 3분이었다(5.3)
- 로컬 재현(Docker 29.8.2 · Compose v5.6.0, `postgis/postgis:17-3.5`)
  - 멈춘 DB 볼륨을 `tar`로 떠서 라벨 붙인 새 볼륨에 풀고 compose로 띄웠다. `Skipping initialization`, 도형 데이터 · 계정이 그대로였고, 옛 비밀번호로 접속되며 새 `POSTGRES_PASSWORD`로는 `password authentication failed`, 데이터 폴더는 `drwx------ postgres postgres`였다(5.3)
  - 같은 볼륨은 `POSTGRES_PASSWORD` 없이 임시 컨테이너로도 뜨고, 지문이 원본과 같았다. 그 컨테이너를 `docker stop`한 뒤 compose로 띄우면 `database system was shut down`(정상 종료)에서 시작한다(5.3 4번)
  - 라벨 없이 만든 볼륨: ``volume "…" already exists but was not created by Docker Compose. Use `external: true` to use an existing volume`` 경고가 나고 동작은 한다(5.3)

  - 없는 서비스에 의존: `service "cloudflared" depends on undefined service "core": invalid compose project` (3장 3번)
  - 그 PC에 없는 주소에 포트: `ports are not available: exposing port TCP 100.99.99.99:18080 -> 127.0.0.1:0: listen tcp4 100.99.99.99:18080: can't bind on the specified endpoint` (3장 5번, 5.5)

  - 러너 라벨은 등록한 뒤 화면(Labels 톱니)이나 REST API로 붙이고 뗀다. 같은 라벨을 가진 러너 중 어느 것이 받는지는 정해져 있지 않다(3장 5번)
