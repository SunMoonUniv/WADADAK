# 인프라 PC 분리 (서버 3대)

상태: 계획 · 작성일 2026-11-20 · 기준: main `43a9aa3`

> **문서 목적**: 지금 core PC를 인프라 PC(DB · 브로커 · 사진 저장소 · 게이트웨이 · 터널)로 남기고, 새 PC로 core 서비스만 옮긴다. 구현 PR이 바꿀 것, PC와 GitHub 화면에서 사람이 할 일, 전환 · 되돌리기 순서를 정한다.
> 서버 2대 구성은 [MSA 분리 준비와 CI·CD](<MSA 분리 준비와 CI·CD - 2026-11-04.md>) 2.3 · 8장, 운영 절차는 [README](README.md)를 따른다.

## 1. 결론

- 할 수 있다. 상태를 가진 것(DB · 사진 · 브로커 볼륨)은 지금 PC에 그대로 남아 데이터를 옮기지 않는다. 옮기는 것은 상태가 없는 core와 길찾기 파일(utilfile 약 1GB)뿐이다.
- 그대로 옮기면 배포가 깨지는 곳이 6곳이다(3장). 모두 로컬 재현이나 소스로 확인했다(8장).
- 전환 때 새 core가 뜰 때까지(최대 약 3분) core API가 멈춘다. DB는 처음부터 끝까지 지금 PC에 있어 되돌려도 데이터를 잃지 않는다.

반대 안(지금 PC를 core로, 새 PC를 인프라로)과 비교:

| | 이 계획 (지금 PC = 인프라, 새 PC = core) | 반대 안 (지금 PC = core, 새 PC = 인프라) |
| --- | --- | --- |
| 옮기는 것 | core(상태 없음) · utilfile 약 1GB | DB · 사진 · 브로커 볼륨 |
| 중단 | 새 core가 뜰 때까지(최대 약 3분) | 볼륨 복사 + 머지 뒤 CI(테스트 · 이미지) 시간 |
| 되돌리기 | 배포만 되돌린다 | 옛 볼륨으로 돌아가면 전환 뒤 쌓인 데이터를 잃는다 |
| 바뀌는 주소 | core 주소(게이트웨이, run의 `CORE_API_URL`) | 인프라 주소(run의 DB · 브로커, core의 접속 정보 전부) |

## 2. 배치

| PC | Tailscale 주소 | 띄우는 것 | 러너 라벨 | compose (프로젝트) |
| --- | --- | --- | --- | --- |
| 인프라 PC (지금 core PC) | `100.75.79.15` 그대로 | postgres · db-init · rabbitmq · storage(RustFS) · gateway(Caddy) · cloudflared | `wadadak-infra` | `deploy/compose.yaml` (`wadadak-server` 그대로) |
| core PC (새 PC) | `<core 주소>` (설치 뒤 정한다) | core · graphhopper | `wadadak-core` | `deploy/core/compose.yaml` (`wadadak-core`) |
| run PC | `100.73.249.33` 그대로 | run · run 전용 postgres | `wadadak-run` | `deploy/run/compose.yaml` (`wadadak-run`) |

```
폰 ─► Cloudflare ─► 인프라 PC: cloudflared ─► gateway(Caddy) ─┬─ /api/v1/runs/* ── Tailscale ──► run PC: run
                                                              └─ 나머지 ────────── Tailscale ──► core PC: core ─ graphhopper
                    인프라 PC: postgres · rabbitmq · storage ◄── Tailscale ── core · run
```

- 그대로인 것: 앱 주소, Cloudflare 터널 설정(cloudflared · gateway · storage가 같은 compose에 남아 Service URL `http://gateway:8080` · `http://storage:9000`이 그대로다), 인프라 PC 주소(run의 DB · 브로커 주소), GitHub 환경과 Secrets, 데이터.
- compose 프로젝트 이름 `wadadak-server`를 바꾸지 않는다. 볼륨 이름(`wadadak-server_db` · `wadadak-server_photos` · `wadadak-server_broker`)이 프로젝트 이름에 묶여 있어, 바꾸면 빈 DB로 뜬다.
- 세 PC는 같은 LAN에 둔다. core의 DB · 브로커 · 사진 저장소 호출이 모두 Tailscale을 탄다(MSA 분리 준비와 CI·CD 2.3의 같은 LAN 규칙이 이제 core에도 걸린다).

| 꺼지는 PC | 멈추는 것 |
| --- | --- |
| 인프라 PC | 전체. 진입점 · DB · 브로커 · 사진 저장소가 여기 있다 |
| core PC | core API 전체와 run의 코스 러닝 준비 · 고스트(core 내부 API를 3초 제한으로 부른다). GPS 업로드에는 동기 호출이 없어 동작한다 |
| run PC | 러닝 API만 |

## 3. 그대로 옮기면 깨지는 곳

| # | 깨지는 곳 | 어떻게 깨지나 | 막는 법 |
| --- | --- | --- | --- |
| 1 | db-init 대기 | `compose up --wait`는 끝난 컨테이너를 실패로 본다. 지금은 core가 `service_completed_successfully`로 db-init을 기다려 넘어간다. core가 빠지면 인프라 배포가 매번 실패한다 | gateway가 db-init을 `service_completed_successfully`로 기다린다(4.1) |
| 2 | cloudflared의 `depends_on: core` | 없는 서비스를 가리켜 compose가 아예 뜨지 않는다 | gateway만 기다린다(4.1) |
| 3 | 사진 저장소 포트 | storage는 포트를 열지 않는다. core가 다른 PC라 닿지 않아 업로드 폼 · 사진 확인 · 삭제가 실패한다. 저장소는 처음 쓸 때 연결해서(`ObjectStorage.ensureBucket`) 배포 healthcheck로는 잡히지 않는다 | storage를 `100.75.79.15:9000`에 연다(4.1) |
| 4 | 러너 라벨 | 지금 PC의 라벨이 `wadadak-core`다. 같은 라벨 러너가 둘이면 어느 PC가 작업을 받을지 정할 수 없다. 다른 PC로 가면 그 PC에 없는 주소에 포트를 열다 실패한다 | 지금 PC는 `wadadak-infra`, 새 PC는 `wadadak-core`. 바꾸는 시점은 5.3 |
| 5 | 새 PC에서 utilfile이 지워진다 | checkout은 git이 없거나, `.git`이 없거나, origin 주소가 `https://github.com/SunMoonUniv/WADADAK`과 글자까지 같지 않으면 `clean: false`여도 작업 폴더 안을 모두 지운다. graph-cache 없이 배포하면 graphhopper가 그래프부터 만들다 300초를 넘겨 배포가 실패한다(README 7번) | 새 PC에 Git을 깔고, 저장소를 미리 clone한 뒤 utilfile을 넣는다(5.1) |
| 6 | 인프라 PC에서 utilfile이 지워진다 | 인프라 작업은 utilfile을 쓰지 않아 checkout을 기본값(`clean: true`)으로 바꾸기 쉽다. 그러면 첫 배포의 `git clean -ffdx`가 utilfile을 지워 옛 구성(graphhopper 포함)으로 되돌릴 수 없다 | 인프라 작업도 `clean: false` + `git clean -ffdx -e /utilfile/`을 그대로 둔다(4.5) |

배포가 확인하지 못하는 것이 둘 있다. 브로커 연결(core는 `management.health.rabbit.enabled: false`라 브로커가 끊겨도 healthy다)과 사진 저장소 연결(3번)이다. 전환 뒤 손으로 본다(5.3). DB 연결은 확인된다. DB에 닿지 않으면 core가 Flyway에서 멈춰 healthy가 되지 않는다.

## 4. 구현 PR

### 4.1 `deploy/compose.yaml` (인프라 PC)

- `core` · `graphhopper`를 빼서 4.2로 옮긴다. `name: wadadak-server`는 그대로다.
- postgres(5432) · rabbitmq(5672) 포트는 그대로 둔다. 이제 run과 core가 함께 쓴다.
- 아래 셋을 바꾼다.

```yaml
  storage:
    # core PC의 core만 Tailscale로 붙는다. 앱은 그대로 터널의 files 주소로 올리고 받는다.
    ports:
      - "100.75.79.15:9000:9000"

  gateway:
    # compose up --wait는 끝난 컨테이너를 실패로 본다. 기다리는 서비스가 있어야 db-init을 한 번 돌고 끝나는 작업으로 본다.
    depends_on:
      db-init:
        condition: service_completed_successfully

  cloudflared:
    depends_on:
      gateway:
        condition: service_healthy
```

### 4.2 `deploy/core/compose.yaml` (core PC, 새 파일)

`deploy/compose.yaml`의 `core` · `graphhopper`를 옮기고 아래만 바꾼다. 나머지 환경 변수 · healthcheck는 그대로다.

| 항목 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| `name` | `wadadak-server` | `wadadak-core` |
| `DB_URL` | `jdbc:postgresql://postgres:5432/wadadak` | `jdbc:postgresql://100.75.79.15:5432/wadadak` |
| `RABBITMQ_HOST` | `rabbitmq` | `100.75.79.15` |
| `STORAGE_ENDPOINT` | `http://storage:9000` | `http://100.75.79.15:9000` |
| core `ports` | `100.75.79.15:8080:8080` | `<core 주소>:8080:8080` |
| core `depends_on` | postgres · rabbitmq · db-init | 없음(다른 PC다) |
| utilfile 경로 | `../utilfile/...` | `../../utilfile/...` (compose 파일 위치 기준) |
| graphhopper 설정 | `./graphhopper/config.yml` | `../graphhopper/config.yml` |

- `GRAPHHOPPER_URL: http://graphhopper:8989`는 그대로다(같은 compose).
- `SERVER_FORWARD_HEADERS_STRATEGY: native`는 그대로다. 게이트웨이가 Tailscale 너머에 있는 것은 run과 같다.

core로 가는 줄만 바꾼다.

```

		reverse_proxy <core 주소>:8080
	}
```

### 4.4 `deploy/run/compose.yaml`

`CORE_API_URL`만 `http://<core 주소>:8080`으로 바꾼다. DB · 브로커 주소(`100.75.79.15`)는 그대로다.

### 4.5 `.github/workflows/backend.yml`

| 작업 | runs-on | environment | concurrency | 하는 일 |
| --- | --- | --- | --- | --- |
| `deploy-infra` (지금 `deploy`) | `[self-hosted, wadadak-infra]` | `wadadak-server` | `wadadak-server` | checkout(`clean: false`) → utilfile 빼고 정리 → `docker compose -f deploy/compose.yaml up -d --wait --wait-timeout 300 --remove-orphans` → `caddy reload` → 이미지 정리 |
| `deploy-core` (새로) | `[self-hosted, wadadak-core]` | `wadadak-server` | `wadadak-core` | checkout(`clean: false`) → utilfile 빼고 정리 → GHCR 로그인 → `docker pull ghcr.io/sunmoonuniv/wadadak-core:main` → `docker compose -f deploy/core/compose.yaml up -d --wait --wait-timeout 300 --remove-orphans` → 이미지 정리 |
| `deploy-run` | 그대로 | `wadadak-run` | `wadadak-run` | 그대로. `needs: deploy-core` |
| `smoke` | `[self-hosted, wadadak-infra]` | 없음 | 없음 | 그대로. gateway가 인프라 PC에 있다 |

- 순서는 `images` → `deploy-infra` → `deploy-core` → `deploy-run` → `smoke`다. 제공하는 쪽을 먼저 띄운다(인프라: DB · 브로커 · db-init, core: run이 부르는 내부 API).
- 비밀값을 PC별로 나눠 넘긴다. 작업은 자기가 적은 Secrets만 받는다.
  - `deploy-infra`: `DB_PASSWORD` · `RUN_DB_PASSWORD` · `STORAGE_SECRET_KEY` · `BROKER_PASSWORD` · `TUNNEL_TOKEN`, 그리고 `COMPOSE_PROFILES`
  - `deploy-core`: `DB_PASSWORD` · `JWT_PUBLIC_KEY` · `JWT_PRIVATE_KEY` · `STORAGE_SECRET_KEY` · `BROKER_PASSWORD` · `FCM_CREDENTIALS_LOCATION` · `NAVER_SEARCH_CLIENT_ID` · `NAVER_SEARCH_CLIENT_SECRET` · `NAVER_GEOCODE_CLIENT_ID` · `NAVER_GEOCODE_CLIENT_SECRET` · `TYPESAFE_API_KEY` · `ADMIN_USERNAME` · `ADMIN_PASSWORD`
- 환경은 새로 만들지 않고 `wadadak-server`를 두 작업이 같이 쓴다. 저장한 Secrets 값은 다시 읽을 수 없어서, 새 환경을 만들려면 원래 값이 있어야 한다. JWT 키를 새로 만들면 모든 기기가 다시 로그인해야 한다.
- 동시 실행 그룹은 PC마다 따로 둔다. 한 그룹을 같이 쓰면 다음 실행의 대기 작업이 앞 실행의 대기 작업을 취소해, 한 PC만 배포된 채 남을 수 있다.
- `deploy-infra`의 checkout을 기본값으로 바꾸지 않는다(3장 6번).

## 5. PC와 GitHub에서 할 일

### 5.1 새 core PC 준비 (언제 해도 된다, 서비스에 영향 없음)

1. Windows 설정은 [README](README.md) 1번과 같다. 절전 안 함, 재부팅 뒤 자동 로그인, Windows 업데이트 사용 시간, 로그인 계정을 `docker-users` 그룹에 넣는다. JWT 개인키가 `docker inspect`로 보이므로 이 계정은 팀 관리자만 쓴다.
2. Docker Desktop을 설치하고 Settings → General → **Start Docker Desktop when you sign in**을 켠다.
   - core JVM과 graphhopper(`-Xmx2g`)가 함께 돈다. Docker(WSL2)는 기본으로 PC 메모리의 절반을 쓰므로 16GB PC를 권한다. 8GB PC면 `%UserProfile%\.wslconfig`의 `memory`를 6GB 이상으로 올린다.
3. **Git for Windows를 설치한다(기본 옵션).** 없으면 checkout이 배포마다 작업 폴더를 통째로 지운다(3장 5번).
4. Tailscale을 설치하고 지금 두 PC와 같은 계정으로 로그인한다. `tailscale ip -4`가 보여 주는 주소가 `<core 주소>`다. 구현 PR에 넣는다.
5. GitHub 러너를 [README](README.md) 2번대로 등록한다(`C:\actions-runner-wadadak`, 작업 스케줄러).
   - **`--labels`는 빼고** 등록한다(라벨 질문은 Enter). 지금 PC가 아직 `wadadak-core`라 같은 라벨을 주면 지금 배포가 새 PC로 갈 수 있다.
   - Git · Docker를 러너보다 먼저 설치한다. 러너를 먼저 띄웠으면 다시 시작한다(`Stop-ScheduledTask` · `Start-ScheduledTask -TaskName 'WADADAK GitHub Runner'`).
   - 포크 PR 승인(README 보안 1번)은 저장소 설정이라 새 러너에도 걸린다.
6. 저장소를 러너 작업 폴더에 미리 받고 utilfile을 넣는다. 러너를 돌리는 계정으로 한다.

   ```powershell
   git clone https://github.com/SunMoonUniv/WADADAK C:\actions-runner-wadadak\_work\WADADAK\WADADAK
   ```

   ```powershell
   git -C C:\actions-runner-wadadak\_work\WADADAK\WADADAK remote get-url origin
   ```

   - 두 번째 명령의 출력이 정확히 `https://github.com/SunMoonUniv/WADADAK`이어야 한다(끝에 `.git` 없음, 대소문자 그대로).
   - 지금 PC의 같은 위치(`…\_work\WADADAK\WADADAK\utilfile`)에서 셋을 복사한다: `graphhopper\`(jar · pbf · `graph-cache`), `elevation\spot_heights.bin`, `layers\`(`sidewalk.bin` · `river.bin` · `lamps.bin`). 원자료 폴더는 필요 없다.
   - 지금 PC의 utilfile은 지우지 않는다. 되돌리기에 쓴다(5.4).
7. 세 PC 모두 Tailscale 키 만료를 끈다. 관리 화면 Machines → 그 PC 줄 오른쪽 메뉴 → **Disable key expiry**. 기본으로 180일 뒤 만료되고, 만료되면 그 PC와의 연결이 끊긴다.

### 5.2 사전 점검 (서비스에 영향 없음)

새 PC에서:

```powershell
tailscale ping 100.75.79.15
```

```powershell
tailscale ping 100.73.249.33
```

```powershell
Test-NetConnection 100.75.79.15 -Port 5432
```

```powershell
Test-NetConnection 100.75.79.15 -Port 5672
```

- ping은 `via <LAN 주소>`(직접 연결)여야 한다. `via DERP`면 중계를 거쳐 core의 DB 호출마다 지연이 붙는다. 같은 LAN인지 본다.
- 포트 둘은 `TcpTestSucceeded : True`여야 한다. 5672가 막히면 core가 healthy로 떠도 이벤트가 오가지 않는다(3장 끝).
- run PC에서도 `tailscale ping <core 주소>`가 직접 연결인지 본다(run → core 내부 API).

새 PC의 8080이 Tailscale로 열리는지(방화벽):

1. 새 PC: `docker run -d --name porttest -p <core 주소>:8080:80 nginx:alpine`. 방화벽 창이 뜨면 허용한다.
2. 인프라 PC · run PC: `Test-NetConnection <core 주소> -Port 8080`이 `True`
3. 새 PC: `docker rm -f porttest`

그 밖에:

- 시계: 세 PC에서 `w32tm /query /status`로 마지막 동기화를 본다. 사진 업로드 폼은 core PC가 10분짜리로 서명하고 인프라 PC의 저장소가 검사한다.
- tailnet: Tailscale 관리 화면에 모르는 기기가 없는지 본다. postgres · rabbitmq · storage · core 포트가 tailnet 안에는 열려 있다.
- GitHub: 지금 PC 러너에 `wadadak-infra` 라벨을 미리 붙인다(Settings → Actions → Runners → 러너 이름 → Labels의 톱니 → `wadadak-infra` 입력 → Create new label). 이 라벨을 쓰는 작업이 아직 없어 영향이 없다. `wadadak-core`는 아직 떼지 않는다.

### 5.3 전환 (순서대로, 한 번에)

1. 준비한다.
   - 구현 PR이 승인 · CI 통과 상태이고 `<core 주소>`가 들어 있다. Actions에 도는 배포가 없다.
   - 지연 비교용으로 지금 core의 요청 로그를 남긴다. 전환하면 옛 core 컨테이너와 로그가 지워진다.

     ```bash
     docker logs wadadak-server-core-1 2>&1 | grep RequestLogFilter > core-before.log
     ```

   - 팀에 core API가 몇 분 멈춘다고 알린다. 여기서부터 끝날 때까지 다른 서버 PR 머지와 Run workflow를 하지 않는다.
2. 라벨을 바꾼다. 지금 PC 러너에서 `wadadak-core`를 떼고(Labels 톱니에서 체크된 라벨을 누른다), 새 PC 러너에 `wadadak-core`를 붙인다.
3. 바로 구현 PR을 머지한다.
4. Actions에서 `deploy-infra`(지금 PC) → `deploy-core`(새 PC) → `deploy-run` → `smoke`를 지켜본다. `deploy-infra`가 옛 core를 지운 뒤부터 새 core가 healthy가 될 때까지 core API는 502다.
5. 확인한다.
   - `https://api.leedohyunn8n.shop/actuator/health`가 `UP`, `https://files.leedohyunn8n.shop/health`가 `ok`
   - 인프라 PC: `docker compose -p wadadak-server ps -a`에 postgres · rabbitmq · storage · gateway · cloudflared가 떠 있고 db-init은 `exited (0)`, core · graphhopper는 없다
   - core PC: `docker compose -p wadadak-core ps`에서 core · graphhopper가 healthy. `docker logs wadadak-core-core-1`에 `표고점 … 읽었다` · `SIDEWALK 칸 … 읽었다`
   - 브로커(배포가 보지 않는다): 인프라 PC에서 `docker exec wadadak-server-rabbitmq-1 rabbitmqctl list_queues name messages consumers`를 돌려 `wadadak.core-service`의 consumers가 1 이상이고 messages가 쌓이지 않는지 본다
   - 사진 저장소(배포가 보지 않는다): 앱에서 사진을 한 장 올린다
   - 앱: 로그인, 코스 자동 생성(graphhopper), 코스 러닝 준비 · 고스트(run → 새 core 내부 API)
   - 지연: `docker logs wadadak-core-core-1 2>&1 | grep RequestLogFilter`의 처리 시간을 `core-before.log`와 비교한다

### 5.4 되돌리기

빠른 길(Actions 재실행, PR 승인 · CI를 기다리지 않는다):

1. 라벨을 되돌린다. 지금 PC 러너에 `wadadak-core`를 다시 붙이고, 새 PC 러너에서 `wadadak-core`를 뗀다. `wadadak-infra`는 붙어 있어도 된다.
2. Actions → Backend CI → 전환 PR 머지 전에 배포까지 성공한 마지막 main 실행 → `deploy` 작업 → **Re-run this job**.
   - 그 실행의 커밋(옛 compose · Caddyfile · 워크플로)으로 돌고, 뒤에 매인 `deploy-run` · `smoke`도 다시 돈다.
   - 지금 PC에 utilfile이 남아 있어 옛 구성(graphhopper 포함)이 그대로 뜬다.
   - 30일이 지난 실행은 다시 돌릴 수 없다. 그때는 아래 느린 길로 간다.
3. 끝나면 새 PC의 core를 멈춘다: `docker compose -p wadadak-core down`. core 둘이 같은 DB · 브로커에 붙어도 깨지지는 않지만(스케줄 작업은 ShedLock, 큐 메시지는 한 소비자만 받는다) 남겨 둘 이유가 없다.
4. main에는 아직 새 구성이 있다. revert PR이나 고친 PR을 머지하기 전에는 다른 서버 PR을 머지하지 않는다. 머지하면 새 워크플로가 되돌린 라벨로 돌다 실패한다.

느린 길: 라벨을 1번처럼 되돌린 뒤 revert PR을 머지한다(승인 1명 + CI).

DB · 사진 · 브로커는 처음부터 지금 PC에 있어 어느 길로 되돌려도 데이터를 잃지 않는다.

### 5.5 안정된 뒤 (며칠 뒤)

- 지금 PC 정리: `utilfile`의 `graphhopper` · `elevation` · `layers`, 이미지 `ghcr.io/sunmoonuniv/wadadak-core:main` · `eclipse-temurin:21-jre`를 지운다. utilfile을 지우면 5.4의 빠른 길은 쓸 수 없다.
- 매달 그래프 갱신은 core PC에서 한다: `docker compose -p wadadak-core stop graphhopper` → `graph-cache` 교체 → `docker compose -p wadadak-core start graphhopper`.
- 재부팅한 PC는 `docker compose -p <프로젝트> ps`로 확인한다. Docker가 Tailscale보다 먼저 뜨면 그 PC 주소에 포트를 못 열어 컨테이너가 뜨지 않는다(`can't bind on the specified endpoint`). 인프라 PC가 그러면 전체가 멈춘다. 안 떴으면 수동 배포(Actions → Backend CI → Run workflow)를 한 번 돌린다.

## 6. DB 분리(MSA 분리 준비와 CI·CD 8.5)와 겹치는 곳

- 8.5 contract는 core PostgreSQL의 Tailscale 포트를 지운다고 적었다. 이 계획 뒤에는 core가 다른 PC에서 그 포트로 붙으므로 포트는 남긴다. contract에서는 run 계정 · run 스키마 · db-init만 지우고, 8.5의 그 문장도 고친다.
- contract에서 db-init을 지울 때 gateway의 `depends_on: db-init`도 함께 지운다. 남기면 3장 2번과 같은 오류로 compose가 뜨지 않는다.
- 어느 쪽을 먼저 해도 된다. contract가 먼저면 3장 1번은 생기지 않는다(db-init이 없다).

  - 아무도 기다리지 않는 한 번짜리 서비스: `container wadadak-verify-a-init-1 exited (0)`, 종료 코드 1 (3장 1번)

  - 러너 라벨은 등록한 뒤 화면(Labels 톱니)이나 REST API로 붙이고 뗀다. 같은 라벨을 가진 러너 중 어느 것이 받는지는 정해져 있지 않다 (3장 4번)

  - 사진 저장소는 처음 쓸 때 연결한다(`ObjectStorage.ensureBucket`). 업로드 폼 유효 시간은 10분이다(`ObjectStorage.FORM_TTL`)
