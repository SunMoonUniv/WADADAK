# 모듈 부하 테스트

상태: 측정 · 작성일 2026-11-14 · 기준: main `9acfdad`

> **문서 목적**: 모든 모듈에 부하를 걸어 어떤 모듈을 서비스로 떼어야 하는지 데이터로 정한다([개발 정책 v3](../개발%20정책%20v3.md) 11.1 기준: 부하 · 장애 격리 · 확장 단위).
> 분리 방법은 [`MSA 분리 준비와 CI·CD`](MSA%20분리%20준비와%20CI·CD%20-%202026-11-04.md)를 따른다.

## 결론

1. **떼어낼 모듈은 run 하나다.** 지금 계획(core + run 2개 서비스)이 맞다.
   - 실제 사용 비율로 섞으면 run은 여정의 1/17인데 **DB 시간의 84~88%**, 서버 CPU의 38%를 쓴다.
   - run 업로드가 몰리면 다른 모든 모듈의 응답이 2~12배 느려진다. 반대로 course · ranking에 초당 240~260개 요청을 걸어도 다른 모듈은 영향이 없었다.
   - run을 다른 인스턴스로 떼자(같은 DB) member · ranking · review · notification은 기준선으로 돌아왔다.
2. **분리만으로는 풀리지 않는 것이 두 가지 있다.** 분리와 함께 고친다.
   - **판정 처리량 상한**: `RunProcessingWorker`에 `@SchedulerLock`이 걸려 있어서, 기록 판정이 클러스터 전체에서 한 번에 하나씩만 돈다. 서버를 몇 대로 늘려도 **초당 약 3.4건(시간당 약 1.2만 건)** 에서 멈춘다. 분리의 "run만 늘린다"는 이점이 이것 때문에 생기지 않는다.
   - **같은 DB의 WAL 경합**: run 업로드는 GPS 한 점을 한 행으로 쓴다(30분 러닝 한 번에 약 2,200행). run을 떼어도 DB가 같으면, core의 **쓰기 요청**은 커밋할 때 이 WAL 쓰기를 기다린다. 코스 상세(조회 수 +1)는 분리 뒤에도 기준선의 2.7배였다.
3. **나머지 모듈은 뗄 이유가 없다.**
   - course는 CPU 비중이 가장 크지만(40%) 요청당 비용이 작고, 과부하에서도 다른 모듈을 방해하지 않았다. 수평 확장(인스턴스 증설)으로 충분하다.
   - ranking · review · member · notification은 합쳐도 CPU 22%, DB 6%다.
4. **이번 테스트는 동시 사용자 약 7,000명 규모다**(결과 5). 이 PC에서 실패 없이 버텼지만, run 때문에 다른 화면 응답이 단독 때보다 4~9배 느려지기 시작했다. 먼저 막히는 곳은 판정 상한(시간당 러닝 약 1.2만 회)이라, 저녁 피크에 러닝이 몰리면 동시 사용자 1만 명 근처부터 기록 결과가 밀린다.

## 권고

| 순서 | 할 일 | 이유 |
| --- | --- | --- |
| 1 | run 분리를 계획대로 진행한다 | 간섭의 절반(커넥션 풀 · 서버 자원)이 풀린다 |
| 2 | 판정 워커가 여러 인스턴스에서 나눠 돌게 한다 | `@SchedulerLock`을 빼고, 대기 세션을 `FOR UPDATE SKIP LOCKED`로 집어 오게 한다(`process()`는 이미 SKIP LOCKED로 세션을 잡는다). 그래야 run 인스턴스를 늘린 만큼 판정이 빨라진다 |
| 3 | run DB 분리(MSA 문서 2.3 · 개발 정책 11.3 5단계)를 "필요할 때"가 아니라 run 서버 이전과 함께 한다 | 같은 DB면 WAL 경합이 남아 core의 쓰기가 느려진다. 또는 업로드 묶음(최대 500점)을 한 행으로 저장해 행 수와 WAL을 줄인다 |
| 4 | 코스 상세의 조회 수 쓰기를 모아서 반영한다(개발 정책 12장 메모) | 조회 화면에 쓰기가 있어 WAL 경합을 그대로 받는다 |

## 측정 환경

| 항목 | 값 |
| --- | --- |
| 서버 | 모놀리스 jar 1개, JDK 21, `-Xmx2g`, Hikari 기본 풀 10개. Windows 11 개발 PC(12코어)에서 실행 |
| DB | Docker의 `postgis/postgis:17-3.5`(포트 5434, `pg_stat_statements` 켬). 개발용 DB(5433)와 분리 |
| 부하 | k6 1.0.0(Docker). 서버와 같은 PC |
| 데이터 | 회원 300 · 사용자 지정 코스 300 · 러닝 기록 1,500(코스 900건 모두 완주 판정, 자유 30분 600건) · GPS 원본 약 900만 행(3GB) · 리뷰 300 |

**절대값은 운영 서버와 다르다.** 같은 PC에서 부하 발생기와 DB를 함께 돌렸다. 모듈 사이의 **비율과 간섭 여부**만 판단 근거로 쓴다.

## 방법

모듈마다 실제 화면 흐름을 한 "여정"으로 만들었다(`loadtest/modules.js`).

| 모듈 | 여정 | 1시간 가중치(가정) |
| --- | --- | --- |
| course | 지도 · 목록(인기순) · 현재 러너 수 · 지역 묶음(30%) · 코스 상세 · 저장 코스(20%) | 6 |
| notification | 안 읽은 알림 수 · 알림 목록(30%) | 4 |
| ranking | 코스 랭킹 · 랭킹 엔트리 · 누적 거리 · 지역 주간 | 2 |
| review | 리뷰 요약 · 목록 · 내 리뷰(30%) | 2 |
| member | 내 정보 · 다른 러너 프로필 · 닉네임 검색(30%) | 2 |
| run | 러닝 1회: 코스 러닝(준비 · 시작 신호 · 구간 종료) 50% 또는 자유 러닝 30분 50%, 원본 500개씩 업로드, 상태 · 기록 목록 | 1 |

- 가중치는 정책 문서의 화면 흐름(홈 진입마다 지도 · 목록, 현재 러너 수 1분 갱신, 앱 열 때마다 알림 수)을 보고 정한 가정이다. 고스트 · 코스 등록 · 사진은 넣지 않았다.
- **단독 측정**: 한 모듈의 여정만 60초 동안 일정한 속도로 보낸다. 서버 프로세스 CPU 증가량(유휴 기준선 0.8코어·초를 뺀 값)과 `pg_stat_statements`의 스키마별 실행 시간으로 여정당 비용을 낸다. run은 업로드한 기록의 백그라운드 판정이 끝날 때까지 잰다.
- **간섭 측정**: 대상 모듈에 과부하를 거는 동안, 초당 5번 모든 모듈의 가벼운 조회(탐침)를 보내 응답 시간을 기준선과 비교한다.
- **분리 실험**: 같은 DB를 쓰는 서버를 하나 더(8091) 띄워 run 요청만 그쪽으로 보낸다. MSA 분리 3단계(run 서비스, DB는 같음)와 같은 상태다.

## 결과

### 1. 여정당 비용 (단독 측정)

| 모듈 | 요청/여정 | CPU/여정 | DB/여정 | p95 | 가중 CPU 비중 | 가중 DB 비중 |
| --- | --- | --- | --- | --- | --- | --- |
| course | 4.5 | 16.1ms | 1.05ms | 23.7ms | 40.2% | 9.9% |
| **run** | 8.4 | **90.9ms** | **53.2ms** | 39.9ms | **37.8%** | **83.8%** |
| ranking | 4.0 | 10.8ms | 1.02ms | 15.2ms | 9.0% | 3.2% |
| member | 2.3 | 5.5ms | 0.39ms | 14.8ms | 4.6% | 1.2% |
| review | 2.3 | 5.2ms | 0.29ms | 14.5ms | 4.3% | 0.9% |
| notification | 1.3 | 2.5ms | 0.14ms | 18.0ms | 4.1% | 0.9% |

- 섞어서 돌린 측정(초당 34여정 = run 초당 2회, 90초)에서도 DB 실행 시간의 **88.2%가 run**이었다. 이때 다른 모듈의 p95는 단독 때보다 4~9배 높았다(member 74ms, notification 159ms).
- run 비용은 대부분 GPS 원본 저장(`run.inputs` INSERT)과 판정이다. course 쪽 DB 시간에는 run 이벤트 수신(도전 수 · 완주 수)도 들어 있다.

### 2. 간섭 (과부하 중 다른 모듈 탐침 p95, ms)

| 모듈 | 기준선 | run 과부하 (초당 10세션) | course 과부하 (초당 260요청) | ranking 과부하 (초당 240요청) |
| --- | --- | --- | --- | --- |
| member | 19.5 | 23.0 ~ 47.6 | 6.2 | 4.0 |
| course 상세 | 37.6 | 107 ~ 194 | — | 18.8 |
| ranking | 9.7 | 26 ~ 115 | 11.5 | — |
| review | 4.7 | 19 ~ 57 | 5.5 | 3.5 |
| notification | 5.7 | 16 ~ 55 | 7.8 | 3.7 |

- run 과부하는 요청 수로는 초당 85개로 가장 적은데 피해가 가장 크다. 범위는 두 번 측정한 값(처음 · 워밍업 뒤)이다.
- run 과부하 중에는 커넥션 풀 대기(최대 7)가 보였고, DB 서버 CPU는 약 1코어로 여유가 있었다.

### 3. 분리 실험 (run 과부하 중 탐침 p95, ms, 둘 다 워밍업 뒤)

| 모듈 | 기준선 | 모놀리스 | run 분리 (같은 DB) |
| --- | --- | --- | --- |
| member | 19.5 | 23.0 (최대 614) | 17.3 (최대 27) |
| ranking | 9.7 | 26.2 | 12.7 |
| review | 4.7 | 19.3 | 6.5 |
| notification | 5.7 | 15.5 | 6.4 |
| **course 상세** | 37.6 | 107.2 | **103.2** |

- 읽기만 하는 요청은 분리로 기준선에 돌아왔다. 커넥션 풀과 서버 자원을 나눠 쓰지 않게 됐기 때문이다.
- 코스 상세는 그대로다. 같은 시간 DB의 대기를 샘플링하면 거의 모두 `COMMIT`의 WAL 대기였다(`LWLock:WALWrite` 53회, `IO:WalSync` 18회 / 25초). 코스 상세는 조회 수를 쓰므로 커밋이 run의 대량 INSERT가 만든 WAL 뒤에 줄을 선다. DB를 나눠야 풀린다.

### 4. 판정 처리량

- 업로드된 기록은 `RunProcessingWorker`가 2초마다 10건씩 차례로 판정한다. 시드 1,500건과 과부하 600건 모두 **초당 약 3.4건**으로 처리됐다.
- `@SchedulerLock(name="freeRunProcessing")` 때문에 인스턴스를 늘려도 한 대만 돈다. 초당 10세션을 1분 넣으면 다 판정하는 데 1분 30초가 더 걸렸다(기록 결과 화면이 그만큼 늦게 뜬다).

### 5. 동시 사용자로 환산

가중치는 "앱을 쓰고 있는 사용자 1명이 1시간에 하는 여정 수"이고 합계는 17이다. 그래서 **동시 사용자 = 초당 여정 수 × 3600 ÷ 17**로 환산한다.

| 테스트 | 부하 | 환산 | 결과 |
| --- | --- | --- | --- |
| **섞어서 (mix)** | 초당 34여정 (run 초당 2회) | **동시 사용자 약 7,200명** | 실패 0건, 다른 모듈 p95 60~160ms |
| course 단독 | 초당 10여정 | course 화면 기준 약 6,000명 몫 | p95 24ms |
| course 과부하 | 초당 60여정 | course 화면 기준 약 36,000명 몫 | 다른 모듈 영향 없음 |
| run 단독 | 초당 2회 | 시간당 러닝 7,200회 | p95 40ms |
| run 과부하 | 초당 10회 | 시간당 러닝 36,000회 | 다른 모듈 2~12배 느려짐 |
| **판정 상한** | 초당 약 3.4건 | **시간당 러닝 약 12,000회** | 인스턴스를 늘려도 그대로 |

- 러닝 중에는 앱이 서버와 통신하지 않는다(개발 정책 1.6). mix는 러닝 완료 초당 2회, 평균 러닝 약 23분이라, 화면을 보는 사용자와 별도로 **약 2,800명이 달리고 있는 상태**에 해당한다.
- k6의 가상 사용자 수(VU)는 실제 사용자 수가 아니어서 환산에 쓰지 않았다. 부하는 도착 속도(초당 여정 수)로 걸었다.

## 한계

- 개발 PC 한 대에서 서버 · DB · 부하 발생기를 함께 돌렸다. 운영 서버의 디스크(WAL 쓰기 속도)가 다르면 간섭의 크기도 달라진다.
- 가중치는 가정이다. 실제 사용 비율은 운영 지표(개발 정책 8.1 모듈 태그)로 다시 확인한다.
  - 특히 "사용자 1명이 1시간에 한 번 달린다"는 높게 잡은 값이다. 구경만 하는 사용자가 더 많으면 run 부하가 줄어, 같은 서버로 결과 5의 환산보다 많은 사용자를 받는다.
  - 결과 5의 동시 사용자 수는 이 가중치를 그대로 따른다. 가중치를 고치면 환산도 다시 한다.
- Windows에서 JFR 샘플이 너무 적게 잡혀서(분당 100개 안팎), 모듈별 CPU는 모듈을 하나씩 돌린 프로세스 CPU 증가량으로 계산했다. 한 여정이 다른 모듈을 부르는 비용(예: 코스 상세 → `MemberApi`)은 부른 쪽에 들어 있다.

## 다시 재기

DB · 서버 · 시드는 [`loadtest/README.md`](../loadtest/README.md) 1~2번을 따른다. 이 문서의 결과 1~4(모듈 단위)는 `modules.js`로 잰다. JFR 스택이 잘리지 않게 서버에 `-XX:FlightRecorderOptions:stackdepth=1024`를 더한다.

```bash
# loadtest/에서. 토큰 · 코스 목록 저장(1시간 유효)
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W):/lt" -w /lt -e SAVE=1 -e MODULE=idle -e DURATION=1s grafana/k6:1.0.0 run modules.js
```

```bash
# 한 번 측정(CPU · DB 시간까지). 결과는 loadtest/results/
./run.sh iso-run -e MODULE=run -e RATE=2 -e DURATION=60s
```

- `MODULE`: 모듈 하나 또는 `mix`(가중치대로), `idle`(기준선). `PROBE=1`: 간섭 탐침. `RUN_BASE=http://host.docker.internal:8091`: run 요청만 다른 인스턴스로(분리 실험).

## 다음 측정 (여정 단위)

모듈이 아니라 여정(사용자 흐름)별로 부하를 단계적으로 올려, 어디서 느려지는지와 run 분리로 한계가 얼마나 올라가는지를 잰다. 가정은 러닝 하루 1회, 코스 등록 하루 한도 4개(사용자 지정 1 + GPS 3)다. 여정 · 판단 기준 · 실행 순서는 [`loadtest/README.md`](../loadtest/README.md)에 있다.

- 2026-11-14 개발 PC(i7-8700 · 메모리 16GB, 여유 1~2GB)에서 시작했다가 멈췄다. 높은 부하 단계에서 PC가 한계가 될 수 있어 사양이 더 좋은 PC에서 처음부터 다시 잰다.
- 그때까지 나온 값은 홈 탐색 여정뿐이다: 초당 80회(초당 640요청)까지 p95 5ms, 초당 160회에서 90ms.
