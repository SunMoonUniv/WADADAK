# MSA 이후 부하 테스트

상태: 측정 · 작성일 2026-11-24 · 기준: main `c702c4f`(운영 이미지. BackEnd는 지금 main과 같다)

> **문서 목적**: run을 떼고 DB까지 나눈 뒤(core · run 2개 서비스), 같은 여정 부하를 운영 서버 PC에 다시 걸어 [이전 측정](모듈%20부하%20테스트%20-%202026-11-14.md)(결과 6~8, 모놀리스)과 비교한다.

## 결론

1. **core · run의 응답은 이번에 건 부하 끝까지 한계에 닿지 않았다.**
   - 하루 흐름 초당 15명에서 전체 p95가 96ms다. 이전에는 모놀리스 1,096ms, 분리 실험(같은 DB) 960ms였다.
   - 조회 여정(홈 · 코스 상세 · 랭킹 · MY)은 초당 160회까지 p95 5~7ms다. 이전에는 이 단계에서 코스 상세가 1,266ms였다.
2. **먼저 막히는 곳은 여전히 판정이다.**
   - 판정은 초당 약 4.1건으로 이전(2.8건)보다 빨라졌다. 그래도 판정 밀림은 이전과 같이 초당 6명부터 시작한다. 대기 시간만 줄었다(러닝 여정 초당 6세션 40초 → 18초, 16세션 169초 → 116초).
   - 원인은 워커 구조다. `RunProcessingWorker`는 2초마다 10건씩, 클러스터에서 한 대만 판정한다. 처리 시간이 0이어도 초당 5건을 넘지 못한다. 이때 run PC CPU는 18%였다.
3. **감당 가능한 DAU는 약 9.6만~14.4만 명이다**(판정이 밀리지 않는 초당 4명 기준, 이전 7.2만~10.8만). 응답만 보면 초당 15명(36만~54만 명)까지 여유가 있다.
4. **조회 초당 320회(초당 약 1,900~2,600요청)에서 처음 보이는 병목은 core의 DB 커넥션 풀이다.**
   - 코스 상세는 core CPU가 44%인데 풀 대기가 최대 185였다.
   - 지금 규모에서는 손볼 필요가 없다.
5. **코스 등록 · 러닝의 바닥값이 약 200 · 110ms에서 20 · 28ms로 내려갔다.**
   - 등록 코드(`RegistrationService` 등)는 이전 측정 때와 같다. 차이는 측정 환경(이전에는 서버를 Windows에서 직접 돌림)에서 온 것으로 보고, 원인은 확인하지 않았다.
   - 이 두 여정은 절대값보다 단계별 변화로 비교한다.

## 측정 환경

| 항목 | 이전 (2026-11-14, 결과 6~8) | 이번 |
| --- | --- | --- |
| 서버 | 모놀리스 jar 1개, `-Xmx2g`, Windows 개발 PC에서 직접 실행 | 운영 이미지 core · run 컨테이너. 각각 core PC · run PC(i7-8700 12스레드, Docker VM 7.67GB). JVM 기본 힙, Hikari 기본 풀 10개 |
| DB | 같은 PC의 PostGIS 하나 | core DB(PostGIS 17-3.5)는 core PC, run DB(PostgreSQL 17)는 run PC |
| 이벤트 | 서버 안 | RabbitMQ 4.1(인프라 PC, 부하용 5673) |
| 부하 | k6 1.0.0, 서버와 같은 PC | k6 1.0.0, 이전 측정과 같은 개발 PC. Tailscale로 서버 PC에 바로 건다(게이트웨이를 거치지 않는다) |
| 데이터 | 회원 600 · 코스 600 · 기록 3,000 · 리뷰 600 | 같다 |

- 측정하는 동안 운영 core · run을 멈추고 같은 PC에 부하용 스택(빈 DB, 가짜 로그인)을 띄웠다. 운영 DB는 건드리지 않았다.
- 여정 · 단계(40초) · 판단 기준은 이전 측정과 같다([`loadtest/README.md`](../loadtest/README.md)). `PC CPU`는 core PC/run PC 순서이고, 서버 JVM이 보는 Docker VM 전체(DB 포함)다. `풀 대기`는 core의 DB 커넥션 풀을 기다린 스레드 수의 최댓값이다.

감당 가능한 DAU = 속도(초당 명) × 3,600 ÷ 피크 비중(15~10%). 근거는 [`loadtest/README.md`](../loadtest/README.md).

| 기준 | 이번 속도 | 이번 DAU | 이전 속도 | 이전 DAU |
| --- | --- | --- | --- | --- |
| **피크 내내 판정이 밀리지 않음** | 초당 4명 | **약 9.6만 ~ 14.4만 명** | 초당 3명 | 약 7.2만 ~ 10.8만 명 |
| 응답 한계(p95 1초) 직전 | 초당 15명 이상(잰 범위 끝, p95 96ms) | 36만 ~ 54만 명 이상 | 초당 12명 | 약 28.8만 ~ 43.2만 명 |

- 판정 워커가 지금 구조면 처리 시간을 줄여도 초당 5명(약 12만 ~ 18만 명)이 끝이다. 권고 1을 하면 첫 줄의 기준이 응답 쪽으로 넘어간다.

## 한계

- 부하 발생기는 개발 PC 한 대다. 조회 초당 640회에서 이 PC의 Docker가 멈춰 320회까지만 쟀다. 홈 초당 320회(누락 182)와 하루 흐름 초당 15명은 이 PC가 먼저 막혔을 수 있다. 이 PC의 CPU는 재지 않았다.
- 게이트웨이(인프라 PC)와 터널(cloudflared)을 거치지 않았다. 실제 요청은 그만큼 더 걸린다.
- 코스 상세의 초당 10~40회 단계는 실수로 러닝 여정(초당 3~16세션)과 겹쳤다. 앞서 멈춘 측정 스크립트가 남아서 돌았다. 겹친 단계의 p95는 8~11ms로 바닥값 수준이라, run 부하가 core 조회에 번지지 않는다는 것은 그대로 보인다. 같은 일로 러닝 여정을 두 번 잰 셈인데, 두 번의 값이 같았다(p95 27~31ms, 초당 16세션 판정 대기 116초).
- 홈 탐색은 커넥션 풀 대기를 재기 전에 쟀다.
- 실패(등록 초당 15회 0.09%, 하루 흐름 초당 15명 0.02%)의 원인은 확인하지 못했다. 부하용 스택을 지울 때 로그도 함께 지웠다.
- 단계 길이(40초)와 하루 흐름 가정(러닝 하루 1회, 코스 등록 하루 4개)은 이전 측정과 같아서, 이전 문서의 한계가 그대로 적용된다.
