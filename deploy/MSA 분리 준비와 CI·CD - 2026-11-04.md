# MSA 분리 준비와 CI·CD

상태: 설계 · 작성일 2026-11-04 · 기준: main `5f0f83d`

> **문서 목적**: run을 첫 서비스로 떼어낼 때 서비스 구성, 전환 배포, CI/CD를 어떻게 바꾸는지 정한다.
> 분리 시점(기능 완성 뒤, 프로젝트 목표)과 그 뒤의 분리 기준은 [`개발 정책 v3`](../개발%20정책%20v3.md) 1.6·11.1을 따르고, 이 문서는 **어떻게**만 다룬다. 규칙의 근거는 개발 정책 1·4·5·8·11장이다.

## 1. 현재 준비도 (run 대상, 개발 정책 11.2)

| 항목 | 상태 | 근거 |
| --- | --- | --- |
| 스키마 경계 SQL·FK 0개 | 충족 | 마이그레이션·네이티브 SQL 전수 확인. 다른 스키마 이름은 주석에만 나온다 |
| 공개 루트 타입만 사용 | 충족 | run → `CourseApi`·`RankingApi`, course·ranking·review → `MemberApi`. 순환 없음. notification은 동기 호출 없음 |
| 단독 기동 | 충족 | `ModularityTests.verify()`, 모듈별 `@ApplicationModuleTest` |
| 이벤트 | 충족 | 이벤트 record 16종이 `event` 모듈에 있고, 리스너는 모두 `@ApplicationModuleListener` + 멱등 처리(5.4) |
| 인증 | 충족 | JWT RS256. 개인키는 member만, 나머지는 공개키로 검증한다 |
| URL prefix | 충족 | 모듈별 prefix라 게이트웨이가 경로로 나눌 수 있다 |
| 동기 호출 규칙(4.4) | 충족 | run의 `CourseApi`·`RankingApi` 호출(`CourseRunService.prepare()`·`OwnGhostCandidates.list()`·`GhostStartService`·`PublicGhostService.prepare()`)은 모두 트랜잭션 밖(`Propagation.NOT_SUPPORTED`)에서 하고, 잠금은 그 뒤 별도 트랜잭션에서 잡는다. 모두 사용자 요청 안이고, 스케줄 작업·리스너에는 서비스 사이 호출이 없다 |

## 2. 서비스 구성

| 서비스 | 모듈 | 이유 |
| --- | --- | --- |
| core | member · course · ranking · review · notification | course·ranking·review가 모두 `MemberApi`를 동기 호출한다. notification은 이벤트만 받아 나중에 떼기 쉽지만, 지금은 core에 둔다 |
| run | run | GPS 업로드·완주 판정·고스트. 부하·장애 격리 대상(개발 정책 1.6) |

### 2.1 서비스 사이 동기 호출 (run → core, `/internal/v1/...`)

| 호출 | 시점 |
| --- | --- |
| `CourseApi.getRouteForRun` | 코스 러닝 준비, 고스트 준비·시작 |
| `RankingApi.findPublicGhostCandidate` | 공개 고스트 준비·시작 |

- GPS 업로드 경로에는 동기 호출이 없다. 분리 효과가 큰 이유다.
- 기록의 GPS 끊긴 구간 판단(`GpsGapWorker`)은 서비스 사이 호출이 아니다. course의 계산 규칙 `GpsGapRule`이 계약 jar `course-api`에 있어 run이 직접 계산한다(개발 정책 4.3).
- **인증**: 두 호출 모두 사용자 요청 안에서 일어난다. run의 HTTP 구현체가 요청의 `Authorization: Bearer` 토큰을 그대로 넘기고, core의 내부 API는 다른 API와 같은 JWT 검증을 받는다. 보안 설정을 따로 두지 않는다(개발 정책 11.3 2단계).
- **오류·시간 제한**: core의 오류 응답은 같은 `AppException`(`CourseErrorCode`·`RankingErrorCode`)으로 되돌리고, `findPublicGhostCandidate`의 404는 빈 `Optional`로 바꾼다. 시간 제한은 `HttpTimeouts`를 쓴다.
- core → run 동기 호출은 없다.

### 2.2 서비스 사이 이벤트

| 방향 | 이벤트 |
| --- | --- |
| run → core | `CourseRunStartedEvent`, `RunSessionEndedEvent`, `RunRecordDeletedEvent`, `CourseActiveRunnersChangedEvent`, `GpsSourceLinkedEvent`, `GpsSourceUnlinkedEvent`, `CourseRunTrackEvent` |
| core → run | `MemberWithdrawnEvent`, `MemberVisibilityChangedEvent`, `CourseStatusChangedEvent`, `GpsCourseRegisteredEvent` |

### 2.3 서버 배치 (물리 서버 2대)

| 서버 | 띄우는 것 |
| --- | --- |
| core 서버 (지금 공용 서버 PC) | core, PostgreSQL, RabbitMQ, RustFS(사진), Caddy 게이트웨이, cloudflared |
| run 서버 (새 PC) | run |

- 두 서버는 Tailscale 사설망으로 잇는다(무료, 포트 개방 없음). run은 이 망으로 core의 `/internal` API, PostgreSQL, RabbitMQ에 붙는다. 공개 터널로 잇지 않는다.
- 진입점은 core 서버 하나다. 터널과 Caddy가 core 서버에 있고, Caddy가 `/api/v1/runs/*`를 run 서버의 사설 주소로 보낸다. 앱 주소는 그대로다.
- DB는 처음에 core 서버 하나로 둔다(개발 정책 11.3 3단계: 같은 DB의 `run` 스키마). GPS 쓰기 부하가 core 서버 DB를 누르면 `run` 스키마를 run 서버의 PostgreSQL로 옮긴다(11.3 5단계).
- 두 서버는 같은 LAN에 둔다. 서로 다른 네트워크에 두면 run의 DB 왕복마다 사설망 지연이 붙어 GPS 업로드가 느려진다. 그렇게 둘 수밖에 없으면 run 컨테이너를 옮길 때 `run` 스키마도 함께 run 서버로 옮긴다. run은 PostGIS를 쓰지 않으므로 run 서버의 PostgreSQL에는 PostGIS가 필요 없다.
- core 서버가 꺼지면 run API도 막힌다(게이트웨이·DB가 core 서버에 있다). run 서버가 꺼지면 run API만 막히고 나머지는 동작한다.
- 옮기는 순서: 먼저 같은 PC에서 분리(7장)하고, 그다음 run 컨테이너를 run 서버로 옮긴다(8장). 분리와 네트워크 변경을 한 번에 하지 않는다.

## 3. Gradle 구조

```
BackEnd/
├── settings.gradle
├── libs/
│   ├── common-core/ common-region/ common-storage/   # 개발 정책 3.3
│   ├── event/
│   ├── course-api/     # CourseApi · CourseRouteSnapshot · GpsGapRule · GpsGapCheck · CourseErrorCode + HTTP 구현체
│   └── ranking-api/    # RankingApi · GhostCandidate · RankingPeriod · RankingErrorCode + HTTP 구현체
└── services/
    ├── core/           # member · course · ranking · review · notification
    └── run/
```

- run은 `common-core`·`event`만으로 빌드되지 않는다. course·ranking 모듈 루트의 공개 타입을 import하기 때문이다. 그래서 계약 jar `course-api`·`ranking-api`를 둔다.
- 패키지 이름은 바꾸지 않는다(개발 정책 3.3과 같다). 나눈 뒤 core에서 `ApplicationModules`를 출력해, jar로 옮긴 모듈 루트 타입이 course·ranking 모듈로 인식되는지 확인한다.
- HTTP 구현체(`@HttpExchange`)도 계약 jar에 둔다. core 테스트가 자기 `/internal` 컨트롤러를 이 구현체로 호출하므로, 계약이 깨지면 core를 바꾼 PR에서 바로 실패한다.
- run 쪽 HTTP 구현체는 지금 스텁과 같은 `@ConditionalOnProperty` 자리에 들어간다(개발 정책 3.2).

## 4. 이벤트 브로커

- **RabbitMQ**(`spring-modulith-events-amqp`). 서버 PC 1~2대 운영에는 Kafka보다 가볍다. 리스너가 이미 중복·순서 바뀜에 안전해서(개발 정책 5.4) 파티션 순서 보장이 필요 없다.
- 외부화 대상은 `EventExternalizationConfiguration` 빈으로 고른다. 레코드에 `@Externalized`를 붙이지 않으므로 `event` jar가 Modulith에 의존하지 않는다.
- exchange는 `wadadak.{발행 모듈}`(topic), 라우팅 키는 **이벤트 타입 이름**(`CourseStatusChangedEvent`)이다. 개발 정책 5.6의 키(ID)는 라우팅 키로 쓰지 않는다. ID로는 바인딩할 수 없어 큐가 모든 이벤트를 받게 된다.
- 큐는 서비스마다 하나(`wadadak.run-service`, `wadadak.core-service`)이고, 2.2의 받는 이벤트만 바인딩한다. run 큐는 `wadadak.member`의 `MemberWithdrawnEvent`·`MemberVisibilityChangedEvent`, `wadadak.course`의 `CourseStatusChangedEvent`·`GpsCourseRegisteredEvent` 4개다.
- **서비스마다 자기 모듈이 발행한 이벤트만 외부화한다.** 받은 이벤트까지 고르면 다시 발행하는 순간 브로커로 되돌아가 끝없이 돈다.
- 수신은 서비스마다 큐를 두고, 받은 record를 트랜잭션 안에서 `ApplicationEventPublisher`로 다시 발행하는 얇은 리스너로 한다. 기존 `@ApplicationModuleListener`가 그대로 처리하고, 실패하면 그 서비스의 아웃박스에서 재시도된다. 비즈니스 코드는 바뀌지 않는다.
- **얇은 리스너의 실패는 아웃박스가 지키지 못한다.** 커밋 전까지 메시지는 큐에만 있다. 브로커 설정으로 지킨다(개발 정책 5.7).
  - 재시도에 간격을 둔다: `spring.rabbitmq.listener.simple.retry.enabled: true`, 지수 백오프(최대 1분 간격, 10회). 기본값은 예외가 나면 바로 다시 전달해 DB가 내려가 있는 동안 끝없이 돈다.
  - `spring.rabbitmq.listener.simple.default-requeue-rejected: false`로 두고 큐마다 DLQ(`wadadak.run-service.dlq`, `wadadak.core-service.dlq`)를 둔다. 재시도를 다 쓴 메시지와 역직렬화에 실패한 메시지가 버려지지 않고 남는다.
  - DLQ에 메시지가 있으면 이벤트 지연과 같은 채널로 알린다. 원인을 고친 뒤 원래 큐로 되돌린다.
- **새 이벤트는 받는 쪽을 먼저 배포한다.** 바인딩 전에 발행된 메시지는 사라진다. 배포 순서가 core → run(8.1)이므로, run이 받는 이벤트를 새로 만들 때는 PR을 둘로 나눈다: run의 리스너·바인딩 먼저, core의 발행은 다음 PR.
- traceId가 브로커를 넘어 이어지게 `spring.rabbitmq.template.observation-enabled`·`spring.rabbitmq.listener.simple.observation-enabled`를 켠다.

## 5. 전환 배포 (한 번)

1. **큐와 run 인프라 테이블을 미리 만든다.** 외부화 배포(개발 정책 11.3 1단계) 때 run 큐를 선언해 둔다. 전환 순간 발행된 이벤트도 큐에 남아 유실되지 않는다.
   - 같은 배포에서 `run.event_publication`·`run.shedlock`을 만든다(모놀리스의 `db/migration/run/`). run 서비스는 `ddl-auto: validate`라 이 테이블이 없으면 뜨지 않고, 전환 배포에는 마이그레이션을 넣지 않는다(4번).
   - 모놀리스가 이미 처리한 이벤트도 큐에 쌓인다. 같은 run 스키마의 멱등 기록(`processed_event`·유니크·`source_version`)이 걸러낸다.
   - 1단계와 전환 사이가 길면 큐가 커지고 처리만 오래 걸린다. 두 배포 사이를 짧게 둔다.
2. **공존 기간을 두지 않는다.** core의 run 의존 제거, run 서비스 투입, 게이트웨이 라우팅을 PR 하나·배포 하나로 한다.
   - core 안의 run 모듈과 run 서비스가 함께 켜지면 ShedLock 테이블이 달라(`common.shedlock` / `run.shedlock`) run 스케줄 작업 4개(`freeRunProcessing`·`courseRunRelease`·`gpsGapBackfill`·`run.gps-source-link`)가 두 번 돈다.
3. **남은 아웃박스 행을 지운다.** 전환 뒤 `common.event_publication`에 남은 run 리스너 행은 core에 그 리스너가 없어 영원히 미완료로 남고, 10분 지연 알림(개발 정책 5.5)을 울린다. 같은 이벤트는 큐로 run 서비스에 전달됐으므로 지운다.
4. **전환 배포에 마이그레이션을 넣지 않는다.** 되돌리기는 revert 머지 한 번(자동 재배포)으로 끝나야 한다.
5. run 서비스의 Flyway 이력·아웃박스·ShedLock은 `run` 스키마에 둔다. 아웃박스·ShedLock 테이블은 1번에서 만들어 둔 것을 쓰고, Flyway는 그 시점 버전으로 baseline한다(이력 테이블만 생긴다, 개발 정책 11.3).

## 6. CI (`backend.yml`)

- **잡은 `./gradlew test` 하나로 유지한다.** 필수 체크 이름이 그대로라 브랜치 보호 설정을 바꾸지 않는다. `changes` 잡의 경로(`BackEnd`·`deploy`·`run/fixtures`)도 그대로다.
- `BackEnd/gradle.properties`에 `org.gradle.caching=true`를 둔다.
  - 안 바뀐 서브프로젝트의 테스트는 캐시에서 복원된다. `setup-gradle`이 main에서 저장한 캐시를 PR이 읽는다.
  - 의존 관계에 따라 자동으로 갈린다. `libs/event`가 바뀌면 두 서비스 모두, `services/run`만 바뀌면 run만 테스트한다.
- 서비스별 잡과 matrix로 쪼개는 건 테스트 시간이 부담될 때 한다. 그때 필수 체크는 결과를 모으는 잡 하나로 둔다.

## 7. CD — 1단계: 같은 PC에서 분리

전환(5장)은 지금 서버 PC 한 대에서 먼저 한다. 네트워크 변수 없이 분리만 검증한다.

### 7.1 이미지

Dockerfile을 서비스마다 둔다. 각 Dockerfile은 그 서비스와 `libs`만 COPY한다. core 코드가 바뀌어도 run 이미지의 레이어 캐시는 그대로라 같은 이미지가 나오고, compose가 run 컨테이너를 다시 띄우지 않는다. 지금 deploy 작업의 "BackEnd가 그대로면 같은 이미지" 원리를 서비스 단위로 넓힌 것이다.

```dockerfile
# services/run/Dockerfile (빌드 컨텍스트 = BackEnd)
COPY gradlew settings.gradle build.gradle ./
COPY gradle gradle
COPY libs libs
COPY services/run services/run
# settings.gradle에 include된 프로젝트 폴더가 없으면 Gradle이 실패한다. core는 build.gradle만 넣는다
COPY services/core/build.gradle services/core/
RUN --mount=type=cache,target=/root/.gradle ./gradlew --no-daemon :services:run:bootJar
```

```yaml
# backend.yml deploy 작업
- run: docker build --provenance=false -f BackEnd/services/core/Dockerfile -t wadadak-core BackEnd
- run: docker build --provenance=false -f BackEnd/services/run/Dockerfile  -t wadadak-run  BackEnd
- run: docker compose -f deploy/compose.yaml up -d --wait --wait-timeout 300 --remove-orphans
```

### 7.2 compose

- `backend`를 `core`로 바꾸고 `run`, `rabbitmq`, `gateway`를 추가한다.
- Cloudflare 터널의 Service URL을 `http://gateway:8080`으로 바꾼다(대시보드에서 한 번).
- 로컬 개발도 같은 compose 구성으로 띄운다. 앱의 `API_BASE_URL`은 하나 그대로다.

```
# deploy/Caddyfile
{
    servers {
        # 같은 Docker 망의 cloudflared가 넘긴 X-Forwarded-*를 믿는다.
        # 없으면 X-Forwarded-Proto가 http로 덮여 서버가 https 주소를 만들지 못한다.
        trusted_proxies static private_ranges
    }
}

# 주소에 도메인을 쓰지 않는다. 도메인을 쓰면 Caddy가 인증서를 받으려다 실패한다(HTTPS는 터널이 처리).
:8080 {
    handle /internal/* {
        respond 404          # 서비스 사이 API는 밖에 열지 않는다
    }
    @run path /api/v1/runs /api/v1/runs/*
    handle @run {
        reverse_proxy run:8080
    }
    handle {
        reverse_proxy core:8080
    }
}
```

라우팅을 Cloudflare 경로 규칙이 아니라 게이트웨이에 두는 이유:
- 라우팅 설정이 git에 남는다.
- 로컬 개발도 같은 구성으로 띄울 수 있다.
- `/internal` 차단이 저장소 안에 있다.

### 7.3 게이트웨이 선택: Caddy

게이트웨이가 하는 일은 경로 라우팅과 `/internal` 차단뿐이다. HTTPS는 Cloudflare 터널이, 인증은 각 서비스가 JWT 공개키로 처리한다.

| 후보 | 판단 |
| --- | --- |
| **Caddy (선택)** | 설정이 가장 짧다. 연결할 때마다 upstream 주소를 다시 찾아 컨테이너 IP가 바뀌어도 따라간다. 요청 본문 크기·응답 대기에 기본 제한이 없어 GPS 기록 업로드에 따로 손댈 것이 없다 |
| nginx | 가장 익숙하지만 우리 조건에서 챙길 설정이 많다. 시작 때 찾은 IP를 계속 써서 `resolver`가 없으면 run 컨테이너가 다시 뜬 뒤 502가 난다. 요청 본문이 기본 1MB로 제한돼 `client_max_body_size`를 늘려야 하고, 응답 대기는 기본 60초다 |
| Traefik | 컨테이너 라벨 자동 등록이 강점이지만 같은 PC의 Docker만 본다. 서버 2대가 되면 run을 파일로 적어야 해 강점이 사라지고, Docker 소켓을 넘겨야 한다(호스트 관리자 권한을 주는 것과 같다) |
| Spring Cloud Gateway | 게이트웨이에서 Java 로직(사용자별 요청 제한, 응답 묶기)이 필요 없어 JVM을 하나 더 띄울 이유가 없다 |

Caddy를 쓸 때 지킬 것은 두 가지이고, 둘 다 위 Caddyfile에 있다.
- 주소는 `:8080`처럼 포트로만 쓴다. 자동 HTTPS가 꺼진다.
- `trusted_proxies`를 둔다.

### 7.4 비밀값

- `RUN_DB_PASSWORD`: `run` 스키마 권한만 가진 계정. 경계를 어긴 코드가 있으면 기동 때 바로 실패한다.
- 브로커 비밀번호를 추가한다.
- **run에는 `JWT_PRIVATE_KEY`를 주지 않는다.** 토큰 발급은 member(core)만 하고, run은 공개키로 검증만 한다.

## 8. CD — 2단계: 서버 2대

run 컨테이너를 core 서버의 compose에서 빼고 run 서버의 compose로 옮긴다. 코드는 바뀌지 않고, 배포 작업의 대상과 Caddy의 run 주소만 바뀐다. 서버 배치는 2.3.

### 8.1 흐름

```
main 머지
 → backend      : ./gradlew test
 → images       : GitHub 러너에서 core·run 이미지 빌드 → GHCR 푸시 (:main + :커밋SHA)
 → deploy-core  : core 서버 러너에서 pull → up --wait
 → deploy-run   : run 서버 러너에서 pull → up --wait   (core 다음)
```

```yaml
  images:
    needs: backend
    if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest            # 빌드를 서버 PC에서 GitHub 러너로 옮긴다
    permissions: { contents: read, packages: write }
    strategy:
      matrix:
        service: [core, run]
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: BackEnd
          file: BackEnd/services/${{ matrix.service }}/Dockerfile
          push: true
          provenance: false
          tags: |
            ghcr.io/sunmoonuniv/wadadak-${{ matrix.service }}:main
            ghcr.io/sunmoonuniv/wadadak-${{ matrix.service }}:${{ github.sha }}
          cache-from: type=gha,scope=${{ matrix.service }}
          cache-to: type=gha,mode=max,scope=${{ matrix.service }}

  deploy-core:
    needs: images
    runs-on: [self-hosted, wadadak-core]
    environment: wadadak-core          # DB 비밀번호 · JWT 개인키
    concurrency: { group: wadadak-core, cancel-in-progress: false }
    permissions: { packages: read }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - run: docker compose -f deploy/core/compose.yaml pull
      - run: docker compose -f deploy/core/compose.yaml up -d --wait --wait-timeout 300 --remove-orphans
        env:
          DB_PASSWORD: ${{ secrets.DB_PASSWORD }}
          JWT_PRIVATE_KEY: ${{ secrets.JWT_PRIVATE_KEY }}
          # ...

  deploy-run:
    needs: deploy-core                 # 제공 쪽(core)을 먼저 배포한다
    runs-on: [self-hosted, wadadak-run]
    environment: wadadak-run           # run DB 계정 · JWT 공개키만. 개인키 없음
    # 단계는 deploy-core와 같고 deploy/run/compose.yaml을 쓴다
```

### 8.2 어느 서버에서 도는지 정하는 곳

| 무엇이 | 정하는 것 | 예 |
| --- | --- | --- |
| Dockerfile | 이미지 안에 무엇이 들어가는지 | `services/run/Dockerfile`이면 run jar만 |
| **러너 라벨** | **잡이 어느 서버에서 실행되는지** | `runs-on: [self-hosted, wadadak-run]` |
| compose 파일 | 그 서버에서 어떤 컨테이너를 띄우는지 | `deploy/run/compose.yaml`에는 run 서비스만 |

- self-hosted 러너는 서버마다 하나씩 설치하고, 설치할 때 라벨을 붙인다. GitHub는 `runs-on`의 라벨을 모두 가진 러너에게만 그 잡을 준다.
- 지금 deploy 작업도 같은 방식이다(`runs-on: [self-hosted, wadadak-server]`, [`README`](README.md) 2번). 라벨은 GitHub의 Settings → Actions → Runners에서 나중에 바꿀 수도 있다.

```bash
# core 서버
.\config.cmd --url https://github.com/SunMoonUniv/WADADAK --token <발급 토큰> --labels wadadak-core
```

```bash
# run 서버
.\config.cmd --url https://github.com/SunMoonUniv/WADADAK --token <발급 토큰> --labels wadadak-run
```

### 8.3 결정

- **바뀐 서비스만 재시작된다.** compose 쪽 이미지는 `:main`을 쓴다. 코드가 그대로면 gha 캐시로 같은 이미지(digest)가 나오고, `pull` 뒤 `up`이 그 컨테이너를 다시 띄우지 않는다. 그래서 변경 감지 스크립트가 필요 없다.
- **SHA 태그는 롤백용이다.** compose의 `image:`를 `...:${TAG:-main}`으로 두면, 수동 실행할 때 `TAG=<커밋SHA>`를 넘겨 이전 이미지로 되돌릴 수 있다.
- **배포는 서버마다 self-hosted 러너를 하나씩 두는 방식으로 한다.** 러너가 GitHub에 바깥으로 연결하므로 지금처럼 포트를 열지 않아도 된다. GitHub 러너에서 SSH로 들어가는 방식은 SSH 포트나 Cloudflare Access 설정이 추가로 필요하다.
- **환경(Secrets)을 서버별로 나눈다.** run 서버는 JWT 개인키와 core DB 비밀번호를 받지 못한다.
- **새 서버 러너에도 지금 서버 PC와 같은 보안 설정을 한다**([`README`](README.md) 보안 1번, 포크 PR 승인). 안 하면 포크 PR이 `runs-on`을 바꿔 머지 전에 서버에서 코드를 돌릴 수 있다.

### 8.4 run 서버 준비

1. Docker를 설치하고, 지금 서버 PC와 같은 방식으로 self-hosted 러너를 `wadadak-run` 라벨로 등록한다([`README`](README.md) 1·2번, 보안 설정 포함).
2. 두 서버에 Tailscale을 설치해 같은 사설망에 넣는다. core 서버의 PostgreSQL·RabbitMQ·core는 사설망 주소로만 연다.
3. GitHub에 환경 `wadadak-run`을 만들고 run 비밀값(run DB 계정 비밀번호, 브로커 비밀번호, JWT 공개키)만 넣는다.
4. compose 파일을 서버별로 나눈다: `deploy/core/compose.yaml`, `deploy/run/compose.yaml`. Caddy의 run 주소를 run 서버의 사설 주소로 바꾼다.
