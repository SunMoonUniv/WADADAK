# 서버 사이 데이터 대조 (core DB · run DB)

기준: main c9f1e14(서버 3대: 인프라 PC · core PC · run PC). 워크플로는 `.github/workflows/reconcile.yml`(5장)이다.

## 1. 결론

- core와 run은 DB를 따로 쓰고 이벤트로 결국 맞춰진다(2장). 이벤트 하나가 끝내 처리되지 않으면 두 DB가 어긋난 채로 남는데, 이를 찾는 장치가 없다.
- 매일 한 번 두 DB에서 같은 기준으로 개수와 md5를 뽑아 비교하는 GitHub Actions 예약 작업을 둔다(5장). 앱 코드와 스키마는 바꾸지 않는다.
- 어긋나면 workflow가 실패해 GitHub가 메일을 보낸다. 고치는 법은 종류마다 4장에 있다. 고치는 기능은 실제로 어긋남이 나온 종류만 그때 만든다.
- 2026-11-23 서버에서 대조 쿼리를 읽기 전용으로 돌려 여섯 가지 모두 일치함을 확인했다. 서버 3대로 나눈 뒤에도 다시 돌려 같았다(7장).

## 2. 지금 맞추는 방식

| 단계 | 하는 일 | 코드 |
| --- | --- | --- |
| 보내기 | 업무 데이터와 같은 트랜잭션에 발행 기록을 남기고(core `common.event_publication`, run `run.event_publication`), 커밋 뒤 RabbitMQ로 보낸다 | Spring Modulith, `EventBrokerConfig` |
| 보내기 재시도 | 1분마다 5분 넘은 미완료 발행을 다시 보낸다. 재시작할 때도 다시 보낸다 | `EventRetryScheduler`, `republish-outstanding-events-on-restart` |
| 받기 | 큐 메시지를 자기 트랜잭션 안에서 다시 발행해 처리기마다 받는 쪽 발행 기록을 만든다. 처리기가 실패하면 그 기록으로 다시 시도한다 | `EventBrokerConfig.BrokerEventRelay` |
| 받기 재시도 | 커밋 전 실패는 브로커가 10번(약 6분) 다시 시도하고 실패 사유를 붙여 DLQ로 보낸다. 운영자 웹 "실패 이벤트"에서 처음 길로 되돌린다 | `application.yml` `listener.simple.retry`, `AdminFailedEvents` |
| 중복 · 순서 | 기록 단위 복사는 기록 ID `ON CONFLICT`, 증감 통계는 `course.processed_events`, 상태 복사는 `source_version`이 클 때만 덮어쓴다 | 각 `*EventHandler` |
| 지연 감시 | 10분 넘게 밀린 발행을 경고 로그로 남긴다. DLQ 메시지 수 · 업무 큐 소비자 수는 run PC Prometheus가 인프라 PC RabbitMQ(15692)에서 읽고, Grafana가 DLQ 잔류 · 소비자 없음을 Discord로 알린다 | `EventMonitor`, `deploy/observability` |

전달은 최소 한 번이다. 남는 구멍은 둘이다. DLQ 알림을 받고도 메시지를 되돌리지 않거나 지워 버리는 경우, 브로커 수신 확인(publisher confirm)이 없어 브로커가 받은 직후 죽는 경우다(`EventBrokerConfig`의 `ponytail:` 주석). 뒤의 것은 알림도 없이 두 DB가 어긋난 채로 남는다.

## 3. 대조 대상

원본(데이터를 처음 만든 쪽)에서 다시 센 값과 복사본(이벤트로 받아 둔 쪽)을 비교한다.

| # | 대상 | 원본 | 복사본 | 비교 단위 | 범위 |
| --- | --- | --- | --- | --- | --- |
| 1 | 코스 완주 | `run.records`의 `result_json.course.completed = true` | `course.course_completions`(`deleted_at IS NULL`) | 공개 중(`ACTIVE`) 코스마다 개수 · 기록 ID md5 | 완주 시각 2026-10-31부터 |
| 2 | 기록 거리 복사 | `run.records` | `ranking.distance_run_records`(`NOT deleted`) | 등록일(Asia/Seoul)마다 개수 · 기록 ID md5 | 등록 2026-10-15부터 |
| 3 | 탈퇴 회원 | `member.members`(`status = 'WITHDRAWN'`) | `run.withdrawn_members` | 개수 · 회원 ID md5 | 탈퇴 2026-10-15부터 |
| 4 | 공개 안 함 회원 | `member.members`(`ACTIVE`, `NOT info_public`) | `run.member_visibility_copies`(`NOT visible`, 탈퇴 제외) | 개수 · 회원 ID md5 | 전체 |
| 5 | 코스 상태 | `course.courses`(`status <> 'ACTIVE'`) | `run.gps_course_status_copies` | 코스마다 상태 | 숨김 2026-11-03부터 |
| 6 | 완주 수 카운터 (core 안) | `course.course_completions` 줄 수 | `course.course_stats.completion_count` | 공개 중 코스마다 값 | 코스 등록 2026-10-31부터 |

범위의 시작일은 복사본 표가 생긴 다음 날이다. 그 전 데이터는 복사본에 처음부터 없다(`course_completions` 2026-10-30, `distance_run_records` · `run.withdrawn_members` 2026-10-14, `gps_course_status_copies` 2026-11-02 마이그레이션). 4번은 회원 표에 바꾼 시각이 없어 범위를 자를 수 없다. 첫 실행에서 2026-10-27(`member_visibility_copies` 생성) 전에 바꾼 회원이 차이로 나오면 4장 4번으로 한 번 맞춘다.

공통 규칙:

- 1시간 전까지 생긴 것만 본다(`registered_at` · `withdrawn_at` · `created_at < now() - 1시간`). 아직 오가는 이벤트를 어긋남으로 보지 않는다. 1번은 두 DB에 같은 값이 있는 완주 시각으로 범위를 자르고, run은 `registered_at`, core는 받은 시각 `created_at`으로 1시간을 자른다.
- 3번은 두 DB의 시각이 같다. core가 탈퇴 시각을 이벤트(`withdrawnAt`)에 실어 보내고 run이 그 값을 그대로 저장한다(`RunService.withdraw`).
- 5번은 core 줄이 run에 같은 상태로 있는지만 본다. run에만 있는 줄(범위 시작 전에 숨긴 코스)은 무시한다.
- 1번은 core가 공개 중 코스 전체를 줄로 낸다(완주 0이면 개수 0). run 줄 중 core 목록에 없는 코스(숨김 · 삭제)는 무시한다. 코스 상태는 `ACTIVE → HIDDEN → DELETED` 한 방향이라, 공개 중 코스의 완주는 모두 공개 중일 때 일어났다.
- md5는 ID를 정렬해 이은 문자열의 md5다. 같은 집합이면 같은 값이다. 회원 ID는 PC 밖으로 보내지 않고 개수와 md5만 낸다. 코스 ID · 날짜 · 개수는 개인정보가 아니다.

뺀 것:

- 도전 수(`challenge_count`): 업로드하지 않은 코스 시도는 탈퇴할 때 run에서 지워지지만 빼기 이벤트가 없다(`RunRecordDeletedEvent`는 등록된 기록만). 그래서 run 시도 수와 다른 게 정상이다. core에 시도 단위 줄도 없다.
- 현재 러너 수: 계속 바뀌는 값이고, 시작 후 3시간이면 run이 스스로 정리한다.
- 리뷰 자격 복사(`review.course_run_records`) · 코스 랭킹 엔트리: 2번과 같은 모양으로 붙일 수 있다. 2번에서 어긋남이 나오면 그때 넣는다.

## 4. 어긋났을 때

먼저 workflow를 손으로 한 번 더 돌린다(Actions → 서버 사이 데이터 대조 → Run workflow). 같은 차이가 남으면 진짜다. 어느 ID가 다른지는 각 PC에서 SSH로 그 코스 · 날짜의 ID 목록을 뽑아 비교한다(5.3).

| # | 어긋남 | 고치는 법 |
| --- | --- | --- |
| 1 · 2 | run에 있고 core에 없다(완주 · 등록 이벤트 유실) | run DB에서 `UPDATE run.records SET registration_published = false WHERE id = '<기록 ID>'`. `RunProcessingWorker`가 2초 안에 `RunSessionEndedEvent`(필요하면 `CourseRunTrackEvent`도)를 다시 보낸다. 두 번 세지 않는다: 완주 수 증가와 완주 줄은 같은 트랜잭션이라 줄이 없으면 센 적이 없다. 거리 복사 · 리뷰 자격 · 고도 프로필은 기록 ID `ON CONFLICT`, 유지 기간 연장은 고정 구간마다 한 번이다(`RetentionEventHandler`) |
| 1 · 2 | core에만 있다(삭제 이벤트 유실) | run은 지운 기록의 ID만 남겨(`run.deleted_records`) 삭제 이벤트를 다시 만들 수 없다. core에서 SQL로 지운다. 1번은 `course_completions.deleted_at`을 채우고 `course_stats.completion_count`를 1 줄인다(`completion_seconds`는 기록 시간을 알 수 없어 못 고친다). 2번은 `distance_run_records.deleted = true` |
| 3 | core 탈퇴가 run에 없다 | 탈퇴 이벤트를 다시 보내야 run이 원본 · 결과를 지운다. 지금은 수단이 없다. 처음 나오면 `member.region_event_backfill` · `RegionEventBackfill`과 같은 방식(대기열 표에 회원을 넣으면 core가 이벤트를 다시 보낸다)을 탈퇴에 만든다. 개인정보라 가장 먼저 고친다. `run.withdrawn_members`에 줄만 넣으면 새 업로드는 막지만 남은 기록은 지우지 않는다 |
| 3 | run에만 탈퇴가 있다 | run은 탈퇴 이벤트로만 이 줄을 만든다. 생기면 안 되는 경우라 원인부터 본다 |
| 4 · 5 | 상태 복사본이 다르다 | run 복사본 줄을 core의 지금 값과 지금 `version`(`members.version` · `courses.version`)으로 넣거나 고친다. 받는 쪽처럼 `source_version`이 더 클 때만 바꾼다. 지금 `version`은 마지막 이벤트의 `version`보다 작지 않아, 늦게 오는 이벤트가 있어도 순서가 깨지지 않는다 |
| 6 | 카운터가 줄 수와 다르다 | `course_stats.completion_count`를 줄 수로 덮어쓴다. `completion_seconds`는 못 고친다 |

같은 종류가 두 번 이상 나오면 고치는 쪽을 코드로 만든다. 1 · 2번이 반복되면 `RunSessionEndedEvent` · `RunRecordDeletedEvent`의 `eventId`를 기록 ID에서 정해지는 값으로 바꾼다(지금은 보낼 때마다 `UuidV7.create()`). 그러면 `course.processed_events`가 중복을 걸러, 어떤 기록이든 다시 보내기만 하면 된다.

## 5. 워크플로

### 5.1 구성

`.github/workflows/reconcile.yml` 하나. 매일 04:30(Asia/Seoul)과 손으로 돌린다.

```yaml
on:
  schedule:
    - cron: '30 19 * * *'   # UTC 19:30 = 04:30 KST
  workflow_dispatch:
```

| 작업 | 러너 | 하는 일 |
| --- | --- | --- |
| `run-digest` | `[self-hosted, wadadak-run]` (run PC) | `docker exec -i wadadak-run-postgres-1 psql -U wadadak_run -d wadadak -At -F ,`로 5.2의 run 쿼리를 돌려 결과를 작업 출력으로 넘긴다 |
| `core-digest` | `[self-hosted, wadadak-core]` (core PC) | `docker exec -i wadadak-core-postgres-1 psql -U wadadak -d wadadak -At -F ,`로 core 쿼리를 돌린다 |
| `compare` | `ubuntu-latest` | 두 출력을 3장 규칙대로 비교한다. 다르면 차이를 작업 요약(`$GITHUB_STEP_SUMMARY`)에 쓰고 실패한다 |

- self-hosted 작업은 **checkout을 하지 않는다**. 쿼리는 workflow 안에 heredoc으로 둔다. 기본 checkout은 작업 폴더를 `git clean -ffdx`해 utilfile을 지운다([인프라 PC 분리](<인프라 PC 분리 - 2026-11-20.md>) 3장 6번).
- 결과는 artifact 대신 작업 출력(`$GITHUB_OUTPUT`, 여러 줄은 구분자 문법)으로 넘긴다. 공개 중 코스 수백 줄이면 한도(1MB)에 한참 못 미친다.
- 러너는 한 번에 한 작업만 돌아서, 배포 중이면 끝난 뒤 돈다. 쿼리는 읽기만 한다.
- 출력 줄 모양은 `종류,키,개수,md5`다. 5번은 `status,코스 ID,상태`, 6번은 `counter,코스 ID,카운터,줄 수`다.

### 5.2 쿼리

범위 시작 시각과 1시간 조건은 3장 그대로다. 아래는 2026-11-23 서버에서 그대로 돌려 본 쿼리다(7장).

run:

```sql
-- 1 코스 완주: 코스마다
select 'completions', r.result_json::jsonb #>> '{course,courseId}', count(*), md5(string_agg(r.id::text, ',' order by r.id))
  from run.records r
  where (r.result_json::jsonb #>> '{course,completed}')::boolean
    and (r.result_json::jsonb #>> '{course,completedAt}')::timestamptz >= '2026-10-31 00:00+09'
    and r.registered_at < now() - interval '1 hour'
  group by 2;
-- 2 기록 거리 복사: 등록일마다
select 'records', (registered_at at time zone 'Asia/Seoul')::date, count(*), md5(string_agg(id::text, ',' order by id))
  from run.records
  where registered_at >= '2026-10-15 00:00+09' and registered_at < now() - interval '1 hour'
  group by 2;
-- 3 탈퇴
select 'withdrawn', '', count(*), md5(string_agg(member_id::text, ',' order by member_id))
  from run.withdrawn_members
  where withdrawn_at >= '2026-10-15 00:00+09' and withdrawn_at < now() - interval '1 hour';
-- 4 공개 안 함
select 'hidden_members', '', count(*), md5(string_agg(member_id::text, ',' order by member_id))
  from run.member_visibility_copies v
  where not visible and not exists (select 1 from run.withdrawn_members w where w.member_id = v.member_id);
-- 5 코스 상태
select 'status', course_id, status from run.gps_course_status_copies;
```

core:

```sql
-- 1 코스 완주: 공개 중 코스 전체(완주 0이면 개수 0)
select 'completions', k.id, count(c.run_record_id), md5(string_agg(c.run_record_id::text, ',' order by c.run_record_id))
  from course.courses k
  left join course.course_completions c on c.course_id = k.id and c.deleted_at is null
    and c.completed_at >= '2026-10-31 00:00+09' and c.created_at < now() - interval '1 hour'
  where k.status = 'ACTIVE'
  group by k.id;
-- 2 기록 거리 복사
select 'records', (registered_at at time zone 'Asia/Seoul')::date, count(*), md5(string_agg(run_record_id::text, ',' order by run_record_id))
  from ranking.distance_run_records
  where not deleted and registered_at >= '2026-10-15 00:00+09' and registered_at < now() - interval '1 hour'
  group by 2;
-- 3 탈퇴
select 'withdrawn', '', count(*), md5(string_agg(id::text, ',' order by id))
  from member.members
  where status = 'WITHDRAWN' and withdrawn_at >= '2026-10-15 00:00+09' and withdrawn_at < now() - interval '1 hour';
-- 4 공개 안 함
select 'hidden_members', '', count(*), md5(string_agg(id::text, ',' order by id))
  from member.members where status = 'ACTIVE' and not info_public;
-- 5 코스 상태
select 'status', id, status from course.courses
  where status <> 'ACTIVE' and hidden_at >= '2026-11-03 00:00+09' and hidden_at < now() - interval '1 hour';
-- 6 완주 수 카운터(core 안에서 바로 비교)
select 'counter', s.course_id, s.completion_count,
       (select count(*) from course.course_completions c where c.course_id = s.course_id and c.deleted_at is null)
  from course.course_stats s join course.courses k on k.id = s.course_id
  where k.status = 'ACTIVE' and k.created_at >= '2026-10-31 00:00+09';
```

- 6번은 마지막 두 값이 다르면 실패다.
- 데이터가 늘어 `run.records` 전체 읽기(`result_json` 파싱)가 무거워지면, 1 · 2번을 최근 30일로 줄이고 전체 대조는 주 1회로 나눈다. 지금은 기록이 수십 건이다.

### 5.3 어긋난 ID 찾기

차이가 난 코스 · 날짜 하나만 각 PC에서 ID 목록으로 뽑아 비교한다. 회원 ID 목록은 화면에서만 보고 파일로 남기지 않는다.

run PC:

```powershell
"select r.id from run.records r where r.result_json::jsonb #>> '{course,courseId}' = '<코스 ID>' and (r.result_json::jsonb #>> '{course,completed}')::boolean order by 1;" | docker exec -i wadadak-run-postgres-1 psql -U wadadak_run -d wadadak -At
```

core PC:

```powershell
"select run_record_id from course.course_completions where course_id = '<코스 ID>' and deleted_at is null order by 1;" | docker exec -i wadadak-core-postgres-1 psql -U wadadak -d wadadak -At
```

## 6. 나중에

- 이벤트 처리 지연(`EventMonitor`의 10분 경고)도 알림으로 받는다. DLQ 잔류 · 소비자 없음 알림은 이미 있다(`deploy/observability`). 대조는 하루 늦게 알지만, 알림은 그 자리에서 안다.
- 탈퇴 다시 보내기(4장 3번)와 `eventId` 고정(4장 끝)은 해당 어긋남이 처음 나올 때 만든다.
